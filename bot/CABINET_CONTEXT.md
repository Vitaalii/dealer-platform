## 1. Что строим и зачем

Клиентский личный кабинет — отдельная веб-страница на поддомене дилерского
сайта (Tilda), вход по индивидуальной ссылке, которую агент «Александр»
присылает клиенту в чат, плюс подтверждение 4-значным кодом.

**Две цели:**

1. **Получение подтверждённого телефона** для перевода диалога на живого
   менеджера. Ссылка выдаётся **только клиенту, который не оставил телефон в
   чате**. Это главная цель.
2. **Структурированный сбор данных** по кредиту и трейд-ину, которые неудобно
   собирать в чате.

**Чего в кабинете НЕТ и не будет:** подписания кредитных условий, простой
электронной подписи, паспортных данных, загрузки файлов и фото, правки анкеты
после отправки, брендинга дилера. Всё это отменено в ходе проектирования —
если всплывёт в обсуждении, это устаревшая постановка.

- **Фото — каталожный рендер модели в дефолтном цвете**, не снимок машины

- В ответе есть также блок `car_history` (ДТП, залог, такси, штрафы) —
  в Deferred, в текущий скоуп не входит.

## 3. Ключевые решения и их обоснования

Принимались с разбором альтернатив. Переоткрывать без новых фактов не нужно.

### Модель доверия — TOFU (trust on first use)

Телефона в базе нет на момент выдачи ссылки, поэтому при первом входе OTP
подтверждает не личность, а владение номером. Идентичность держится на токене.

- `bound_phone` изначально пуст, заполняется при первой успешной верификации
  и фиксируется **навсегда** — переиграть нельзя.
- При последующих входах номер не спрашивается, код уходит на привязанный.
- До верификации страница не показывает ничего персонального.
- Остаточный риск пересланной ссылки принят: последствие — испорченный лид,
  не утечка данных.

**Практическое следствие для тестирования:** для каждого сценария нужен новый
`--user` и `--deal`, иначе телефон уже привязан.

### Одна активная ссылка, идемпотентная выдача

При наличии активного токена той же связки «клиент + дилер + сделка» агенту
отдаётся тот же URL: момент отправки выбирает LLM-агент, а он склонен
повторяться — при отзыве старого токена клиент получил бы `link_expired` по
ссылке из более раннего сообщения.

Исключения: другая сделка или другой дилер → старый токен отзывается.
Перепривязка после склейки дублей → токен сохраняется, обновляется `deal_id`.

Реализовано без хранения открытого токена: он выводится детерминированно через
HMAC от `issue_nonce`, в БД только хеш.

### Смягчённое требование неразличимости (R5)

Несуществующий, отозванный и истёкший токен дают один ответ `link_expired`;
гарантии по времени отклика нет. Обоснование: токен — 32 случайных байта.

### SMS — прямая интеграция с ProstoSMS

Механизм через роботы Bitrix24 спроектирован, проверен и **отклонён по
скорости**. Прямой вызов API из Python проще и даёт статус доставки.

Два канала: голос (`route=vc`) и SMS, **равноправный выбор клиента**, голос
может быть предвыбран. Автофолбэк голос → SMS как страховка.

Фолбэка «код в мессенджер» нет и не будет: он ломает основную цель — при
отправке кода в чат мы не получаем телефон.

### Миграции без Alembic

Собственная конвенция репозитория: идемпотентные `ALTER TABLE ... ADD COLUMN`
внутри `init_db()`. Введение Alembic потребовало бы baseline существующей
схемы на живой продовой базе.

### Передача заявки в Bitrix — существующим путём

Кабинет не создаёт параллельный механизм конверсии. `final_sync_wrapper` уже
ставит стадию `BITRIX_STAGE_QUALIFIED` и вычисляет статус через
`_map_type(scenario_type)`. Новых стадий и статусов не вводится.

Три триггера: явная отправка анкеты; таймаут бездействия от последнего сигнала
жизни (10 мин); абсолютный потолок от верификации (60 мин).

**Почему не отслеживаем закрытие окна:** событие выгрузки страницы теряется
при закрытии браузера, разряде батареи, обрыве связи. Прекращение фоновых
пингов `/cabinet/api/me` раз в 5 мин — надёжнее.

### Два компенсирующих сигнала дилеру

- **Сигнал A** — «запросил код, но не подтвердил номер, заявки в CRM нет».
  Отменяется верификацией.
- **Сигнал B** — «номер подтверждён, заявка передана, анкета не заполнена».

### Read-only анкеты после отправки

Оставлено как есть, но **спорное решение**: опечатку в VIN или доходе клиент
исправить не может. В Deferred как «правка анкеты с версионированием».

## 4. Размещение и раздача страницы

**Хостинг — Tilda, поддомен дилера, адрес `/cabinet`.** Адрес выводится из
поля `Website_URL` в таблице `Dealers` NocoDB (`muruk10ipof33m5`) добавлением
`/cabinet`. Схема обязана быть `https`. **Смена `Website_URL` применяется
только при рестарте бота.**

**На Tilda — заглушка, не вёрстка.** Один блок произвольного кода с
`#cabinet-root` и тремя скриптами. Вся разметка, стили и логика — в
репозитории бота, раздаются через `add_static('/widget-custom/')`.

**Порядок загрузки трёх скриптов обязателен:**

```html
<div id="cabinet-root"></div>
<script>window.UNIFIEDBOT_URL = 'https://<домен-бота>';</script>
<script src=".../calc_engine.browser.js?v=2026-08-06.1"></script>
<script src=".../calc_model.js?v=1"></script>
<script src=".../app.js?v=2"></script>
```

Движок и модель обязаны загрузиться раньше `app.js`.

**Версионирование обязательно и его легко забыть.** После правки `app.js`
нужно инкрементировать `?v=` именно у него — иначе CDN Tilda отдаст старую
копию, и правка «не применится». Уже наступали на это.

**Одна страница** со сменой экранов внутри. Токен приходит во фрагменте URL
(`/cabinet#t=<token>`) — фрагмент не уходит на сервер Tilda.

Дилеру: создать страницу, задать адрес `/cabinet`, **убрать шапку и подвал
лендинга**, вставить блок, опубликовать.

**Проверено по макету (2026-08-10):**
- Ставки нет **нигде** — ни в десктопной анкете, ни в мобильной, ни в одном
  из четырёх состояний `#slider-states`.
- Строки «Автосалон — <модель>» в `#auth` нет.
- Десктоп: срок и взнос в `duo` двумя колонками; `slider-head` — заголовок
  слева, значение справа на одной строке; `bounds` **под** ползунком; плитки
  `tiles--4` в четыре колонки; плитки канала `tiles--2`.
- Мобильный: `slider-head--tap` — три элемента (min, значение, max) **над**
  ползунком; плитки в столбец.

Решения по вёрстке, принятые при планировании:
- **Платёж — редактируемый ввод** (`money__input`), ввод = прикосновение.
- **Ползунки — нативный `input[type=range]`**; blocked-зона градиентом на
  треке плюс кламп в обработчике. Кастомные div-ползунки на тач конфликтуют
  с прокруткой.
- **Плитки — скрытый нативный `radio` + `label`**, не ARIA-роли на div.

## 7. Кредитный калькулятор

Расчёт выполняется **в браузере, синхронно**, при каждом движении ползунка.
Обращений к сети нет.

### Источник математики

`calc_engine.js` — канон, живёт в **репозитории n8n**
(`N8N/Alex_refactoring/flow/lib/`). `build_calc_engine_workflow.py` запекает
его в Code-ноду n8n и вторым выходом кладёт браузерную копию в статику бота.
**Формулы не переписывать и не портировать.**

Используются `calculatePMT`, `calculateMaxLoan`, `getSmartRate`, `round1k`,
`round10k`. Сценарные функции кабинету не нужны.

**Защита от дрейфа версий — двухуровневая:**
- Маркер `CALC_ENGINE_VERSION = "2026-08-06.1"` в каноне и
  `EXPECTED_CALC_ENGINE_VERSION` в `calc_model.js`; несовпадение → статус
  `engine_mismatch`.
- Контентная сверка нормализованного содержимого канона с браузерной копией —
  ловит случай «канон правлен без пересборки», когда маркеры совпадают.

**Билд-скрипт монолитен:** перезаписывает **четыре** воркфлоу, а не два —
`Tool_ Calc Engine.json`, `Test_ Calc Engine.json`, `Tool - Car Search.json`,
`Tool_ Combo Calculator.json`. Идемпотентность доказана диффом на неизменном
графе; при добавлении нод в граф доказательство придётся повторить.

Golden-тесты (`calc_engine.golden.test.mjs`, 13 кейсов) обязаны прогоняться и
на браузерной сборке.

### Модель зависимости величин — «последнее прикосновение выигрывает»

- правит платёж → пересчитывается взнос при текущем сроке
- двигает срок → пересчитывается взнос
- двигает взнос → пересчитывается платёж

**Ставка разрешается в два прохода**, как в n8n: черновая ставка → взнос →
финальная ставка по проценту → пересчёт платежа.

**Разрешение противоречия «последнее прикосновение» × «два прохода»:**
ведущая величина неприкосновенна, второй проход пересчитывает только ведомую.
Ручка не убегает из-под пальца.

**Округляется только ведущая величина.** Ведомая считается от округлённой.

**Границы** задаёт программа (`Min_Down_Payment_Pct`, `Max_Term_Months`, срок
от 12). Дефолт `Min_Down_Payment_Pct` без строки программы — **20**, как в
движке (`calc_engine.js:49`), а не 10.

**Платёж недостижим** (`status: "impossible"`): подставить минимально
возможное значение, показать пояснение, ползунки зафиксировать. Молча замереть
нельзя.

**Комбо:** взнос равен оценке трейд-ина и не регулируется. Поле «Доплата к
взносу» прибавляется к оценке перед расчётом — расширение `extraDown` внесено
в канон и покрыто golden-кейсами #10–12.

### Данные для расчёта

Замораживаются в `cabinet_profile` при генерации ссылки: `item_id`, `price`,
`target_payment`, `rates`, `program`, `found_info`, оценка трейд-ина. Причина —
скользящий TTL 30 дней: живые ставки за это время сменятся.

Отдаются в `/cabinet/api/me` **только после верификации**. Карточка авто и
фотографии тянутся живьём по `item_id` через `/cabinet/api/car`.

`Rates_Table_ID` и `Program_Table_ID` **уже приходят** в конфиг дилера
(`CACHED_DEALERS[...]["db_config"]`) — заводить ничего не потребовалось.

**Матчинг программы идёт по каталожному Id строки модели, не по
комплектационному `item_id`** — паритет с реальной нодой Get Program.
Промах предиката тихий: дефолтные границы ползунков без ошибки.

**Две точки заморозки:** при сборке payload и дополнительно при сохранении
кэша (`main.py:521–523`) — иначе в флагманском сценарии «выбрал → получил
ссылку» снапшот отставал бы на ход и `calc` был бы `null` именно там, где
калькулятор нужен.

**Неудачная заморозка никогда не затирает существующий снапшот.**

**Сверка при сабмите — по содержанию, не по времени:** 409 `conflict` только
если сменились `item_id` или `price`. Перезаморозка теми же данными
конфликтом не является — иначе 409 отлетал бы любому клиенту, который
параллельно переписывается с агентом. Поле снапшота в `submit` опционально:
отсутствует → проверка пропускается.

## 9. Фактический контракт API

**Истина в коде, не в брейншторме.**

Схема передачи токенов — по каждому эндпоинту (сверено по коду 2026-08-11:
`cabinet_api.py` хендлеры + `register_routes`). В кабинете ДВЕ разные схемы:
кабинетный токен ссылки до верификации и `Authorization: Bearer` после.

| Эндпоинт | Схема аутентификации |
|---|---|
| `POST /cabinet/api/auth/init` | кабинетный токен в теле: `{"token": …}` |
| `POST /cabinet/api/auth/request-code` | токен в теле (+ `phone`/`channel`/`consent`/`use_known`) |
| `GET /cabinet/api/auth/send-status` | токен ТОЛЬКО в заголовке `X-Cabinet-Token`; `?token=` не принимается — серверный фолбэк удалён, прежняя пометка «одна правка остаётся» неактуальна |
| `POST /cabinet/api/auth/verify` | токен в теле `{"token", "code"}` → в ответе `access_token` |
| `GET /cabinet/api/me` | `Authorization: Bearer <access_token>` |
| `PUT /cabinet/api/form` | `Authorization: Bearer` |
| `POST /cabinet/api/form/submit` | `Authorization: Bearer` |
| `GET /cabinet/api/car` | `Authorization: Bearer` |

`X-Cabinet-Token` существует только ради `send-status` (GET без тела — чтобы
токен не попадал в access-лог); все пост-верификационные эндпоинты — Bearer
(общая валидация `cabinet_service.py`, R37).

- `cabinet_status` — `not_visited` / `phone_confirmed` / `form_submitted`.
  `send-status` дополнительно возвращает служебные `none` и `expired`.
- Отправка кода синхронна в хендлере: ответ несёт фактический исход.
- Ответ `request-code` в паузе breaker или при неуспехе отправки —
  `retry_free`: попытка не засчитана.
- Пинг `/cabinet/api/me` раз в 5 минут двигает `last_seen_at`; отсчёт
  таймаута идёт от `max(last_seen_at, bound_at)`.
- Фронт шлёт заголовок `ngrok-skip-browser-warning` из единой точки `api()`;
  он же включён в whitelist `Access-Control-Allow-Headers`.

### Контракт с n8n: `evaluation_carryover`

Бот шлёт в `qualification_context` **на каждом ходе**:

```json
"evaluation_carryover": {
  "found_info": { ... },
  "ti_valuation": 450000,
  "request": { "plate": "А123БВ777", "mileage": 66000 }
}
```

Нет данных → **ключа нет вовсе**, а не пустой объект. Приёмная сторона
обязана терпеть отсутствие ключа.

`request` зарезервирован под будущее кэширование платной оценки на стороне
n8n — заложен сразу, чтобы не править бота вторым заходом.

## 10. Механика кэша — критично для стороны n8n

**Бот `n8n_cache` не очищает никогда.** Единственная операция записи —
полная перезапись ответом n8n (`main.py:526–527`).

Но при TTL 10 минут или переходе к стадии расчёта бот шлёт n8n
`cached_json = None` (`main.py:1123–1130`, `CACHE_TTL_SECONDS = 600`) — сигнал
пересобрать каталог. n8n перезапускает Car Search и возвращает свежий
`json_cache`, который затирает контекст целиком.

**Прежний кэш на rebuild-ходе не приходит ни под каким ключом** — ни в
`session_context` (слоты/счётчики/флаги), ни в `recent_history` (только
видимые реплики). Поэтому переносить данные оценки «из входящего кэша»
невозможно: источник пуст именно тогда, когда нужен. Отсюда и появился
`evaluation_carryover`.

**Следствие:** вливание carryover обязано выполняться при **каждой**
пересборке кэша, иначе данные оценки исчезнут примерно на десятой минуте
диалога.

**Ловушка порядка:** подмешивать carryover можно только **после** Cache Gate.
Гейт различает ходы по непустоте `cached_json` — влей carryover до него, и
rebuild-ход увидит непустой объект, уйдёт в обход Car Search, а каталог
перестанет обновляться.

Хелпер подмешан во **все три** выхода, возвращающие `json_cache` (не только
Final Response): кабинет морозит снапшот на каждом ходе, и байпас-ход или
ход-напоминание без ключей обнулили бы снапшот.

`session_context_update` как канал **не работает**: бот этот ключ ответа не
читает вовсе, `session_context` пересобирается из его собственного контекста
на каждом ходе.

## 11. Платные вызовы auto.ru — открытая проблема

**Структурно подтверждено:** подпоток оценки исполняется **безусловно при
каждом вызове Combo Calculator**, до всего остального, без гейта и без кэша
(`Execute Workflow Trigger → Parse Input → Execute Workflow (оценка) → If`).
Каждый пересчёт комбо («а если платёж 35?») — ещё один заход.

Внутри воркфлоу **четыре HTTP-ноды** к auto.ru (`predict_by_vin_or_lp` и
`stats/predict`, по паре в основной и retry-ветке); на одно исполнение
отрабатывает от одной до трёх. **«Исполнение» и «платный запрос» — не одно и
то же; на чём считает биллинг, нужно уточнить по договору.**

**Замер по логам невозможен ретроспективно:** ретенция n8n 2.5 суток, в окне
нашёлся ровно один комбо-диалог с одним вызовом, и клиент в нём не просил
пересчёта. Сценарий «десяток» не опровергнут — он не наблюдался.

**Промптовое лечение сейчас нереализуемо:** модель оценку не видит. В
`ai_clean_context` ноль вхождений `ti_valuation` / `found_info`; белый список
отдаёт только `user_id`, `deal_id`, `model`, `user_data`, `user_request`,
`complectations`. Хуже: активные блоки `D_TRADEIN` и `D_COMBO` говорят «JSON —
твой ЕДИНСТВЕННЫЙ источник правды», а правило «запрещено называть цифры
выкупа до вызова `evaluate_auto`» вместе с безпамятной архитектурой агента
(ни одной memory-ноды из 35) **предписывает** повторный вызов.

Единственный блок с запретом повторного вызова, `WF_TRADEIN_LEGACY`, выключен.

**Согласованный порядок лечения** (обратный интуитивному):
1. Вывести `ti_valuation` в `ai_clean_context` (~5 строк, та же форма, что
   U5) — **обязательный спутник** промпт-правила, без него правило косметика.
2. Правка промпта: «есть `found_info`/`ti_valuation` в кэше → повторно
   `evaluate_auto` не вызывай; повторный вызов только при смене госномера или
   пробега». Покрывает **оба** маршрута, графа не трогает.
3. Повторный замер с **заранее включённым** сбором.
4. Только потом решение по кэшу `(plate, mileage)` на стороне n8n — по
   фактическим числам.

Кэш оценён и **не начат**: отдельный план на 3–4 юнита, риск средне-высокий,
покрывает только комбо-маршрут. Главный риск — не логика, а билд: добавление
ноды в граф Combo Calculator может сломать доказанную идемпотентность
монолитного `build_calc_engine_workflow.py` и утащить защищённые Calc Engine
JSON.

## 12. Прод-баг `init_db()` — гейт деплоя

**Найден и исправлен (коммит `63646c8`), в прод ещё не выкачен.**

Весь `init_db()` был обёрнут в один `engine.begin()` — одну транзакцию.
Первым оператором стоял легаси `ALTER TABLE users RENAME COLUMN max_user_id
TO platform_user_id`, который падал на **каждом** старте (колонки давно нет).
Исключение проглатывалось, но PostgreSQL помечал транзакцию как отравленную,
и на выходе `COMMIT` превращался в `ROLLBACK` — откатывалось всё, включая
`create_all`. И печаталось «✅ Database initialized successfully».

Прод жил только потому, что откатывать было нечего: схема полная,
`create_all` при полной схеме — no-op. Проверено запросом к прод-базе: все
девять колонок `users` на месте, включая `channel`.

**На деплое кабинета это был бы полный отказ:** шесть новых таблиц создаются,
затем откатываются, бот стартует, любой запрос к кабинету падает с «relation
does not exist», в логе галочка. Воспроизводимо на каждом рестарте.

**Фикс:** DDL по отдельным коротким транзакциям, недостающие колонки через
инспектор SQLAlchemy (штатных исключений нет вовсе), легаси-`RENAME` удалён,
«✅» печатается только после проверки фактической полноты схемы.

**Правило:** `63646c8` должен уехать на прод **первым или одновременно** с

## 16. На что посмотреть при реализации

1. **Версионирование скриптов на Tilda.** После правки `app.js`
   инкрементировать `?v=` именно у него. Уже наступали.
2. **Пинг должен двигать `last_seen_at`.** Иначе клиент, читающий анкету без
   правок, уедет в CRM через 10 минут при открытой вкладке.
3. **Единственный комментарий о брошенном черновике.** Сценарий «подтвердил
   телефон, ничего не заполнил, ушёл» должен давать ровно один комментарий.
4. **Проверочная отправка на четыре сети** (МТС, Мегафон, Билайн, Tele2) с
   замером задержки. Она же зафиксирует фактические `reporter`/`state` в
   колбэке ProstoSMS — сейчас в коде предположение по DLR-семантике.
5. **Антифлуд оператора** может сработать на автофолбэк голос → SMS с тем же
   кодом.
6. **Прод-режим** определяется явным `ENVIRONMENT=production`, не эвристикой
   по `DATABASE_URL`.
7. **Процессное состояние лимитов и breaker'а** корректно только при
   однопроцессном развёртывании.
8. **Особенность выката:** подбор зависших захватов ориентируется на
   отсутствие события `handoff_done`. Токены, захваченные до выката, при
   первом тике будут доведены повторно.
9. **Инлайн-заморозка в per-turn пути** дублирует фоновую того же хода и
   добавляет обращение к NocoDB **без таймаута** перед вызовом n8n — то есть
   в критический путь ответа клиенту в чате. Стоит закрыть до релиза.

## 17. Уроки, зафиксированные в `docs/solutions/`

- **Naive datetime в `timestamptz` интерпретируется по таймзоне машины**, а не
  как UTC (доказано пробой: −8 часов). Договорённость «naive, но по
  соглашению UTC» не работает — интерпретацию выбирает драйвер. Второй случай
  того же класса после находки №3 прошлого ревью (та про чтение, эта про
  запись). Поставлен страж: `datetime.utcnow` и `datetime.now()` запрещены в
  кабинетных модулях, `database.py` и всех тестах; легаси `main.py` запинено
  точными счётчиками (1 + 14).
- **Тесты гоняются на том же движке, что в проде.** Два прогона на настоящем
  PostgreSQL дали два прод-бага, невидимых для SQLite-сюиты из 372 тестов.
- **CORS проверяется по-браузерному.** Тестовый клиент aiohttp preflight не
  исполняет; нужен тест, проверяющий `Access-Control-Allow-Origin` на
  **успешных** ответах каждого эндпоинта, а не только на preflight.
- **Кириллический омоглиф** — русская «С» вместо латинской «C» в
  идентификаторе (`Сonsumption`). Визуально неотличимо, поле молча не
  находится. Стоит завести страж на кириллицу внутри идентификаторов.
- **Сверка по содержанию, а не по времени** — 409 при сабмите.
- **Секреты:** приватность репозитория не защищает; `.gitignore` заводится
  **до** `git init`, значения переменных проверяются грепом по содержимому
  индексируемых файлов, а не только по именам.
- **`ClientTimeout` объектом, а не числом.**
- **NocoDB-токен никогда в клиентский JS** — только через серверный прокси.
- **Медиазапрос макета переносится как есть** — брейкпоинт не выбирается
  заново; `--tap`-модификаторы — укрупнение под палец, а не «второй набор
  вёрстки» (прежний вывод о «галерее двух наборов» опровергнут; 2026-08-11).
- **Ширина контейнера не проверяется грепом по CSS** — только замером
  computed-ширины в браузере: итерация, принятая по грепам, приехала
  с корнем 520px (2026-08-11).
- **Формула из n8n без области поиска n8n — молчаливое чужое совпадение**:
  сравнение по Complectation id скопировано дословно, но n8n ищет в массиве,
  отфильтрованном одной моделью, а бот — по всему каталогу, где id не
  уникален (по выгрузке дилера 99: id 11 — 7 строк разных моделей).
- **Идемпотентность выдачи токена проверяется по содержимому таблицы после
  нескольких ходов**, не по коду ветки выдачи: зелёная ветка «тот же URL»
  ничего не говорит о границе процессов (у скрипта выдачи был СВОЙ дев-ключ
  HMAC — бот и скрипт взаимно отзывали токены). Ключ детерминированного
  вывода — часть контракта всех процессов над одной таблицей; ответ на
  невоспроизводимость — сохранить и просигналить, не отозвать (2026-08-12).
