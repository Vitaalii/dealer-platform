### П. 3 — согласие, поп-апы, NocoDB

**Текущий текст подписи** — константа `CONSENT_TEXT`, `app.js:62-63`:

> Я ознакомлен(а) с Политикой конфиденциальности и даю Согласие на предоставление и обработку персональных данных

Обе целевые фразы присутствуют дословно; «Согласие на предоставление» — начало
более длинной фразы «Согласие на предоставление и обработку персональных данных»
(границу кликабельной зоны решает владелец, см. открытые вопросы). Рендер —
`app.js:822`: `esc(CONSENT_TEXT)` текстовым узлом в `span.check__text` внутри
`<label>` чекбокса; для ссылок сборку придётся заменить на конкатенацию
экранированных кусков с кликабельными обёртками. Ссылки внутри `<label>` требуют
гашения дефолтного поведения (клик по ссылке не должен переключать чекбокс).

**Путь данных дилера до фронта:**
1. NocoDB `muruk10ipof33m5` → `load_data_from_nocodb` (`main.py:1471-1553`),
   строит `CACHED_DEALERS` (`main.py:104`) **явной проекцией полей**
   (`main.py:1523-1550`) — новые колонки автоматически в кэш **не попадают**,
   нужно явно добавить в словарь.
2. `CACHED_DEALERS` → `cabinet_service` через `_dealers_provider`;
   `_dealer_payload` (`cabinet_service.py:927-931`) отдаёт фронту только
   `name` и `brand_model`.
3. Фронт: `POST /cabinet/api/auth/init` (`app.js:2848, 2917`), ответ строится в
   `auth_init` (`cabinet_service.py:936-955`), ключ `dealer` есть в обеих ветках
   (`bound` и `need_phone`) — расширение ложится сюда; эндпоинт доступен до
   авторизации, что и нужно экрану согласия. Сейчас фронт поле `dealer`
   не читает вовсе (grep `dealer` по `app.js` — ноль обращений к `initData.dealer`).

**Живой запрос к NocoDB (2026-08-31, `GET /api/v2/tables/muruk10ipof33m5/records`):**
- Колонки `Policy` и `Agreement` существуют и приходят в API-ответе без
  специальных параметров (полная строка дилера 99 содержит оба ключа).
- Заполнены только у дилера 99: `Policy` — 17 577 символов, 260 переносов строк;
  `Agreement` — 6 648 символов, 25 переносов. Символа `<` нет — чистый текст,
  не HTML. У остальных 14 дилеров оба поля `null`.

**Кэш справочника дилеров:** загрузка — один раз на старте (`init_app`,
`main.py:3859`) плюс watchdog `ensure_dealers_loaded` (`cabinet_service.py:1425`),
который повторяет загрузку **только пока кэш пуст**. Периодического рефреша и
admin-эндпоинта перезагрузки нет → после посадки правок полям нужен **рестарт
бота**; до рестарта пустые поля в ответе — не ошибка реализации (учесть в приёмке).

**Фильтрация `ncRecordHash`/`thumbnails`** (`main.py:1633-1636`) относится к кэшу
каталога (`DICT_STOCKS`, refresh stock) — к таблице дилеров не применяется,
`load_data_from_nocodb` ничего не вычищает. Новые текстовые поля она не задевает.

**Механизмы поп-апов в кабинете — два:**
- `#cab-popup` (ошибки: `showConflictPopup` `app.js:1477-1500`,
  `showFormNetworkErrorPopup` `app.js:2730-2757`) — монтируется в `document.body`,
  стили — параллельные селекторы по id (`app.js:183-194`); ровно урок хендоффа
  «стили на id + mount в body». Но диалог узкий (400px), без скролла и крестика.
- `#cab-car-popup` (характеристики авто, `app.js:1708-1830`) — `popup--wide`:
  720px, `max-height` + `overflow:auto` (`app.js:326`), крестик/оверлей/Esc, но
  живёт **внутри** `#cabinet-root` (комментарий `app.js:175-180`) и к body-mount
  не готов.
- Вывод: ни один в чистом виде не переиспользуется — нужен небольшой третий:
  текстовый поп-ап по образцу `#cab-popup` (body-mount, id-стили, поверх экрана
  авторизации) со скролл-поведением от `popup--wide` (тексты 6–17 тыс. символов).

**Вставка текста:** безопасный дефолт — текстовый узел (`textContent`) + CSS
`white-space:pre-wrap`: переносы `\n` сохраняются, никакой будущий HTML в полях
не исполнится. Вставка через `innerHTML` исполнила бы разметку — вопрос
санитизации вынесен владельцу (см. открытые вопросы).

## Key Technical Decisions

1. **П. 5 суффикс** — внутри существующего литерала, условно при
   `tiValuation != null`; отдельный DOM-элемент не заводится.
2. **П. 2 селектор** — добавочное правило `#cabinet-root .card .divider--md`
   рядом с текущим (`app.js:102`), глобальное правило не трогаем. Область — три
   экрана потока авторизации (дефолт до ответа владельца, легко сузить).
3. **П. 3 транспорт** — `Policy`/`Agreement` добавляются в проекцию
   `CACHED_DEALERS` и в `_dealer_payload`/`auth_init`; отдельный эндпоинт не
   заводится (~24 КБ на первом запросе сессии, gzip ужмёт; поп-ап открывается
   мгновенно и оффлайн-устойчиво). Alternative rejected: ленивый
   `GET /cabinet/api/consent-docs` — лишний роут и состояние загрузки ради
   экономии, несущественной на этом трафике.
4. **П. 3 вставка** — текстовый узел + `white-space:pre-wrap` (безопасный
   дефолт до решения владельца о санитизации).
5. **П. 3 поп-ап** — новый текстовый компонент по паттерну `#cab-popup`
   (body-mount, параллельные id-селекторы — урок хендоффа) со скроллом как у
   `popup--wide`.
6. **П. 6 механизм** — константа-флаг вверху `app.js`
   (`HIDE_PERSONAL_TILES_IN_COMBO = true`) + условие в `showPersonal`:
   `scenario === 'combo' && HIDE_PERSONAL_TILES_IN_COMBO` → не рендерим.
   Код блоков не удаляется, откат — однострочный. Alternatives:
   CSS `display:none` (блоки в DOM: фокусируемы, видны в таб-обходе и
   инспекторе — хуже) и бэкенд-конфиг (оверкилл для «вернуть возможно»).

## Open Questions (владельцу, до старта соответствующих юнитов)

- **В1 (п. 2, блокирует U2):** «экран авторизации» — все три экрана потока
  (ввод телефона, выбор канала, ввод кода; у всех один заголовок «Авторизация»)
  или только первый? Дефолт плана — все три.
- **В2 (п. 3, U4):** санитизация текстов поп-апа. Дефолт — «только текст,
  переносы сохраняются» (HTML в полях никогда не исполнится). Альтернатива —
  вставка как разметки: любой будущий HTML в полях NocoDB исполнится в браузере
  клиента; тогда нужен санитайзер.

## Risks & Notes

- Grep-тесты фронта пиновают точные строки — правки текстов сопровождать
  обновлением пинов в том же коммите (ловушка хендоффа §5).
- Приёмка п. 3: до рестарта бота поля в `auth/init` пусты — это кэш, не дефект.
- Поп-ап согласия на экране авторизации: `setScreen` перерисовывает экран при
  смене канала/шагов — body-mount переживает перерисовку; закрытие при
  навигации проверить руками (см. Verification U4).
