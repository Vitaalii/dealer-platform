# feat: Гейт UF_CRM_65B0A5E1003B2 на единый предикат телефона

## Резюме

Поле Bitrix `UF_CRM_65B0A5E1003B2` («Канал коммуникации (квалиф)», env `BITRIX_FIELD_CHANNEL`) получает двух владельцев: до квалификации — Тильда (значения `web`/`max`/`tg`), после — бот (значение «По телефону»). Критерий перехода владения один: валидный телефон по `database.is_valid_phone` (database.py:430). Значение «В MAX» из логики бота уходит. Пока телефона нет — бот не отправляет ключ вовсе, значение Тильды остаётся нетронутым.

Разведка подтвердила: сегодня бот затирает значение Тильды тремя присваиваниями «В MAX» без телефона (main.py:2548, 2563, 2596), запись уходит через два билдера payload (main.py:359, 378) по всем путям схождения сделок, включая охоту за дублем (main.py:2035). Замер по живому CRM: поле — тип **string** (не список), дефолт «По телефону»; в базе 143 сделки с «В MAX».

---

## Постановка

**Требование владельца.** Бот пишет в поле ровно одно значение — «По телефону» — и ровно при одном условии — `is_valid_phone`. Без телефона ключ не отправляется. Интент, режим дилера, способ передачи — не критерии.

**Проверенное утверждение владельца.** «В режимах Manager и SmartBot клиент не может выбрать связь в мессенджере» — подтверждено для кнопок: в Call клавиатура выбора подавлена (main.py:1799-1800), в Smartbot/Call вопрос о способе связи вырезается и автоматически триггерится «ПО ТЕЛЕФОНУ» (main.py:2580-2603), в Manager текст заменяется финализацией и клавиатура обнуляется (main.py:2592-2596, 2607-2608). Остаточный канал — свободный текст: Dialogflow может вернуть интент `11_Contact_Telegram` на фразу «в мессенджере» в любом режиме до активации ИИ (main.py:2561-2563) — гипотеза, зависит от конфигурации DF-агента. Устранение «В MAX» из логики закрывает и этот канал.

---

## Ключевые технические решения

### КТР-1. Двухуровневая защита: снятие присваиваний + гейт в билдерах

Убрать три присваивания «В MAX» недостаточно: `channel_val: "В MAX"` уже персистирован в `context_json` живых пользователей и в снапшотах кабинетной конверсии — после деплоя он продолжил бы уходить в CRM через `update_deal_data`/`create_deal_with_contact`. Поэтому:

1. **Источник** — в финализации остаётся единственное присваивание `channel_val = "По телефону"` при `has_valid_phone` (main.py:2558-2560); три присваивания «В MAX» удаляются.
2. **Гейт на выходе** — в обоих билдерах (main.py:345-361, 372-380) ключ `F_CHANNEL` включается только если значение равно «По телефону» **и** телефон валиден. Это единая точка контроля, закрывающая все пути: `final_sync_wrapper`, `background_deal_hunt`, кабинетную конверсию, устаревшие контексты.

Существующей фильтрации `None` (main.py:363, 383) достаточно только для отсутствующего ключа; она не защищает от унаследованных «В MAX» в персистентных контекстах — потому гейт обязателен.

**Известный остаток:** строки `pending_sync` (очередь повторов, main.py:3366-3374) реплеят замороженный payload как есть — уже поставленные в очередь обновления со старым «В MAX» доедут после деплоя. Объём мал (очередь — аварийный путь), скраб очереди не предлагается; зафиксировано как принятое переходное поведение (ОВ-3).

### КТР-2. Потребители channel_val внутри бота не переезжают на CRM-правило

`channel_val` читают ещё два места, не связанных с Bitrix: карточка-алерт менеджеру («Способ связи: …», main.py:1003-1029) и архив NocoDB (`Final_Status`, main.py:2840-2848). После снятия «В MAX» алерт покажет «Не указан», архив — `DF_Finalized`. Это видимое продукту изменение — вынесено владельцу (ОВ-2).

## Юниты

### U1. Снятие «В MAX» из финализации чата

**Цель:** единственный источник значения — валидный телефон.
**Файлы:** main.py (блок финализации ~2542-2600).
**Подход:** удалить присваивания main.py:2548 (`__SYSTEM_TIMEOUT_HANDOFF__`), 2563 (интент 11), 2596 (Manager-форсинг). Оставить 2560. Ветки финализации (is_final_step, scenario_type) не трогать — меняется только запись `channel_val`.
**Оценка:** S.
**Тест-сценарии:**
- Финализация с валидным телефоном (интент 10/12) → в снапшоте `channel_val == "По телефону"`.
- Таймаут-хендофф Smartbot без телефона → `channel_val` отсутствует в снапшоте.
- Manager-форсинг без телефона → `channel_val` отсутствует, `is_final_step` истинен.
- Интент 11 (мессенджер) → `channel_val` отсутствует, финализация происходит.

### U2. Гейт в билдерах BitrixService

**Цель:** ключ `F_CHANNEL` уходит в CRM только при «По телефону» и валидном телефоне; унаследованные «В MAX» из персистентных контекстов отсекаются.
**Зависимости:** независим от U1 (защита сработает и без него), но по смыслу пара.
**Файлы:** main.py (`create_deal_with_contact` ~345-364, `update_deal_data` ~371-387).
**Подход:** в оба билдера добавить условие эмиссии ключа. Валидность телефона: в `create_deal_with_contact` телефон уже аргумент; в `update_deal_data` телефона нет — либо пробрасывать, либо гейтить по значению (`== "По телефону"`), что достаточно при выполненном U1. Развилку решить на реализации: минимум — гейт по значению (закрывает «В MAX» навсегда), максимум — ещё и по предикату.
**Оценка:** S.
**Тест-сценарии:**
- Контекст с унаследованным `channel_val: "В MAX"` → `crm.deal.update` уходит **без** ключа `F_CHANNEL` (значение Тильды не затирается).
- Контекст с «По телефону» → ключ уходит со значением «По телефону».
- Контекст без `channel_val` → ключа нет (текущее поведение, пин).
- То же для `create_deal_with_contact`.
- Кабинетная конверсия со старым снапшотом «В MAX» → ключ не уходит.

### U3. Кабинетная конверсия пишет «По телефону» (условный — ждёт решения владельца, ОВ-1)

**Цель:** OTP-подтверждение в кабинете = квалификация → поле переходит боту.
**Файлы:** cabinet_service.py (`build_conversion_snapshot` ~2474-2524), тест tests/test_cabinet_handoff.py.
**Подход:** по образцу `CABINET_TYPE_KEY` — снапшот-only ключ, ничего не персистится: при активном токене и подтверждённом телефоне (`User.phone` валиден после OTP) выставлять `snapshot['channel_val'] = "По телефону"`, не перетирая уже стоящее «По телефону» из чата. Техническая возможность подтверждена: снапшот уже дополняется полями поверх context_json (cabinet_service.py:2509-2523).
**Оценка:** S-M.
**Тест-сценарии:**
- Конверсия с подтверждённым телефоном → снапшот несёт «По телефону».
- Конверсия без подтверждённого телефона → ключа нет.
- Чатовое «По телефону» в context_json не перетирается.

### U4. Тестовый контур

**Цель:** зафиксировать оба правила и не сломать базу 602+4 (SQLite) / 606 (PostgreSQL).
**Файлы:** новый tests/test_channel_field_gate.py (или секция в tests/test_cabinet_handoff.py — там уже пины билдеров F_TYPE, строки 892-925, образец монкипатча `_request`).
**Подход:** тесты U1/U2/U3 из сценариев выше; существующие тесты билдеров (test_update_deal_data_*) не затрагиваются — их контексты не содержат `channel_val`.
**Оценка:** M.

## Открытые вопросы владельцу (до старта)

**ОВ-1. Писать ли «По телефону» из кабинетной конверсии (U3)?**
- Вариант А — писать (снапшот-ключ при подтверждённом OTP-телефоне). Плюс: правило «есть валидный телефон → поле бота» едино для чата и кабинета; поле заполнено у кабинетных заявок, где чат мог не дойти до финализации. Минус: +1 юнит работы и тесты. Оценка: S-M.
- Вариант Б — не писать (кабинет наследует то, что записал чат; без чатового «По телефону» остаётся значение Тильды). Плюс: ноль работы. Минус: OTP-квалифицированные заявки могут остаться с `web`/`max` — по смыслу требования это уже «этап бота». Оценка: 0.
- Рекомендация: Вариант А — он буквально следует критерию владельца «один критерий — валидный телефон».

**ОВ-2. Видимые следствия вне CRM.** После снятия «В MAX»: карточка-алерт менеджеру покажет «Способ связи: Не указан» (main.py:1003, 1029), архив NocoDB — `Final_Status: DF_Finalized` вместо «В MAX» (main.py:2840-2848). Призыв «свяжитесь с клиентом в MAX» в алерте сохраняется (условие main.py:1007 — «не По телефону»). Принять как есть или сохранить внутренний маркер для алертов/архива отдельно от CRM-записи?

**ОВ-3. Переходный хвост.** Уже стоящие в `pending_sync` payload'ы со старым «В MAX» доедут в CRM после деплоя (реплей шлёт замороженные поля, main.py:3369-3372). Принять (объём — единицы, очередь аварийная) или добавить одноразовый скраб очереди?

**ОВ-4 (справочно).** Замер: значения `tg` в CRM нет ни в одной сделке (0 из ~10.5 тыс.), `web` — 429, `max` — 1583. Если tg-источник должен писать `tg` — это вопрос к Тильде/интеграции, вне этого плана.

## Вне объёма

- Миграция 143 существующих сделок с «В MAX» — по прямому указанию владельца не предлагается; карточки остаются как есть.
- Изменение списка значений поля в Bitrix — не требуется: поле строковое (замер `crm.deal.userfield.list`: `USER_TYPE_ID: "string"`), а не списочное; никаких элементов списка заводить не нужно.
- Дефолт поля «По телефону» на стороне Bitrix (замер: `SETTINGS.DEFAULT_VALUE`) — поведение UI-форм CRM, ботом не управляется.
