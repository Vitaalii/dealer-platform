# fix: Чистый лист истории для Александра с момента передачи

## Summary

Александр перестаёт наследовать транскрипт воронки квалификации: в момент AI handoff бот ставит в `chat_history` маркер границы передачи, а производная `recent_history` для n8n собирается только от последней границы и без служебных строк-кнопок — на INIT-ходе и на всех последующих. Архив `chat_history` остаётся нетронутым источником правды; правки — только в производной.

## Problem Frame

Дев-стенд, MAX, кредит: первое сообщение Александра нарушило его блоки — попросило телефон вместо расчёта. Диагноз n8n (исполнение 3316): промпт собран правильно, единственное различие с корректным веб-сценарием — содержимое `recent_history`. В MAX туда попал хвост воронки, последняя реплика которого («Для получения расчета, подтвердите Ваши контакты») оставила висящий вопрос — модель его продолжила. Веб отработал верно случайно: режим Manager подменяет финал одной нейтральной строкой.

Глубже симптома два системных дефекта: (1) окно «последние 8 строк» тянет хвост воронки и на второй-третий ход Александра, пока живой диалог его не вытеснит — фикс только INIT-хода вернул бы дефект там, где его никто не ищет; (2) в истории лежат строки с ролью «клиент», которые клиент не писал — кнопки типа «ПО ТЕЛЕФОНУ» при дилерах Call/Smartbot нажимает сам бот (служебная механика запуска сценария), и модель может сослаться на «выбор», которого не было.

## Фактура: где собирается recent_history и что туда попадает

**Сборка одна на все каналы и оба режима.** `recent_history` строит `payload_v2.build_recent_history` из `ctx['chat_history']`: последние 8 строк ролей user/bot, фильтр только по префиксам `__SYSTEM`/`INIT_AI_HANDOFF` (`payload_v2.py:141-152`). Вызывается в обеих точках сборки payload — chat-ход (`main.py:1305-1307` через `extend_payload`) и INIT-ход (`main.py:1413`). По каналам и режимам сборка НЕ отличается — отличается содержимое `chat_history` к моменту передачи:

- **Запись реплик клиента** — одна универсальная точка `main.py:2106-2117`: всё, включая тексты кнопок (`type: "button"`) и `__SYSTEM_TIMEOUT_HANDOFF__`.
- **Запись реплик бота воронки** — `main.py:2569` (стандартная отправка), `2535` (усечённый финал перед авто-нажатием), `2611` (30-сек таймер Smartbot), `2044` (перехват возражения).
- **Висящий вопрос** «Для получения расчета, подтвердите Ваши контакты» — подмена текста `main.py:2411-2418`, в историю через `2569`.
- **Режимы** (per-канал: `comm_type` MAX / `comm_type_td` web / `comm_type_tg` TG — `main.py:1447-1455, 2504-2512`): `Manager` подменяет финал на «Принято! Ваш запрос отправлен специалисту ⚡» и сразу передаёт (`main.py:2528-2531`); `Smartbot` передаёт только без телефона, плюс путь 30-сек таймера; `Chat`/`Call` в ветку A не входят — **INIT_AI_HANDOFF у них не бывает** (`main.py:2641-2645`, ветка B `2724-2741`).
- **Кнопки, нажимаемые ботом, — случай существует**: для дилеров Call/Smartbot на интентах 03/05/08/90/91 бот рекурсивно вызывает `process_input(user_id, "ПО ТЕЛЕФОНУ", ..., input_type="button")` (`main.py:2515-2538`), клиент клавиатуру не видит (`main.py:1743-1745`). В истории строка неотличима от человеческого нажатия — оба пишутся как `{"role": "user", "type": "button"}`.
- **Границы передачи в данных сегодня нет**: в момент handoff пишутся только `is_smartbot_active=True` (`main.py:2672-2674`), стадия Bitrix и `deal_id`; ни таймстампа, ни маркера в `chat_history` (строка `INIT_AI_HANDOFF` живёт только в payload, `main.py:1376`).

## Карта потребителей chat_history — что нельзя сломать

| Потребитель | Где | Вердикт |
|---|---|---|
| `recent_history` → n8n | `payload_v2.build_recent_history`, обе точки payload | Меняем намеренно — это и есть задача |
| `msg_count` и стадийная эвристика | `payload_v2.build_session_context:203` считает user-строки ПОЛНОЙ истории | НЕ переводить на срез: `msg_count==0 → greeting`, срез дал бы greeting на INIT вместо `tool_needed` (R4) |
| `last_bot_message` → AI-рерайт ремайндера | `main.py:3066-3072` → payload `1231` | Не трогаем: читает сам `chat_history`; после первого УСПЕШНОГО ответа ИИ последняя bot-строка — реплика Александра. При сбое INIT (одна попытка, без ретраев — `main.py:1416-1428`) ремайндер может рерайтить финал воронки — существующее поведение, зафиксировано в Рисках |
| Нормализация ссылки `[CABINET_LINK]` | `normalize_bot_text_for_history` пишет В `chat_history` (4 точки) | Не трогаем: пишет в источник, а не в производную |
| Архив: стенограммы NocoDB + Bitrix-таймлайн | `finalize_transcript_archive`, `format_chat_history` | Источник правды — не фильтруем; новая system-строка маркера в стенограмме видна (это плюс: менеджер видит момент передачи) |
| Восстановление контекста | `load_context_from_db` | Формат строк истории не меняется; добавляется один новый `type` у system-строки |

## Варианты решения и цена

- **A. Пустая история только на INIT.** Цена минимальная (одна точка `main.py:1413`). Не решает: хвост воронки возвращается на ходах 2-3 через окно последних 8 строк, псевдо-нажатия остаются навсегда. Отклонён.
- **B. Фильтр служебных строк (`type=="button"`).** Дёшево и надёжно (машинный признак уже пишется, текстовых эвристик не нужно). Но сам по себе не решает: висящий вопрос — реплика бота, не кнопка. Нужен, но недостаточен.
- **C. Обрезка последней реплики воронки «если содержит вопрос».** Текстовая эвристика («что считать вопросом») хрупка, чинит один частный симптом, не чинит псевдо-нажатия и вторые ходы. Отклонён.
- **D. Рекомендация (принята владельцем): граница передачи + фильтр кнопок.** Маркер в `chat_history` в момент handoff; производная для n8n собирается от последней границы и без `type=="button"`. INIT получает пустую `recent_history` (чистый лист), последующие ходы — только диалог с Александром. Обобщает A и B на все ходы; эвристик по тексту нет.

## Ветка «по телефону»: разбор и рекомендация (решение — за владельцем, в план не входит)

По коду «выбор по телефону» в сценариях с Александром — **не выбор клиента**: при дилерах Call и Smartbot кнопку нажимает бот (рекурсивный вызов, `main.py:2515-2538`), а клавиатуру выбора клиент не видит (`main.py:1743-1745`). Человеческое нажатие «ПО ТЕЛЕФОНУ» возможно только там, где клавиатура показана — это режимы без Александра (Chat), либо web-механика. При этом Call-дилеры до Александра не доходят вовсе (ветка B), а Smartbot-дилеры доходят ровно через это авто-нажатие — то есть «ветка по телефону» и есть штатный вход Смартбота, а не особый случай.

**Рекомендация: ветку из-под Александра не выводить.** Авто-нажатие — маршрутизация сценария, а не волеизъявление клиента; после отсечки по границе передачи модель этих строк не увидит, и «вы говорили, что хотите по телефону» станет невозможным. Закрывать ветку без Александра означало бы отключить основной вход Smartbot-режима. Если когда-то появится реальный человеческий выбор «по телефону» перед передачей — это отдельное продуктовое решение; данные для него (`type: "button"` + режим дилера) в архиве сохраняются.

## Requirements

- R1. `recent_history` для n8n начинается с момента ПОСЛЕДНЕЙ передачи — на INIT-ходе (пустая) и на всех последующих ходах; при повторной передаче — от последней границы.
- R2. Строки с `type=="button"` не попадают в `recent_history` ни на каком ходе (нажатия — служебная механика, независимо от того, бот нажал или человек).
- R3. Архив `chat_history` не фильтруется и не переписывается; единственное добавление — маркер границы передачи; стенограммы NocoDB/Bitrix сохраняют полную картину, включая видимую строку передачи.
- R4. `msg_count`, флаги и стадийная эвристика `session_context` продолжают считаться по полной истории — стадии не меняются.
- R5. Срез ключуется на стабильный машинный признак маркера, не на отображаемый текст (урок formula-parity: идентичность не на строках, которые могут переименовать).
- R6. Усечение `chat_history` при сохранении контекста не ломает срез: маркер не найден при активном smartbot → текущее поведение (окно из 8) как fallback, без исключений.
- R7. Контракт производной задокументирован для n8n-стороны: где граница, кто её пишет, «пустая recent_history на INIT — норма».

## Key Technical Decisions

- КТР-1. Граница — маркер-строка в `chat_history`, не индекс и не таймстамп: `{"role": "system", "type": "ai_handoff", "text": "— Диалог передан ИИ-ассистенту —"}`. Индекс ломается усечением истории при сохранении; маркер переживает усечение, пока в окне, а его потеря деградирует безопасно (R6). Роль `system` уже прецедентна (`main.py:2349` «Клиент перешел по ссылке»), и такие строки автоматически не проходят фильтр ролей user/bot в `build_recent_history` — сам маркер в n8n не утекает.
- КТР-2. Срез ключуется на `type == "ai_handoff"` (машинный токен), отображаемый текст свободен для правок (R5).
- КТР-3. Фильтр служебных строк — по `type == "button"` при сборке производной, без текстовых списков кнопок: признак уже пишется в универсальной точке записи (`main.py:2117`), переименование кнопок фильтр не ломает.
- КТР-4. Правки только в производной (`build_recent_history`) и в точке записи маркера (ветка A): `msg_count`/флаги/`last_bot_message`/нормализация/архив не затрагиваются — по решению владельца «архив — источник правды, производная — для n8n».
- КТР-5. Маркер пишется в момент активации ветки A до отправки INIT-payload, в том же блоке кода, что `is_smartbot_active=True`, — но отдельным НЕМЕДЛЕННЫМ сохранением контекста: общей транзакции там нет (`is_smartbot_active` — отдельный UPDATE `users`, `main.py:2672-2674`), а штатный `save_context_to_db` после передачи условный — только при успешном ответе n8n (`main.py:2711`). Писатель и читатель метки — в одном месте пайплайна (урок token-idempotency).

## Implementation Units

### U1. Маркер границы передачи в момент AI handoff

- **Goal:** В `chat_history` появляется машинно-узнаваемая граница «дальше — диалог с Александром», переживающая рестарт.
- **Requirements:** R1, R3, R5, R6 (запись); R7 (документируемое место записи).
- **Dependencies:** нет.
- **Files:** `main.py` (ветка A активации, окрестность `main.py:2645-2672` — до `send_handoff_webhook`); константа типа маркера — в `payload_v2.py` (рядом с фильтрами истории, чтобы писатель и читатель делили один токен); `tests/test_payload.py` или новый `tests/test_handoff_history.py`.
- **Approach:** append маркер-строки В ОБА объекта — находка ревью, кросс-подтверждена: (1) в `ctx_snapshot['chat_history']` — deepcopy снапшота сделан на `main.py:2628` ДО точки записи, а INIT-payload (`send_handoff_webhook` → `extend_payload`, `main.py:1413`) читает именно снапшот; (2) в живой `USER_CONTEXT[...]['chat_history']` с собственным немедленным `save_context_to_db` — штатное сохранение после передачи условное (только при успешном ответе n8n, `main.py:2711`), маркер должен пережить и сбой INIT. Прецедент двойного проброса — `deal_id` (`main.py:2683-2684`). Повторная активация пишет новый маркер — срез всегда от последнего.
- **Patterns to follow:** system-строка `main.py:2349-2353`; сохранение контекста как в соседних точках ветки A.
- **Test scenarios:**
  - Активация ветки A → в `chat_history` появилась ровно одна строка `type=="ai_handoff"` до первого ответа ИИ.
  - Маркер присутствует В СНАПШОТЕ, уходящем в `send_handoff_webhook` (проверка именно передаваемого объекта, не живого контекста), И в персистентном контексте после отработки точки — включая случай, когда n8n на INIT ответил ошибкой.
  - Повторная передача в том же диалоге → два маркера, срез от последнего (сквозной сценарий с U2).
  - Маркер не попадает в `recent_history` (роль system) и не ломает стенограмму (`format_chat_history` рендерит system-строки: `main.py:149-170`).
- **Verification:** тесты зелёные; в дев-прогоне стенограмма диалога показывает строку передачи.

### U2. Срез и фильтр в build_recent_history

- **Goal:** Производная для n8n начинается от последнего маркера и не содержит строк-кнопок.
- **Requirements:** R1, R2, R4, R6.
- **Dependencies:** U1 (токен маркера).
- **Files:** `payload_v2.py` (`build_recent_history`); `tests/test_payload.py` (существующие тесты recent_history) + сквозные сценарии в `tests/test_handoff_history.py`.
- **Approach:** до существующих фильтров — отрезать всё до последней строки `type=="ai_handoff"` включительно (нет маркера → без отсечки, текущее поведение); затем исключить `type=="button"`; далее существующая логика (роли, `__SYSTEM`, лимит 8). `build_session_context`/`msg_count` не трогать (R4).
- **Execution note:** тесты — по фактическому содержимому среза за несколько ходов (урок token-idempotency-verified-by-table-rows: не «прошли ветку», а «что именно в списке»), включая сценарий инцидента 3316.
- **Test scenarios:**
  - Сценарий инцидента: история воронки MAX (кнопка «ПО ТЕЛЕФОНУ» type=button, «Для получения расчета, подтвердите Ваши контакты», маркер) → INIT `recent_history == []`.
  - Ход 2: клиент ответил, Александр ответил → срез содержит только эти строки, ни одной воронковской.
  - Кнопка ПОСЛЕ маркера, не попадающая под `__SYSTEM`-префикс — например «НИЧЕГО НЕ НУЖНО» (`btn_stop_ai`, пишется как `{"role":"user","type":"button"}`) → исключена фильтром R2. Изолирующий тест: сегодня такая строка проходит в `recent_history`, без реализации фильтра тест обязан падать (находка ревью: `__SYSTEM_TIMEOUT_HANDOFF__` для этого не годится — он режется существующим префикс-фильтром и в реальном потоке лежит ДО маркера).
  - Сквозной timeout/intercept-путь Smartbot: [воронка, sys_msg таймера, user-строка `__SYSTEM_TIMEOUT_HANDOFF__`, «Переводим диалог на специалиста», маркер] → INIT `recent_history == []`.
  - Сквозной Manager-путь: «Принято! Ваш запрос отправлен специалисту ⚡» записана до маркера (`main.py:2529 → 2569`) → отрезана срезом.
  - Нет маркера в истории (легаси-диалог, усечение) → поведение идентично текущему (окно 8), без исключений.
  - Два маркера → срез от последнего.
  - `msg_count` и `current_stage` не изменились от появления маркера и среза (регресс-стражи на существующих тестах стадий).
- **Verification:** тесты зелёные; ручная проверка на дев-стенде в ДВУХ каналах: MAX (первый ответ Александра содержит расчёт и выбор «салон/кабинет», телефона не просит) и web в режиме Manager (единственный сегодня корректный путь — регресс качества первого ответа после пустого INIT не должен уйти незамеченным).

### U3. Контракт производной в документации n8n

- **Goal:** Двусторонний контракт: n8n-сторона знает, что `recent_history` начинается с передачи, пустая на INIT — норма, кнопки исключены.
- **Requirements:** R7.
- **Dependencies:** U1, U2.
- **Files:** `docs/N8N_HANDOFF_CABINET.md` (новый короткий раздел или дополнение существующего о payload).
- **Approach:** зафиксировать: границу пишет бот в момент handoff (где именно), из среза исключены `type=button`, полная история живёт в архиве и доступна для разборов; связать с правилом рерайта из раздела 5 документа `docs/N8N_HANDOFF_CABINET.md` (контракт маркера ссылки; `last_bot_message` после первого успешного ответа ИИ — реплика Александра). Отдельно упомянуть intercept-путь: реальный текст возражения клиента в историю не попадает вовсе (подмена на `__SYSTEM_TIMEOUT_HANDOFF__` до точки записи, `main.py:2065 → 2117`) — на этом пути Александр стартует без реплики-триггера, и это существующее поведение, не следствие отсечки.
- **Test scenarios:** none — документация; контракт покрыт тестами U2.
- **Verification:** описание достаточно, чтобы n8n-сторона не ждала воронку в истории.

## Риски

- Маркер в стенограмме увидят менеджеры — задуман как читаемая строка; если формулировка не понравится, правится без кода среза (КТР-2).
- Легаси-диалоги, переданные до выката, маркера не имеют → остаются на текущем поведении до конца сессии (fallback R6) — осознанно, добора не делаем.
- Пустая `recent_history` на INIT — проверить, что n8n-воркфлоу не падает на пустом массиве (сегодня первый ход диалога без истории уже существует у новых клиентов — риск низкий, пункт приёмки).
- Смежный факт вне скоупа: `__SYSTEM_TIMEOUT_HANDOFF__` пишется в историю как user-строка (`main.py:2116-2117`) и виден в стенограммах — существующее поведение, не трогаем.
- Сбой INIT (одна попытка, без ретраев — `main.py:1416-1428`): ответа Александра в истории нет, и ремайндер через 30 минут рерайтит `last_bot_message` = финал воронки с висящим вопросом — существующее поведение, планом не создаётся и не чинится; зафиксировано, чтобы «нетронутость» ремайндеров не читалась как гарантия.

Если да — после отсечки он станет недоступен n8n на всех ходах, и потребуется владельческое решение о переносе такого текста в структурированное поле payload. ## Scope Boundaries

### Deferred to Follow-Up Work

- Отметка «нажатие сделано ботом, не человеком» в самих строках истории (`pressed_by: bot`) — полезно для разборов, но требует правки точки записи; сейчас различение возможно только по логам.
- Просьба владельца при будущем появлении реального человеческого выбора «по телефону» перед передачей — отдельное продуктовое решение (данные для него в архиве есть).

### Вне задачи

- Судьба ветки «по телефону» — только рекомендация выше, реализация не закладывается (решение владельца).
- Изменения n8n-воркфлоу, промптов, Dialogflow-воронки, режимов Manager/Call.
- Фильтрация или переписывание архива `chat_history`.
