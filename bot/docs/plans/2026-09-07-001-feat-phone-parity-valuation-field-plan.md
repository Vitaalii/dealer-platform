# feat: Паритет извлечения телефона + поле суммы оценки трейд-ина

## Summary

Блок 1: извлечение телефона на ИИ-пути переводится с узкого регэкспа PHONE_RE на
схему «кандидаты по цифрам → решает normalize_phone» — критерий паритета Р1.
Прототип прогнан на живом коде: 0 пропусков, 0 ложных на обязательном наборе;
старый PHONE_RE при этом сам даёт ложное срабатывание на диапазоне цен.
Блок 2: сумма оценки в ai_payload НЕ приходит (контракт finalize без такого
ключа), но бот уже владеет ею механически — ctx['n8n_cache']['ti_valuation']
(подтверждено сохранённым исполнением: 1820000 в логах сессии инцидента).
Правка контракта n8n НЕ требуется; значение защёлкивается персистентным слотом
и пишется в UF_CRM_1788758195 (тип string — замер портала) на колбэке и мосту.

## Установленные факты (маркировка: [прогон]/[live]/[код])

- [прогон] Механизм-кандидат ловит все 8 форм номера включая слэши/точки/склейку
  с текстом; НЕ ловит ни один из 14 нетелефонных входов (госномер+пробег, цены,
  VIN, год, диапазоны, дата). Старый PHONE_RE ловит диапазон «850000-2010000»
  как телефон — новый механизм чище старого и на негативах.
- [код] Контракт finalize (AI Agent v3.0.json, промпт ai_payload; список ключей
  идентичен v2.0): tradein_plate/make/model/year/mileage — ключа суммы НЕТ.
- [live] Архив NocoDB сессии инцидента: ti_valuation=1820000 присутствует в
  теле, которое бот сам отправлял в n8n (кэш/carryover) — сумма у бота есть.
- [live] UF_CRM_1788758195: USER_TYPE_ID=string, не множественное.
- [код+live] Кабинет УЖЕ пишет ti_valuation в ДРУГОЕ поле UF_CRM_1785857524
  (cabinet_service.py:1553, запись из снапшота при сабмите анкеты, строки
  1930-1944, 2022). В сделке 51365 оба поля пусты.
- [код] cabinet_uf_map.json ключа оценки не содержит → фильтр R34
  filter_cabinet_owned_fields новое поле не отбракует.

## Key Technical Decisions

- **KTD-1 (механизм, п.1.1):** не новый регэксп, а «кандидаты → валидатор»:
  кандидат = максимальная подстрока из цифр и разделителей `+ \s - ( ) . / ,`
  (границы — буквы/прочее); кандидат принимается, если is_valid_phone истинен
  (т.е. digit-strip даёт ровно 10-11 цифр по правилам РФ). Порядок: кандидаты
  первыми (извлекается чистая подстрока), fallback — весь текст целиком
  (буквальный паритет с путём C, «как прислано»). Обоснование: единственный
  способ выполнить критерий Р1 без перечня разделителей — отдать решение
  эталону; регэксп-вариант воспроизводил бы перечень.
- **KTD-2 (пересмотрен Д3 → KTD-7):** посимвольные окна внутри склеек не
  ищутся (ловят диапазоны цен), но это правило уточнено групповыми окнами ниже.
- **KTD-7 (Д3, граница паритета — окна по цифро-группам):** внутри кандидата
  окна перебираются по ЦЕЛЫМ цифро-группам (группа цифр неделима, окно —
  непрерывный набор групп); каждое окно решает is_valid_phone. Это закрывает
  класс «число и номер подряд» («148000 89805552817», «26000 8 980 555 28 17» —
  все ловятся, [прогон Д3]) без ложных на диапазонах/ценах/картах/СНИЛС.
  Замер обоих механизмов: потерь настоящих номеров нет; единственный вход
  «старый ловил, новый нет» — «850000-2010000», где старый извлекал обрезок
  диапазона цен «850000-2010» (ложное срабатывание, снято сознательно).
  Попутно закрыт дефект старого: на «148000 89805552817» PHONE_RE извлекал
  ОБРЕЗАННЫЙ номер « 8980734596» (10 цифр без последней) — в базу ушёл бы
  битый номер; новый извлекает полный. Граница паритета: номер, слитый с
  другой цифрой БЕЗ разделителя (одна группа длиннее 11 цифр,
  «14800089807345967»), не ловится — старый на таком классе тоже давал только
  обрезки-мусор.
- **KTD-3 (источник суммы, п.2.1-2.2):** сумма берётся из собственного
  ctx['n8n_cache']['ti_valuation'] — механический продукт TOOL AUTO.RU
  EVALUATION, который бот уже читает (payload_v2.register_evaluation:91,
  build_evaluation_carryover:314). Надёжнее ai_payload по построению: не
  зависит от генерации модели. Правка контракта n8n не нужна. Парсинг текста
  отчёта запрещён постановкой.
- **KTD-4 (персистентность суммы):** значение защёлкивается слотом
  ctx['evaluation_value'] в register_evaluation — по образцу существующей
  защёлки evaluation_received/evaluation_plate (payload_v2.py:79-106), потому
  что n8n_cache пересобирается (U6 TTL/стадии) и значение в нём не вечно.
- **KTD-5 (формат записи):** голое число строкой ('1820000') — тип поля string,
  консистентно с контрактной конвенцией «только цифры» (credit_initial,
  tradein_mileage).
- **KTD-6 (пути B/C не трогаем, п.1.4):** таймер-перехват (main.py:2150-2185)
  и стадия воронки (main.py:2597-2603) работают и остаются как есть; путь C
  семантически уже равен fallback-шагу нового извлекателя, путь B чуть строже
  (буквы<5 на весь текст) — унификация кода возможна позже отдельной задачей,
  в этой правке риск не оправдан. Их поведение пиняется характеризационными
  тестами до правки пути A.

## Риски и действия при срабатывании

- **Р-1. Ложное извлечение (центральный, п.1.2).** Замер: 0 ложных на наборе,
  включая реплику инцидента; механизм строже старого (диапазон цен). Остаточный
  класс: клиент диктует ЧУЖОЙ валидный номер (номер из объявления и т.п.) —
  неотличим никаким извлекателем и сегодня проходит в путях B/C; последствия
  ограничены существующими стражами: PHONE_WRITE_GUARD не даёт перетереть
  OTP-подтверждённый bound_phone (database.py:435-459). Если риск сработает
  (жалоба на чужой номер в карточке): откат — revert коммита U2 (путь A
  вернётся на пропуск, B/C не затронуты); лог извлечённого значения (U2) даёт
  разбор по конкретной сессии.
- **Р-2. Флаг для n8n станет чаще True** — Александр увидит телефон там, где
  раньше «не видел» (слэш-формы). Это выравнивание с реальностью; статусы
  visit/call модель и так ставила по факту номера в диалоге (отчёт 51365 прямо
  говорил «предоставил номер»). Действие: уведомление второй стороне (раздел
  ниже), правка контракта не требуется.
- **Р-3. Значение оценки протухло/снято** (новый госномер снял защёлку до
  колбэка) → слот пуст, поле не пишется — деградация до сегодняшнего поведения,
  не ошибка.
- **Р-4. Двойная запись поля с кабинетом** — исключена: кабинет пишет другое
  поле (1785857524), пересечения с R34-фильтром нет [код].

## Второму агенту (n8n) — уведомление, задача-минимум

Правка контракта НЕ требуется (KTD-3). Уведомить о семантическом изменении:
`session_context.flags.has_valid_phone_in_msg` начнёт возвращать True для
номеров с нестандартными разделителями (слэши, точки, склейка с текстом),
которые раньше давали False. Критерий нового флага: в сообщении есть цифровая
последовательность, валидная как телефон РФ по правилам бота (10-11 цифр,
7/8/9). Stage Classifier v3.0, если он опирается на флаг, начнёт видеть
телефонный сигнал раньше — поведение желаемое, но пусть вторая сторона
подтвердит отсутствие завязок на старую (узкую) семантику.
