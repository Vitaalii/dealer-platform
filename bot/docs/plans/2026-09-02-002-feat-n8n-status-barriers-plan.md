# feat: Статусы n8n — логирование подстановки, working, два телефонных барьера

## Резюме

Четыре работы по `handle_n8n_callback` (main.py): Р1 — наблюдаемость подстановки нераспознанного статуса; Р2 — легализация статуса `working`; Р3 — подстановка только при валидном телефоне, иначе «ОЖИДАНИЕ»; Р4 — visit/call без валидного телефона не уходят на «Обогащение», а в «ОЖИДАНИЕ» без карточки дилеру. Критерий валидности везде — `database.is_valid_phone` (database.py:451). При уходе в «ОЖИДАНИЕ» уведомление в группу дилера не отправляется (решение владельца: стадия ручной обработки саппорта).

Это код передачи заявок дилеру: главный принцип реализации — **барьеры меняют только стадию и факт алерта, никогда не блокируют запись данных** (смарт-поля, тип, стенограмма, архив пишутся как раньше). Ложное срабатывание барьера — заявка в «ОЖИДАНИИ» у саппорта (восстановимо), а не потерянное обращение.

---

## Ключевые технические решения

### КТР-1. Чистая функция нормализации статуса

Логика «сырой статус → итоговый статус + признак подстановки» (сегодня main.py:1112-1121) выделяется в чистую функцию (естественное место — crm_mapping.py, рядом с картой стадий и реестром дедупа). Вход: сырой статус, `smart_data`, признак валидного телефона. Выход: итоговый статус, флаг подстановки, исходное значение. Это делает Р1-Р3 юнит-тестируемыми без конструирования aiohttp-запросов и убирает дублирование белого списка.

### КТР-2. Телефон читается один раз в начале обработчика

Р3 и Р4 требуют `User.phone` до подстановки и до отправки в Битрикс. Сегодня телефон читается только в фоновой задаче (main.py:1208-1213). Добавляется одно раннее чтение из БД; результат используется тремя потребителями: подстановкой (Р3), выбором стадии (Р4), гейтом алерта.

### КТР-3. Барьер = переопределение стадии, не отбраковка данных

При срабатывании Р3/Р4: `STAGE_ID` принудительно `C9:UC_HW8Q2H` («ОЖИДАНИЕ»), алерт подавляется; всё остальное — смарт-поля, «Тип обращения», обновление контакта (телефона всё равно нет), стенограмма, архив NocoDB, реестр дедупа — работает без изменений. Открытый вопрос В2 может это скорректировать.

### КТР-4. Реестр дедупа не трогаем

Реестр хранит пару «сделка+статус» (crm_mapping.py:38-48). Барьеры меняют стадию, не статус → ретраи Save-to-CRM (5×3с) дедупятся как раньше. При Р3 без подстановки регистрируется сырой статус — одинаковые ретраи дают одинаковую пару. Расхождение с мостом (мост регистрирует сырой, колбэк — подменённый) для бестелефонных исчезает само (подстановки нет), для телефонных остаётся как сегодня — не хуже.

## Юниты

### U1. Р1 — логирование подстановки + выделение нормализации

**Цель:** факт подстановки и исходное значение фиксируются в логе; частота явления становится измеримой.
**Файлы:** main.py (handle_n8n_callback), crm_mapping.py (новая функция), tests/test_n8n_status_gate.py (новый).
**Подход:** выделить нормализацию (КТР-1) с сохранением текущего поведения бит-в-бит; при подстановке — `log_session(..., "WARNING")` с исходным значением (repr, обрезка длинного мусора), deal_id и итогом. Строка «Status (Fixed)» (main.py:1123) остаётся.
**Оценка:** S-M. **Независим:** да, можно начинать сразу.
**Тест-сценарии:** подстановка `None`/пустой строки/опечатки/другого регистра/пробельного значения → WARNING с исходным значением; валидный статус → WARNING нет; эвристика next_step («визит в салон» → visit) сохранена; лог содержит исходное значение дословно.

### U2. Р2 — статус working в белом списке

**Цель:** законный статус карты стадий перестаёт подменяться.
**Зависимости:** U1 (правка в выделенной функции).
**Файлы:** crm_mapping.py или main.py — там, где после U1 живёт белый список (сегодня main.py:1116); tests/test_n8n_status_gate.py.
**Подход:** `working` в белый список; стадия — по карте: `C9:UC_HW8Q2H` (crm_mapping.py:12). Алерт не уходит (условие visit/call, main.py:1230), «Тип обращения» не пишется (main.py:1163-1166) — само по текущим условиям, зафиксировать тестами.
**Оценка:** S.
**Тест-сценарии:** `working` → без подстановки, стадия «ОЖИДАНИЕ», алерта нет, тип не пишется; WARNING не логируется.

### U3. Р3 — узкий барьер: подстановка только при телефоне

**Цель:** бестелефонная заявка с нераспознанным статусом не превращается в «call»; уходит в «ОЖИДАНИЕ».
**Зависимости:** U1 (функция нормализации), КТР-2 (раннее чтение телефона).
**Файлы:** main.py, crm_mapping.py, tests/test_n8n_status_gate.py.
**Подход:** при невалидном телефоне подстановка не выполняется, статус остаётся сырым, стадия форсится в `C9:UC_HW8Q2H`. Реестр дедупа регистрирует сырую пару (КТР-4). Эвристика next_step при отсутствии телефона тоже не применяется — иначе «визит» без телефона обошёл бы барьер (согласуется с Р4).
**Оценка:** S-M.
**Тест-сценарии:** нераспознанный статус + нет телефона → стадия «ОЖИДАНИЕ», подстановки нет, алерта нет, WARNING с исходным значением есть; нераспознанный + телефон валиден → подстановка как раньше; ретрай той же пары → дубль, повторной обработки нет.

### U4. Р4 — широкий барьер: visit/call без телефона → «ОЖИДАНИЕ»

**Цель:** честный или подменённый visit/call по заявке без валидного телефона не уходит на «Обогащение» и не порождает карточку дилеру.
**Зависимости:** КТР-2; логически независим от U1-U3 (проверка итогового статуса), но сливается с ними в одном обработчике — исполнять после U3.
**Файлы:** main.py (выбор стадии перед `background_crm_update`, гейт алерта main.py:1230), tests/test_n8n_status_gate.py.
**Подход:** после нормализации: если итоговый статус visit/call и `not is_valid_phone(user.phone)` → стадия `C9:UC_HW8Q2H` вместо `resolve_stage`, алерт подавлен. Данные пишутся полностью (КТР-3). Лог-строка о срабатывании барьера (INFO достаточно — стадия видна в CRM).
**Оценка:** M.
**Тест-сценарии:** call без телефона → стадия «ОЖИДАНИЕ», алерта нет, смарт-поля и тип в `crm.deal.update` присутствуют; visit без телефона → то же; call с телефоном → «Обогащение» + алерт (пин текущего поведения); in_progress/refuse/ban — барьер не вмешивается (пины: «Нет номера»/LOSE/APOLOGY); подменённый call (мусор + телефон валиден, Р3 пропустил) → алерт и «Обогащение» как сегодня.

## Риски

- **Код передачи заявок: ошибка = потерянное обращение.** Митигация в конструкции: барьер никогда не отбрасывает данные и не прерывает обработку — худший исход ложного срабатывания: заявка в «ОЖИДАНИИ» у саппорта со всеми данными и стенограммой. Обратное (пропуск барьера) = сегодняшнее поведение.
- **Ранний запрос телефона в обработчике** — +1 чтение БД на колбэк; объём колбэков единицы в день (архив: 13 ИИ-финализаций visit/call за всю историю) — несущественно.
- **Скрытая связка с эвристикой next_step:** без её гейтирования (U3) бестелефонный «визит» обходил бы барьер — закрыто тестом.
- **Мост остаётся дырой при «нет» по В1** — фиксируется как принятый риск решением владельца.
- **Изменение семантики «ОЖИДАНИЯ»:** стадия начинает использоваться как приёмник барьеров; сейчас на ней 0 сделок (замер), конфликтов с текущим использованием нет — но саппорт должен знать о новом источнике (задача владельцу, вне кода).
