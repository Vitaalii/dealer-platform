# fix: allowlist /catalog — таблицы всех дилеров из живой схемы Dealers

> **ПРАВИЛО ДАННЫХ (решение владельца 2026-09-25, действует всегда):**
> колонка Dealers с именем `* table id` = ПУБЛИЧНАЯ таблица — её содержимое
> доступно в интернете через /catalog. Не заводить такие колонки для
> чувствительных таблиц. Жёсткого denylist в коде НЕТ (решение владельца);
> появление новой таблицы в этих колонках даёт техалерт `catalog-allow-new`.

**ИТОГ (2026-09-25):** реализовано по плану с правками владельца (В1 колонка
«Color table id» — ед. число, ловится шаблоном; В2 быстрый путь не делали;
В3 КТД-1 подтверждён; denylist заменён техалертом `catalog-allow-new` с
дедупом). Код-коммит 6055e05: `_dealer_table_columns` (шаблон `*tableid`),
`catalog_allowed_tables` (статика + union по дилерам, мёртвый color_table_id
удалён), `dealers_refresh_worker` (600 с, ошибка кэш не трогает),
`_report_new_catalog_tables`. Тесты: SQLite 931 passed / 4 skipped,
PostgreSQL 16.8 935 passed; живой список — 23 таблицы из колонок + статика.
Выкат multy-v3.3.3 успешен: оснащение и цвета открываются на лендингах
Geely, Belgee, Haval; архив/Bots — 404; регрессий нет. Learning:
docs/solutions/security-issues/allowlist-built-from-one-consumer.md.

## Summary

Гейт `/catalog` (введён 1109cfb, прод multy-v3.3.2) собирает allowlist только
из полей Dealers, которые читает код бота, — таблица оснащения Geely живёт в
поле «Features table id», которое код не читает вовсе, поэтому лендинг Geely
получает 404. План: собирать allowlist из ВСЕХ id-колонок живой схемы Dealers
(по шаблону имени колонки — будущие поля попадают без правок кода), добавить
периодическую перечитку справочника дилеров, покрыть тестами «второй дилер с
другим набором таблиц». Плюс быстрый путь без пересборки образа (данные
NocoDB + рестарт) и выкат multy-v3.3.3.

---

## 1. Причина (разбор, файл:строка)

**Одной фразой:** allowlist строится только из тех полей Dealers, которые
код читает для собственных нужд (Sourse/Stock/Program/Rates + статичная
тройка сайта), а оснащение Geely лежит в новом поле «Features table id»,
которое не читается вовсе — Haval выжил лишь потому, что его таблица
оснащения захардкожена в статичной тройке.

Механика точно:

- `main.py` `catalog_allowed_tables()` (main.py:119–133): статичная тройка
  `CATALOG_STATIC_ALLOWED_TABLES` (mywf0f16ptn25gk, mm8wldgk5vn9gwh,
  muruk10ipof33m5) + env `NOCODB_TABLE_ID` + по каждому дилеру из
  `CACHED_DEALERS`: `color_table_id`, `table_id` и `db_config`
  (catalog/stock/program/rates/credit_table_id).
- `CACHED_DEALERS` наполняет `load_data_from_nocodb()` (main.py:1859–1949):
  из NocoDB читаются ТОЛЬКО «Sourse base id», «Sourse table id»,
  «Stock_Base_ID», «Stock_Table_ID», «Program_Table_ID», «Rates_Table_ID»
  (main.py:1884–1889). «Features table id» не читается. Ключ
  `color_table_id` в `CACHED_DEALERS` не пишется никогда — в
  `catalog_allowed_tables()` это мёртвая ветка.
- Подмножества дилеров НЕТ: в кэш попадают все строки с непустым
  Dealer_Code (main.py:1872–1874) — Geely-строки в кэше, их каталог
  m2flt4d2r5d9cpa в allowlist ЕСТЬ. 404 ловит именно оснащение
  mvsw7fa9at92jnv («Features table id» — код его не знает).
- Момент сборки: `load_data_from_nocodb()` вызывается один раз на старте
  (main.py:4522); `dealers_watchdog` (main.py:4511,
  `cabinet_service.ensure_dealers_loaded`) только ретраит загрузку ПУСТОГО
  справочника — периодической перечитки нет. `catalog_allowed_tables()`
  пересчитывается на каждый запрос — но по устаревшему кэшу.
- Почему инцидент не поймали проверки 2.2: лендинг Haval (и дев-лендинг)
  используют статичную тройку; Geely-лендинг — свои таблицы. Тест «второй
  дилер с другим набором» отсутствовал.

## 2. Требования

- R1. Все таблицы из ВСЕХ id-полей ВСЕХ строк Dealers разрешены в `/catalog`
  и `/catalog-colors` целиком, без фильтрации полей (решение владельца:
  персональных данных там нет).
- R2. Whitelist 7 полей сохраняется ТОЛЬКО для самой таблицы Dealers
  (muruk10ipof33m5): Dealer_Code, Dealer_location, Dealer_name,
  Dealer_status, Dealer_address, Dealer_workinghours, Dealer_phone.
- R3. Пустые поля — норма (у большинства дилеров заполнен только «Sourse
  table id»); код не падает и не шумит.
- R4. Новое id-поле в Dealers (как «Features table id») попадает в allowlist
  БЕЗ правки кода.
- R5. Новый дилер попадает в allowlist без перезапуска приложения.
- R6. Недоступность NocoDB не отключает сайт: статичная тройка всегда
  разрешена; последний успешный список дилерских таблиц живёт, пока жив
  процесс (кэш не очищается при неудачной перечитке).
- R7. Всё прочее — 404 без подробностей (архив mnivr6uyf5ckzru, Bots
  ma0nf1e807qb9e0, Prompt_Blocks mipsjod64tdgpee и т.д.).

## 3. Key Technical Decisions

- **КТД-1. Сборка по шаблону имени колонки, а не по фиксированному списку
  полей.** При загрузке строки дилера собирать значения всех колонок, чьё
  нормализованное имя (lower, без пробелов/подчёркиваний) оканчивается на
  `tableid` — сейчас это «Sourse table id», «Features table id»,
  «Stock_Table_ID», «Program_Table_ID», «Rates_Table_ID»; будущие
  («Colors table id» и т.п.) подхватятся автоматически (R4). Живая схема
  Dealers проверена 2026-09-25: других id-колонок нет; «Sourse base id» и
  «Stock_Base_ID» — идентификаторы БАЗ (p…), а не таблиц: `/catalog/{id}`
  принимает только table id — в allowlist им делать нечего (колонка,
  обрезанная на скриншоте на «b», — Business_Connection_ID, к таблицам
  отношения не имеет).
- **КТД-2. Результат хранится в `CACHED_DEALERS[d]['catalog_tables']`**
  (set), `catalog_allowed_tables()` суммирует его со статикой; `db_config`
  и прочие ключи, которые читает бот и n8n, НЕ меняются — их семантика
  трогается нулевым образом.
- **КТД-3. Периодическая перечитка дилеров** (R5): лёгкий цикл раз в 600 с —
  повторный вызов `load_data_from_nocodb()` (он уже идемпотентен: clear +
  refill только при HTTP 200; при ошибке кэш остаётся прежним → R6).
  Разместить рядом с registry_worker по его образцу; отдельный воркер, не
  расширение `ensure_dealers_loaded` (у того другая семантика — аварийный
  ретрай пустого справочника).
- **КТД-4. Статичная тройка остаётся** (R6): mywf0f16ptn25gk и
  mm8wldgk5vn9gwh — таблицы «общего» сайта (Haval/дев используют именно их;
  сайт не должен зависеть от успешной загрузки дилеров), muruk10ipof33m5 —
  Dealers с whitelist полей (R2). env NOCODB_TABLE_ID остаётся. Мёртвый ключ
  `color_table_id` из `catalog_allowed_tables()` удаляется.
- **КТД-5. `/catalog-colors` использует тот же `catalog_allowed_tables()`**
  (уже так, main.py:3472) — отдельной логики не появляется; цветовые таблицы
  попадут в allowlist, когда их id окажутся в id-колонке Dealers (см.
  Открытые вопросы — сейчас их там НЕТ ни у одного бренда).

## 4. Implementation Units

### U1. Сборка allowlist из всех id-колонок Dealers + перечитка

- **Goal:** R1, R3–R6.
- **Files:** `main.py` (load_data_from_nocodb, catalog_allowed_tables,
  новый воркер в start_background_tasks), тесты — U2.
- **Approach:** в цикле по строкам Dealers собрать
  `catalog_tables = {v for k, v in row.items() if _norm_field_name(k).endswith('tableid') and v и строковое}`;
  положить в запись кэша; `catalog_allowed_tables()`: статика + env +
  `union` по дилерам (убрать `color_table_id`/`db_config`-перечисление —
  db_config теперь покрыт `catalog_tables` супермножеством). Новый воркер
  `dealers_refresh_worker(interval=600)` по образцу
  `bot_registry.registry_worker` (main.py:4514): try/except, лог WARNING при
  неудаче, кэш не трогается при ошибке.
- **Patterns to follow:** `_norm_field_name` (main.py:117), registry_worker.
- **Test scenarios:** в U2.
- **Verification:** дев: `/catalog/<таблица из «Features table id»>` → 200
  после добавления значения в NocoDB и ≤10 мин ожидания (без рестарта).

### U2. Тесты (tests/test_catalog_allowlist.py)

- **Goal:** случай инцидента больше не проходит незамеченным.
- **Test scenarios:**
  1. **Инцидент:** два дилера с РАЗНЫМИ наборами таблиц (второй — только
     «Sourse table id» + «Features table id» со своими id) → обе таблицы
     второго дилера отдают 200.
  2. Пустые/отсутствующие поля у дилера → не падает, лишнего не разрешает.
  3. Новое поле с именем «Colors table id» (нет в коде) → его значение в
     allowlist (проверка шаблона имён, R4).
  4. Поле «Sourse base id»/«Stock_Base_ID» → НЕ попадает в allowlist.
  5. Неизвестная таблица → 404; архив/Bots/Prompt_Blocks → 404 (R7).
  6. `/catalog/muruk10ipof33m5` → ровно 7 полей (R2).

  8. Перечитка: обновлённый ответ NocoDB (новый дилер) → таблицы в

## 5. Быстрый путь (п.7 владельца) — ДО выката, без пересборки

Кода в образе не хватает ровно в одном месте: он не читает «Features table
id». Но allowlist v3.3.2 собирается из «Sourse table id» / «Stock_Table_ID» /
«Program_Table_ID» / «Rates_Table_ID» ЛЮБОЙ строки Dealers → можно скормить
недостающие таблицы через СЛУЖЕБНУЮ строку Dealers:

1. В Dealers завести (или использовать неработающего дилера 98, если строка
   существует — владелец говорил, что 98 не используется) строку с
   Dealer_Code, не пересекающимся с живыми кодами; заполнить:
   «Sourse table id» = `mvsw7fa9at92jnv` (оснащение Geely),
   «Stock_Table_ID» = `mxp17sn00b0tfvt` (оснащение Belgee),
   «Program_Table_ID»/«Rates_Table_ID» — про запас (цвета, если известны).
   Остальные поля пустые.
2. Рестарт прод-приложения (кэш дилеров читается на старте; пересборки нет).
3. Проверка: поп-ап оснащения Geely работает; `/catalog/mvsw7fa9at92jnv` → 200.
4. После выката v3.3.3 строку удалить (при перечитке 600 с исчезнет сама).

Издержки: строка светится в `/catalog/muruk10ipof33m5` (7 полей; всё, кроме
кода, пустое) и висит в CACHED_DEALERS (диплинков с её кодом нет — не
маршрутизируется). Приемлемо на день-два.

## 6. Что ещё могло сломаться и пока не проявилось

- **Цвета — у ВСЕХ брендов.** Цветовые таблицы (пример: mwyu1qq92hm96o9
  «HAVAL Color», её запрашивал старый демо-лендинг) НЕ лежат ни в одном
  поле Dealers и не в статике → `/catalog-colors` и `/catalog` для них
  сейчас 404 на проде. Не проявилось, вероятно, потому что поп-ап цветов
  открывается по клику. Решение: владелец добавляет колонку «Colors table
  id» в Dealers и заполняет — КТД-1 подхватит автоматически (и быстрый путь
  п.5 может включить их раньше).
- **Сток/программы/ставки сайтов** Geely/Belgee — уже в allowlist (читаемые
  поля), не сломаны. Chery/Tenet/TANK/GAC/Changan/Solaris — только каталоги
  («Sourse table id») — в allowlist, ок.
- **Запросы самого бота от allowlist НЕ зависят**: бот ходит в NocoDB
  напрямую с сервера (get_cars_from_nocodb_dynamic main.py:2008 — каталог и
  сток; load_prompts_from_nocodb; реестр ботов; архив; Dealers) — гейт
  `/catalog` стоит только на публичном HTTP-эндпоинте для сайта/Кабинета.
  n8n читает NocoDB тоже напрямую (свой токен). Ничего ботового гейт не
  ломает.
- **Страница Кабинета** делает голый fetch `/catalog` (комментарий
  main.py:3438–3443) — использует таблицы дилера из читаемых полей + Dealers
  → уже работает; после правки станет устойчивее.

## 7. Риски и ручные проверки владельца (п.9)

- Шаблон `*tableid` заберёт ЛЮБУЮ будущую id-колонку — в т.ч. если однажды
  заведут колонку с чувствительной таблицей. Митигция: правило владельцу —
  «колонка `* table id` в Dealers = публичная таблица»; зафиксировано здесь.
- Перечитка каждые 600 с — новая фоновая нагрузка на NocoDB (1 запрос) —
  ничтожна на фоне стока.
- Владельцу проверить руками после выката: оба лендинга (каталог, оснащение,
  контакты, ЦВЕТА после добавления колонки), кабинет любого дилера
  открывается, `/bot-links` жив, боты Geely/Haval отвечают (рестарт).
