## Шаг 2 — риски (все проверены измерением)

### Риск А — валидаторы телефона: расхождения реальны, опасный сценарий невозможен

Живой прогон обоих валидаторов (2026-09-01):

| Вход | бот `is_valid_phone` | кабинет `normalize_phone` |
|---|---|---|
| `+79001234567`, `89001234567`, `9001234567`, `8 (900) 123-45-67`, `79991234567` | True | `+7…` |
| `84951234567`, `74951234567` (11-значные городские) | **True** | **None** |
| `4951234567` (10 цифр не с 9) | False | None |
| `+375291234567`, `+380501234567` | False | None |
| `phone79001234567` (≥5 букв) | **False** | **`+79001234567`** |
| `тел 8-900-123-45-67 срочно позвонить` (>20 симв.) | **False** | **`+79001234567`** |

Кабинетный валидатор — `cabinet_service.py:680-690` (строго мобильные
+79xx); бот-валидатор шире по городским 11-значным и уже по «грязным»
строкам.

**Опасный сценарий «кабинет подтвердил — бот не видит» невозможен по коду:**
кабинет пишет через `_post_verify_hook` канонический `+79XXXXXXXXX`
(`cabinet_service.py:2604-2608`), а `is_valid_phone('+79…') == True`
(измерено) — кабинетные номера — строгое подмножество ботовских. Формат
хранения совместим в обе стороны: `save_user_phone` пишет как прислано,
`is_valid_phone` парсит любые разделители.

**Новая несогласованность после переноса** (не существовавшая в проде — там
нет кабинета): выдача ссылки кабинета гейтится `has_phone=bool(...)`
(`main.py:1270`), а воронка бота перейдёт на `is_valid_phone`. Клиент с
мусорным номером в БД: бот считает «телефона нет» (запросит номер / уведёт
в кабинетный путь), выдача ссылки считает «есть» → ссылки не будет.
Решение — вопрос B2 (юнит U4).

### Риск Б — thumbnails: снят

Чистка уже в нашей ветке (`main.py:1640-1646`). Галерея кабинета
спроектирована под её результат: карточка отдаёт только абсолютные URL,
комментарий «thumbnails уже вырезаны» — `cabinet_service.py:3071-3073`.
Переносить нечего, ломаться нечему.

### Риск В — GZIP/CORS/ngrok: снят

GZIP-ветка с ручным `Access-Control-Allow-Origin: *` уже живёт у нас
(`main.py:2958-2969`). Кабинет каталог-роутом НЕ пользуется (grep `catalog`
по `widget-custom/cabinet-app/app.js` — ноль; карточка авто идёт через
`/cabinet/api/car`). CORS-middleware ставит заголовки присваиванием
(`response.headers[...] = ...`, `main.py:2942-2949`) — для сжатого ответа
ACAO перезаписывается, дублей нет; `ngrok-skip-browser-warning` разрешён в
`Allow-Headers` обеих веток middleware (`main.py:2934, 2948`). Обе ветки
(сжатая/несжатая) работоспособны сегодня.

### Риск Г — save_user_phone против OTP: подтверждён вызов, отказ невозможен, возврат не проверяется

Кабинетный путь ВЫЗЫВАЕТ `database.save_user_phone`
(`cabinet_service.py:2606-2608`, `_post_verify_hook`) и возврат НЕ
проверяет. После переноса отказ по невалидности для кабинета невозможен
(канонический `+79xx` проходит новый предикат — измерено), молчаливая потеря
подтверждения не возникает. Порядок проверок при переносе: валидность —
ПЕРВОЙ, до `get_or_create_user` и стража (как в 3.1.2); кабинетный страж
остаётся второй причиной False. Существующие тесты стража
(`tests/test_bot_integration.py:265-284`) используют валидные номера — не
задеваются. Защитный лог `False` в `_post_verify_hook` — включён в U2.

**Синергия:** чат-путь сейчас игнорирует возврат `save_user_phone`
(`main.py:2513`) — бот отвечает «Принято!…» даже когда кабинетный страж
отклонил запись чужого номера. Ханок 3.1.2 (`if await save_user_phone(...)`)
закрывает и эту слепоту.

## Шаг 3 — конфликты с кабинетной работой (факты)

- **Пересечений по строкам нет.** Все 15 непересённых ханков ложатся на
  регионы, дословно совпадающие с 3.1.0 (проверено grep-ами контекстов).
  WEB-ханки живут в тех же функциях, что свежий override «Типа обращения»
  (`create_deal_with_contact`/контакт-апдейт), но на других строках.
- **WEB vs UF_CRM_666D69C9EEE1B — не конфликтуют:** WEB — поле КОНТАКТА
  (`crm.contact.add/update`, `main.py:300, 336`), UF — поле СДЕЛКИ
  (`crm.deal.*`); разные сущности и вызовы.
- **«Принято! Ваш запрос отправлен специалисту»** порождается нашей веткой в
  Manager-режиме чата (`main.py:2585`, с суффиксом «📨» — substring-матч
  виджета устойчив). Кабинетный сценарий этот текст не шлёт; двухфазная
  логика виджета кабинетом не задевается. Триггер уже есть в нашем
  widget.js (:307).
- **widget.js и app.js не пересекаются:** разные файлы и страницы; app.js
  widget.js не референсит. Единственная связь — widget.js рендерит ссылку
  КАБИНЕТА в пузыре (наша фича) — перенос обязан её сохранить (пины
  `tests/test_cabinet_link_render.py:172-200`).
- **Перенос НЕ затрагивает `cabinet-app/app.js`** → инкремент `?v=` для
  app.js НЕ нужен. Нужен cache-bust для **widget.js** на Tilda (правило — в
  шапке самого widget.js, строка 5-6).

## Key Technical Decisions

1. **`database.py` целиком НЕ переносится ни при каких обстоятельствах.**
   Переносятся ровно две функции (`normalize_phone`, `is_valid_phone`) и
   guard-строка валидности в `save_user_phone`. Наш `init_db` (механизм
   `63646c8`: по-DDL-транзакции, инспектор, `SCHEMA_COLUMN_DROPS`,
   кабинетные таблицы) **остаётся как есть — старый однотранзакционный
   init_db из 3.1.2 не возвращается.**
2. **Имена не конфликтуют осознанно:** `database.normalize_phone` (бот,
   широкий) и `cabinet_service.normalize_phone` (кабинет, строго +79xx) —
   разные модули и разные контракты; не объединять (кабинетная строгость —
   требование шлюза ProstoSMS, err 617).
3. **Валидность — первая проверка `save_user_phone`**, до
   `get_or_create_user` и `PHONE_WRITE_GUARD` (порядок 3.1.2 + наш страж
   второй причиной False).
4. **widget.js: канон — 3.1.2**, наша фича ссылки в пузыре сохраняется
   поверх; `person-icon.png` заменяется на `robot.png` (вопрос B1
   подтвердить).
5. Thumbnails/GZIP/CORS не трогаем — уже в ветке, идентичный код.
