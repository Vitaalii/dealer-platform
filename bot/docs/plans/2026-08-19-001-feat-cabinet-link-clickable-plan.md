# feat: Кликабельная ссылка на кабинет вместо голого URL

## Summary

Ссылка на личный кабинет перестаёт появляться в чате голым URL. Александр по промпту выводит маркер `[CABINET_LINK]`, бот в единой точке отправки (`send_smartbot_reply`) подставляет гиперссылку на фразу. Первая очередь — веб-виджет (основной канал общения) вместе с точкой подстановки; MAX и Telegram работают без правок клиентов и получают гиперссылки в момент переключения промптов. Тихая страховка перехватывает сырой URL, если модель напечатала его мимо маркера. Кнопки в этой версии не используются.

## Problem Frame

Сейчас адрес кабинета попадает в сообщение изнутри текста, сгенерированного моделью. На тестировании это дало три проблемы: ссылка не кликабельна (в виджете — вообще, там URL рендерится как простой текст), знак препинания вплотную к адресу ломает переход, а длинный токен в URL выглядит подозрительно — клиент такое не жмёт. Есть и четвёртая, скрытая проблема: модель воспроизводит токен руками на каждом ходе, и любое искажение в одном символе — мёртвая ссылка, которую бот не замечает. Основной трафик диалогов идёт через чат на сайте, поэтому виджет чинится первым.

Вывод по форме подачи: гиперссылка на фразу достижима во всех трёх каналах, причём в MAX и Telegram — вообще без правок клиентов: они догоняют сами в момент переключения промптов. Кнопка потребовала бы правки маппинга в Telegram, новой механики в виджете и решения «к какой части [SPLIT] цеплять». Это подтверждает выбранное направление: гиперссылка — основная форма, кнопки в v1 не нужны нигде.

## Точка перехвата

Точка одна на все каналы: `send_smartbot_reply` (`main.py:509`). Через неё проходят все четыре пути доставки ответа ИИ — обычный ход (`main.py:2184`), LONG RETRY (`main.py:2231`), ветка A первого AI handoff (`main.py:2661`) и ремайндер (`main.py:3102`). Каналы скрыты за `BaseBotClient.send_message`, различие каналов внутри функции уже используется (`get_client`, `supports_contact_button`).

Отдельно от отправки живёт запись в историю: `bot_text` кладётся в `chat_history` до `send_smartbot_reply` и вычищает только `[SPLIT]` — четыре точки записи: обычный ход (`main.py:2177-2180`), LONG RETRY (`main.py:2226-2229`), ветка A (`main.py:2654-2657`), ремайндер (`main.py:3094-3099`). Историю тоже придётся трогать во всех четырёх (см. КТР-6).

## Сравнение подходов и рекомендация

**A. Перехват URL в готовом тексте.** Бот может узнать точный URL в любой момент (`prepare_cabinet_context` идемпотентен, ссылка стабильна — R19; здесь и далее R19 — сквозное требование кабинета из `docs/brainstorms/2026-07-29-client-cabinet-requirements.md`, та же нумерация живёт в комментариях кода; R-иды этого плана — отдельные). Поэтому «надёжно находить адрес в свободном тексте» не требуется: достаточно точного вхождения известной строки. Плюс: промпты можно не менять вовсе. Решающий минус: модель продолжает воспроизводить длинный токен руками. Исказила один символ — точное вхождение не совпало, перехват молчит, клиент получает мёртвый голый URL. Класс ошибок, ради которого всё затевается, остаётся.

**B. Маркер-заглушка.** Модель выводит `[CABINET_LINK]` вместо адреса; бот подставляет авторитетный URL из своих данных. Модель никогда не касается токена — искажение исключено по построению. Механизм проверен в проде: `[CONTACT_BUTTON]` работает ровно так (`main.py:624-627`), модель надёжно эмитит маркер. Риск «модель потеряла/исказила маркер» закрывается страховкой A и деградацией (см. ниже).

**Рекомендация (принята): B основной, A — тихая страховка.** Минимальный вариант «только A, без правки промптов» существует, но не лечит искажение токена моделью — оставлен как этап отката, не как целевое состояние.

## Контракт маркера (вход для переписывания BLK_*_CABINET_CHOSEN)

- Токен: `[CABINET_LINK]` — ставится ровно в том месте фразы, где должна стоять ссылка; сам адрес модель не печатает никогда; не больше одного маркера на сообщение.
- Бот заменяет маркер на `<a href="{cabinet_url}">{анкор}</a>`. Анкор по умолчанию — фиксированная фраза на стороне бота: «личный кабинет» (форма совпадает в им. и вин. падежах — «откройте личный кабинет», «ваш личный кабинет»).
- Расширенная форма `[CABINET_LINK:текст анкора]` — парсер понимает её с первого дня; инструкция модели остаётся на простой форме. Текст анкора перед подстановкой в HTML **экранируется** (`<`, `>`, `&`, кавычки) — анкор приходит из текста модели и не должен ломать разметку ни в HTML-каналах, ни в восстановительном регэкспе виджета.
- **Границы парсинга битых маркеров:** анкор — непустая строка до первой `]`, без вложенных скобок. Всё, что не распарсилось (`[CABINET_LINK:]`, оборванный `[CABINET_LINK` на конце текста, `]` внутри анкора), вычищается из текста с предупреждением в лог, а ссылка доставляется голым URL — принцип «ссылку не терять» проверяется негативными тестами U1.
- Правило «если `cabinet_url` пустая — кабинет не упоминай» остаётся в промпте и совпадает с реальностью payload: при не настроенном кабинете бот кладёт `null` (а при аварии блока ключа нет вовсе).
- Действующая инструкция блоков «после адреса не ставить точку» при переходе на маркер уходит — пунктуация больше не соседствует с URL (фиксируется в чек-листе U3).
- Контракт фиксируется в `docs/N8N_HANDOFF_CABINET.md` целиком — синтаксис обеих форм, позиция, поведение при отсутствии URL, правило для рерайт-сценариев (урок `docs/solutions/logic-errors/formula-parity-without-scope-parity.md`: контракт бот↔n8n документировать двусторонне, не только строку токена).

## Key Technical Decisions

- КТР-1. Маркер — основной механизм, перехват URL — страховка: модель не касается токена (см. сравнение выше); страховка и основной путь разделены явно — страховка тихая, срабатывает только на точное вхождение известного URL, выполняется тем же проходом по исходному тексту (до вставки `<a>`), чтобы не найти URL внутри только что созданного `href`.
- КТР-2. Гиперссылка на фразу — основная форма во всех каналах; кнопок в v1 нет: кнопка выглядит элементом системы, а не репликой живого сотрудника, цепляется к сообщению целиком, требует правки Telegram-маппинга и недокументирована при пересылке на обеих платформах.
- КТР-3. Простой маркер с анкором на стороне бота (расширенная форма — в парсере, но не в промпте): минимальный контракт надёжнее; деградация без URL даёт связный текст (фраза-анкор без ссылки), а не дыру в предложении.
- КТР-4. Подстановка — в `send_smartbot_reply`, по возможностям канала. Первая очередь включает и виджет (U2), поэтому целевое состояние — `<a>` во всех трёх каналах сразу; ветка «web → голый URL» сохраняется в коде как переключатель деградации (старый закэшированный `widget.js`, откат) — не как этап выката.
- КТР-5. Источник URL — запрос у `cabinet_service` в момент подстановки, БЕЗ стэша в контексте (решение по итогам ревью). Выдача идемпотентна (R19), поэтому повторный запрос возвращает тот же URL; живой токен не попадает в `context_json` — модель хранения «в БД только отпечаток» (`_hash_token`, `_derive_token_plain` из nonce) не нарушается, а проблемы жизненного цикла стэша (deepcopy-снапшот ветки A `main.py:2578`, перезапись контекста на пути ремайндера, рестарт) исчезают классом. Выбор между повторным `prepare_cabinet_context` и лёгким read-only геттером активного токена — деталь реализации U1; требование плана — URL не персистируется и запрашивается на каждую отправку с маркером/вхождением.
- КТР-6. В `chat_history` (и, следовательно, в `recent_history` для n8n) маркер заменяется на голый URL: n8n должен видеть фактическое состояние диалога, а не служебный токен. Следствие (находка ревью): URL попадает и в `last_bot_message`, который уходит в AI-рерайт первого ремайндера — правило «адрес не перепечатывать, ставить маркер» должно покрывать и рерайт-сценарий (чек-лист U3). Существующая утечка `[CONTACT_BUTTON]` в историю — не в скоупе, вынесена в отложенное.
- КТР-7. Стиль ссылки в виджете (решение по итогам ревью): наследовать цвет текста пузыря плюс подчёркивание — синяя браузерная ссылка в чёрно-белой палитре виджета чужеродна; область клика достаточна для пальца.

## Поведение при [SPLIT]

Вопрос «к какому из сообщений цепляется кнопка» снимается выбором гиперссылки: подстановка выполняется до разрезания по `[SPLIT]`, ссылка остаётся инлайн в той части, где модель поставила маркер. Прецедентное правило «кнопку — к последней части» (`main.py:655-656`) относится только к `[CONTACT_BUTTON]` и не затрагивается. Маркер вплотную к `[SPLIT]` — негативный сценарий U1. Если когда-нибудь понадобится кнопка-ссылка — цеплять её к части с маркером, а не к последней; зафиксировано в отложенном.

## Деградация и отказы

- Маркер есть, URL не получен: запрос у `cabinet_service` в момент подстановки — это и есть основной механизм (КТР-5), отдельного «повторного» пути не нужно. Если запрос не дал URL — маркер заменяется на анкорную фразу без `<a>`, текст остаётся связным; лог различает причины: «кабинет не настроен у дилера» против «сбой cabinet_service» (по исключению) — оператор должен отличать нарушение промпта от лежащего сервиса.
- Канал не готов к HTML-ссылке (старый кэш `widget.js`, откат U2): ветка деградации web → голый URL, отделённый пробелами от пунктуации.
- Страховка: точное вхождение известного `cabinet_url` в тексте без маркера → обёртывается в ту же форму `<a>` тем же проходом; не совпало (модель исказила адрес) — текст не трогаем. Немое искажение токена невозможно обнаружить на стороне бота — это остаточный риск варианта «модель печатает URL», который маркер и убирает.
- Битый маркер (см. контракт): вычистить, доставить голым URL, предупреждение в лог. Общий принцип из уроков репо (`docs/solutions/integration-issues/token-idempotency-verified-by-table-rows.md`): при любом сбое парсинга ссылку не терять.
- Экранирование URL в `href`: токен — base64url (`[A-Za-z0-9_-]`, 43 символа, `cabinet_service.py:857-863`), URL — `https://host/cabinet#t=<токен>` (`cabinet_service.py:934`); символов `&`, `?`, кавычек в ссылке не бывает по построению. HTML-экранирование значения `href` всё равно выполняется как дешёвая страховка от будущих изменений формата.

## Пересылка и копирование

- Пересылка внутри канала: гиперссылка — это text-entity, она путешествует вместе с текстом. Для Telegram это общеизвестное поведение клиентов, но Bot API его не документирует; для MAX не документировано вовсе (проверен весь справочник dev.max.ru — ни слова о forward/copy). Обе проверки — эмпирически на стенде, пункты в приёмке. Кнопки при пересылке в Telegram в общем случае теряются (косвенно подтверждено `LoginUrl.forward_text`) — ещё один довод в пользу гиперссылки.
- Копирование как текст: href теряется во всех трёх каналах — в буфер уходит анкорная фраза без адреса. Запасной путь не строим: ссылка идемпотентна (повторный запрос у Александра возвращает тот же URL — R19), это штатный способ восстановить её. Вариант «показывать домен в анкоре» отвергнут — ломает фразу и возвращает подозрительный вид.
- Виджет: пересылки нет, только копирование; поведение то же.

## Requirements

- R1. Ссылка на кабинет доставляется кликабельной гиперссылкой на фразу во всех трёх каналах; веб-виджет — в первой очереди работ наравне с точкой подстановки.
- R2. Модель не печатает адрес: промпт выводит маркер, бот подставляет URL, запрошенный у `cabinet_service` в момент подстановки; искажение токена моделью исключено по построению; живой токен не персистируется в `context_json`.
- R3. Тихая страховка: сырой `cabinet_url`, напечатанный моделью мимо маркера, преобразуется в ту же форму по точному вхождению одним проходом; страховка не мешает маркерному пути и не срабатывает на изменённые адреса.
- R4. Деградация без потери ссылки: битый маркер → голый URL; URL не получен → связный текст без ссылки-пустышки плюс лог с различением причин; ссылка не теряется молча ни на одном пути.
- R5. `[SPLIT]`-совместимость: ссылка остаётся в той части сообщения, где стоял маркер, включая маркер вплотную к `[SPLIT]`.
- R6. В `chat_history`/`recent_history` уходит нормализованный текст (URL вместо маркера) во всех четырёх точках записи; правило «адрес не перепечатывать» распространяется и на рерайт-сценарий ремайндера (чек-лист U3).
- R7. Виджет рендерит `<a>` безопасно (только https, экранирование href и анкора, `target=_blank`, `rel=noopener`) во всех путях отрисовки, включая восстановление истории; стиль — цвет текста пузыря с подчёркиванием, тач-таргет достаточен для пальца.
- R8. Поведение при пересылке проверено живьём в MAX и Telegram, рендер `<a>` в виджете — живьём в браузере на стенде, до переключения промптов.

## Implementation Units

Первая очередь — U1 + U2 вместе (виджет — основной канал); U3 — документация к ним; MAX и Telegram правок не требуют.

### U1. Маркерная подстановка и страховка в исходящем тексте

- **Goal:** Бот превращает `[CABINET_LINK]` (и сырой URL — страховкой) в гиперссылку в единой точке отправки, запрашивая URL у `cabinet_service` в момент подстановки, с деградацией и нормализацией истории.
- **Requirements:** R1-R6.
- **Dependencies:** нет.
- **Files:** новый `cabinet_link_render.py` (чистые функции: парсинг обеих форм маркера с границами, экранирование анкора и href, подстановка, страховочный перехват одним проходом, выбор формы по каналу); `main.py` — вызов в `send_smartbot_reply` до логики `[SPLIT]` (после аварийного моста и подписи), получение URL через `cabinet_service`, нормализация во всех четырёх точках записи `chat_history` (обычный ход `main.py:2177-2180`, LONG RETRY `main.py:2226-2229`, callback `main.py:2654-2657`, ремайндер `main.py:3094-3099`); `tests/test_cabinet_link_render.py`.
- **Approach:** чистая функция вида `render_cabinet_link(text, url, channel) -> (text, applied)` — тестируется без сети; wiring в `main.py` минимальный, по образцу `payload_v2` (логика в модуле, в `main.py` только вызовы). URL запрашивается у `cabinet_service` непосредственно перед подстановкой и не сохраняется в контекст (КТР-5); запрос выполняется только когда в тексте есть маркер или вхождение URL возможно.
- **Patterns to follow:** маркерный перехват `[CONTACT_BUTTON]` (`main.py:622-627`); вынос логики в модуль с wiring-only в `main.py` (`payload_v2.py`).
- **Test scenarios:**
  - Маркер в середине фразы → `<a href>` с анкором, текст вокруг не изменён.
  - Маркер при недоступном URL → анкорная фраза без ссылки; лог различает «не настроен» и «сбой сервиса».
  - Расширенная форма `[CABINET_LINK:свой анкор]` → анкор из маркера, HTML-экранированный (анкор с `<`, `>`, `&`, кавычками не ломает разметку).
  - Битые маркеры: `[CABINET_LINK:]`, оборванный `[CABINET_LINK` в конце текста, `]` внутри анкора → маркер вычищен, ссылка доставлена голым URL, предупреждение в лог.
  - Маркер во второй части `[SPLIT]`-сообщения и маркер вплотную к `[SPLIT]` → ссылка в правильной части, разрезание не ломается.
  - Сырой URL с точкой/скобкой вплотную (без маркера) → обёрнут по точному вхождению, пунктуация вне `<a>`.
  - URL, искажённый на один символ → текст не изменён (страховка молчит).
  - Два вхождения одного URL в тексте → оба обёрнуты одинаково.
  - Маркер и сырой URL в одном тексте → подстановка и страховка одним проходом, URL внутри вставленного `href` повторно не оборачивается.
  - Канал web в ветке деградации → маркер заменён на голый URL с пробелами-разделителями.
  - Нормализация истории: в `chat_history` записан URL, маркера нет — на всех четырёх путях записи (для ремайндера — контекст, загруженный из БД).
- **Verification:** тесты зелёные; живая отправка на стенде в MAX и Telegram — фраза кликабельна, переход в кабинет работает, пересылка сообщения сохраняет ссылку (эмпирическая проверка R8).

### U2. Виджет: рендер гиперссылки (первая очередь, вместе с U1)

- **Goal:** Веб-виджет рендерит `<a href>` из текста бота кликабельной ссылкой в стиле виджета.
- **Requirements:** R1, R7, R8.
- **Dependencies:** U1 (форма `<a>` определена там); выкатывается одной очередью с U1.
- **Files:** `widget-custom/widget.js` — `renderText` (восстановление строго ограниченной формы `<a href="https://...">текст</a>`), стиль ссылки в CSS виджета, аудит всех путей отрисовки бот-сообщения: `appendBotBubble`, восстановление истории из localStorage (`widget.js:586`); версионирование подключения `widget.js` (cache-bust) — старый закэшированный виджет показал бы экранированный литерал `<a href=...>` вместо ссылки.
- **Approach:** прецедент нужного класса уже живёт в самой `renderText`: регулярка находит в тексте адреса картинок и подменяет их на `<img>` (`widget.js:434-438`) — «найти адрес, заменить элементом» в проде работает; восстановление тегов по белому списку — второй прецедент там же (`<b>`/`<i>`). Порядок операций в функции: экранировать всё → восстановить `<b>`/`<i>` → **восстановить `<a>` (новый шаг)** → картинки → переносы строк. Вставка до шага картинок; конфликт с `<img>` исключён и по порядку, и по формату (cabinet-URL не оканчивается на расширение изображения, регэксп картинок его не матчит). Только https в `href`, экранирование кавычек, `target="_blank"`, `rel="noopener"`; общую линкификацию произвольных URL не вводить. Стиль: цвет текста пузыря, подчёркивание, тач-таргет для пальца (КТР-7).
- **Execution note:** приёмка только в живом браузере на дев-стенде — в этом репо фронтенд-правки дважды проходили по grep-тестам и ломались визуально (`docs/solutions/frontend-issues/css-width-verify-in-browser.md`, `mockup-media-query-transfer.md`); отдельно проверить, что ссылка переживает перерисовку контейнера (`docs/solutions/frontend-issues/error-render-overwrites-sibling-elements.md`).
- **Test scenarios:**
  - Текст с `<a href="https://дилер/cabinet#t=...">личный кабинет</a>` → кликабельная ссылка в стиле пузыря (цвет текста, подчёркивание), открывается в новой вкладке.
  - `href` с `javascript:` или `http://` → рендерится как текст, не как ссылка.
  - `href` или анкор с кавычкой/угловой скобкой → не ломает разметку пузыря.
  - Сообщение со ссылкой И картинкой-URL в одном тексте → оба элемента отрисованы, `<img>`-регэксп не тронул содержимое `<a>`.
  - Сообщение со ссылкой после перезагрузки страницы (восстановление истории из localStorage) → ссылка кликабельна.
  - Обычные сообщения с `<b>`/`<i>` и картинками → рендер не изменился.
  - Старый кэш виджета (до cache-bust) → проверить фактическое поведение на стенде; после cache-bust клиенты получают новый `widget.js`.
- **Verification:** браузерная проверка всех сценариев на дев-стенде; предусловие стенда — у стендового дилера https `Website_URL`, иначе ссылка не выдаётся вовсе (`_cabinet_base_url` возвращает `None` для http — `cabinet_service.py:878-905`), и проверять будет нечего.

### U3. Контракт в документации и чек-лист для промптов

- **Goal:** Двусторонний контракт маркера зафиксирован; переписывание трёх блоков `BLK_*_CABINET_CHOSEN` обеспечено точной инструкцией.
- **Requirements:** R2, R6.
- **Dependencies:** U1 (финальный синтаксис).
- **Files:** `docs/N8N_HANDOFF_CABINET.md` — раздел о маркере: синтаксис обеих форм и границы парсинга, позиция в фразе, «адрес не печатать никогда», поведение при пустом `cabinet_url`, что бот кладёт в историю; чек-лист требований к блокам: маркер внутри фразы, нет URL в few-shot-примерах, устаревшая инструкция «после адреса не ставить точку» удалена, правило «адрес из истории не перепечатывать, ставить маркер» распространено на рерайт-сценарий ремайндера (`last_bot_message` несёт голый URL после нормализации КТР-6).
- **Test scenarios:** none — документация; корректность контракта покрыта тестами U1.
- **Verification:** блоки переписываются по чек-листу без вопросов к коду (сами блоки — вне плана, их переписывает владелец промптов; по договорённости передаются заранее, до выката кода).

## Порядок и оценка объёма

| Шаг | Объём | Комментарий |
|---|---|---|
| Блоки `BLK_*_CABINET_CHOSEN` под маркер | вне плана | владелец промптов, заранее, по чек-листу U3 |
| U1 бот-сторона + тесты | S (~полдня) | один новый модуль, точечный wiring в `main.py` |
| U2 виджет + браузерная приёмка | S (~2-4 часа + приёмка) | оценка снижена: механизм-образец (URL→элемент) уже в `renderText`, добавляется один шаг в готовую последовательность + стиль + cache-bust |
| U3 документация контракта | S (часы) | вместе с U1 |
| Живое переключение промптов | — | после приёмки U1+U2 на стенде (браузер + живые отправки MAX/TG) |

Правило отката: пока маркерные промпты активны, откатывать код ниже U1 нельзя — клиенты увидят литерал `[CABINET_LINK]`; при необходимости отката сначала вернуть до-маркерные промпты, потом код.

Затрагивается: `main.py` (точечно), новый `cabinet_link_render.py`, `widget-custom/widget.js`, `docs/N8N_HANDOFF_CABINET.md`, тесты. Клиенты `max_client.py` и `telegram_client.py` не меняются. БД, n8n-воркфлоу не затрагиваются; в `cabinet_service.py` возможен только новый read-only геттер URL (деталь реализации U1).

## Риски

- Модель игнорирует или искажает маркер → страховка по точному URL + счётчик подстановок в логах для наблюдения первых дней.
- `<a>` в MAX заявлен документацией, но живьём нами не проверялся → живая приёмка на стенде до переключения промптов; если рендер плохой — канал переводится на голый URL одним условием выбора формы в U1.
- XSS-поверхность в виджете при разрешении `<a>` → строгая форма (https-only, экранирование href и анкора), без общей линкификации; сценарии в U2.
- Запрос URL на каждую отправку с маркером → один лишний вызов `cabinet_service` на такую отправку; частота мала (маркер появляется в единичных сообщениях диалога), выигрыш — отсутствие живого токена в `context_json` и всего класса проблем жизненного цикла стэша.
- Пересылка в MAX не документирована → эмпирическая проверка в приёмке; негативный результат не блокирует фичу (ссылка в тексте хуже не станет, чем сегодняшний голый URL).
