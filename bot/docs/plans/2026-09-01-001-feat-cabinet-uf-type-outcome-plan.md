# feat: «Тип обращения» различает анкету и авторизацию в кабинетной конверсии

Ветка `feat/cabinet-calculator`. Кабинетная конверсия должна писать в
`UF_CRM_666D69C9EEE1B` значение «Анкета {сценарий}» / «Авторизация {сценарий}»
вместо нынешнего единого значения из `_map_type`. Ограничения владельца:
только кабинетная конверсия (некабинетные сделки — прежнее поведение),
чат-путь (`main.py:641,643,1130,1132`) не трогаем.

---

## Установленные факты (разведка 2026-09-01, все — по коду на f3f0862+5)

### Признак исхода: триггер vs submitted_at

**Не эквивалентны; надёжен только submitted_at в момент конверсии.**

1. Триггер до точки формирования поля не доезжает вовсе: `_complete_handoff`
   получает `trigger` только для логов/событий, `_run_conversion(user_id)`
   вызывается без него (`cabinet_service.py:2336-2338`).
2. Recovery ломает триггер-признак: рестарт/падение между захватом и
   конверсией → повтор идёт `_complete_handoff(user_id, "recovery")`
   (`cabinet_service.py:469`) — конверсия сабмит-захвата приходит с чужим
   триггером. `submitted_at`, прочитанный из БД в момент конверсии, даёт
   верный ответ и здесь.
3. Пограничный случай владельца — «отправил, но передача сработала по
   таймауту» — по коду устроен так: если таймаут-захват выиграл раньше
   сабмита, вторая конверсия не выполняется никогда — сабмит попадает в
   ветку `late_submit` и делает только `push_form_to_bitrix`
   (`attempt_handoff`, `cabinet_service.py:2176-2183`; докстринг 2135-2139).
   Поле остаётся со значением «Авторизация …», хотя анкета в итоге
   отправлена и её UF дописаны в сделку. Оба признака здесь дают одинаковый
   результат — это свойство единственной конверсии, не различие признаков.
   Дозапись поля в этой ветке — открытый вопрос O1.
4. Гонка в пользу submitted_at: захват таймаутом, сабмит успевает до чтения
   снапшота → поле получит «Анкета …», и это соответствует действительности
   (UF анкеты придут late_submit-пушем).

**submitted_at до точки формирования не доезжает.** `build_conversion_snapshot`
читает только `User.context_json` и `CabinetProfile`
(`cabinet_service.py:2421-2440`); `CabinetForm` не читает. Цепочка до поля:
`_complete_handoff` (`cabinet_service.py:2320`) → `_run_conversion`
(инъекция, `cabinet_service.py:2336-2338`) → `_cabinet_run_conversion`
(`main.py:3760-3771`) → `build_conversion_snapshot`
(`cabinet_service.py:2414-2440`) → `final_sync_wrapper` (`main.py:384`) →
`update_deal_data` (`main.py:367-385`) / `create_deal_with_contact`
(`main.py:323-360`), где `cls.F_TYPE: cls._map_type(...)` (`main.py:354, 371`).
Протаскивание — один слой: чтение формы в `build_conversion_snapshot`;
дальше снапшот и так передаётся как `context` без изменения сигнатур.

**Отличить кабинетную конверсию по данным снапшота сейчас нельзя.**
`final_sync_wrapper` обслуживает и чистый чат (`main.py:2702, 2783` —
ctx-снапшоты чата), и кабинет (`main.py:3771`); маркера кабинета в снапшоте
нет. Гарантия отделения при добавлении: ключ кладётся в снапшот в памяти
только внутри `build_conversion_snapshot`, которую вызывает только кабинетная
обёртка `_cabinet_run_conversion`; чатовые контексты строятся из
`USER_CONTEXT`/ctx и ключа не содержат; `build_conversion_snapshot` ничего
не персистит — загрязнение `context_json` исключено.

### Сценарии

**«Только кредит/трейд-ин/комбо» — опровергнуто.** Чат пишет в
`ctx['scenario_type']`: credit/tradein/combo/stock/consult
(`scenario_map`, `main.py:2469-2474`), refusal (`main.py:2536, 2539`),
other_model (`main.py:2542`). Выдача ссылки кабинета сценарием не гейтится —
только `has_phone`/активный токен (`prepare_cabinet_context`,
`cabinet_service.py:3148-3172`); вызывающие передают
`user_context.get('scenario_type', 'unknown')` (`main.py:1289, 1403`).
Тройка сценариев — правда только для UI анкеты (`KNOWN_SCENARIOS`,
`widget-custom/cabinet-app/app.js:2395`; неизвестный сценарий рендерит полный
набор блоков). В кабинетную конверсию могут прийти stock, consult, refusal,
other_model, 'unknown' и пустое значение → открытый вопрос O2.

**Источники сценария могут расходиться.** Снапшот: `context_json`
приоритетен, профиль дополняет только пробелы (`cabinet_service.py:2436-2437`).
`profile.scenario_type` обновляется при каждом prepare с непустым
отличающимся значением (`cabinet_service.py:2652-2653`). Расхождение реально:
клиент после выдачи ссылки переквалифицировался в чате → `context_json`
обновлён, профиль — только при следующем prepare → открытый вопрос O3.

### Совместимость

- Сравнений значения поля со старыми подписями в коде и тестах **нет**:
  все вхождения меток — сам словарь `_map_type` (`main.py:491-497`), записи
  чат-пути (`main.py:641,643,1130,1132`) и независимая переменная
  `next_contact` для алерта менеджеру (`main.py:1188` — поле не читает).
  В `tests/` упоминаний меток нет; тесты трогают конверсию только
  source-grep'ом другого содержания (`tests/test_cabinet_otp_flow.py:445`,
  `tests/test_cabinet_rebind.py:354`, `tests/test_cabinet_handoff.py:588-601`).
- Поле в Битриксе строковое (`USER_TYPE_ID=string`, измерено 2026-08-31) —
  новые подписи не требуют конфигурации списка.
- **Факт для владельца:** существующие сделки остаются со старыми
  значениями; миграция не предлагается.

### Чат-путь после кабинетной конверсии

**Перезапись возможна, код её не запрещает.** В `handle_n8n_callback` от
входа до записи поля упоминаний кабинета ноль (grep по `main.py:1062-1128`);
запись безусловна при `status` visit/call (`main.py:1129-1132`);
`filter_cabinet_owned_fields` режет только коды `cabinet_uf_map.json` и
только после `submitted_at` (`cabinet_service.py:3247-3268`) —
`UF_CRM_666D69C9EEE1B` в карте нет. «Александр закрывает чат» — поведение
промпта, кодом не обеспечено. Условия перезаписи: диалог продолжается после
кабинетной конверсии и ИИ завершает его статусом visit/call (штатный финал
`main.py:1130-1132` или аварийный мост `main.py:641-643`) → открытый
вопрос O4 (защита требует правки чат-пути, запрещённой ограничением 2).

## Key Technical Decisions

1. **Признак исхода — `submitted_at` формы в момент конверсии**, не триггер:
   триггер до точки формирования не доезжает и искажается recovery (факты
   выше). Форма читается по `(user_id, deal_id активного токена)` — тем же
   адресом, каким `push_form_to_bitrix` шлёт UF (`cabinet_service.py:2013`).
2. **Готовое значение в снапшоте, override с фолбэком в BitrixService**
   (направляющая схема, не спецификация): `build_conversion_snapshot`
   вычисляет подпись «Анкета/Авторизация {сценарий}» в `cabinet_service`
   (домен кабинета) и кладёт её отдельным ключом снапшота;
   `update_deal_data`/`create_deal_with_contact` используют её при наличии,
   иначе прежний `_map_type` — одна строка вида
   `context.get(<ключ>) or _map_type(...)` в каждой из двух точек.
   Гарантия для некабинетных сделок видна в этой же строке: ключа нет ни в
   одном чатовом контексте (см. факты), фолбэк оставляет поведение прежним.
   Отвергнутая альтернатива — ветвление внутри `_map_type` по маркеру:
   размывает границу «кабинетная логика в cabinet_service», требует тащить
   маркер туда же, выигрыша нет.
3. **Словарь подписей — в `cabinet_service`,** рядом с вычислением исхода:
   «Анкета кредит/трейд-ин/комбо», «Авторизация кредит/трейд-ин/комбо» —
   дословно из таблицы владельца. Поведение вне тройки — по решению O2.
4. **Чат-путь и `_map_type` не меняются** (ограничения владельца 1 и 2).

## Implementation Units

### U1. Исход и подпись в build_conversion_snapshot

**Goal:** снапшот кабинетной конверсии несёт готовое значение поля,
различающее «анкета отправлена» / «черновик» × сценарий.
**Dependencies:** решения O2 (сценарий вне тройки) и O3 (источник сценария);
без них можно начинать с дефолтами, помеченными в коде как решения владельца.
**Files:** `cabinet_service.py` (`build_conversion_snapshot`,
`cabinet_service.py:2414`; словарь подписей рядом),
`tests/test_cabinet_handoff.py`.
**Approach:** прочитать `CabinetForm.submitted_at` по `(user_id,
deal_id активного токена)` в той же функции (сессия уже открыта); вычислить
подпись по словарю KTD 3 и положить отдельным ключом снапшота. Ничего не
персистить. Сценарий — по решению O3, поведение вне тройки — по O2.
**Test scenarios** (паттерн —
`test_handoff_feeds_real_snapshot_into_conversion`,
`tests/test_cabinet_handoff.py:511-534`):
- анкета отправлена (submitted_at задан) + сценарий credit → в снапшоте
  «Анкета кредит»; tradein/combo — аналогично;
- черновик (submitted_at IS NULL) + credit → «Авторизация кредит»;
- формы нет вовсе → как черновик («Авторизация …»);
- сценарий вне тройки (stock) и пустой сценарий → поведение по O2;
- ключ не попадает в `context_json` (после билда перечитать User — без
  изменений).
**Verification:** тесты U1 зелёные; `build_conversion_snapshot` остальных
ключей не меняет (существующие тесты 477-534 не падают).

### U2. Потребление в BitrixService с фолбэком

**Goal:** кабинетное значение уходит в `UF_CRM_666D69C9EEE1B`; некабинетные
вызовы — прежний `_map_type`.
**Dependencies:** U1.
**Files:** `main.py` (`update_deal_data` `main.py:371`,
`create_deal_with_contact` `main.py:354`), `tests/test_cabinet_handoff.py`
или `tests/test_cabinet_wiring.py` (пин), поведенческий тест — модуль с
`import main` (образец: `tests/test_cabinet_form.py:24`).
**Approach:** KTD 2 — в обеих точках `cls.F_TYPE:` подставлять кабинетное
значение при его наличии в context, иначе `cls._map_type(...)`. None-фильтр
(`main.py:359, 382`) сохраняет текущую семантику «нет значения — ключ не
шлём».
**Test scenarios:**
- кабинетный контекст с готовым значением → `_request` получает его в
  `F_TYPE` (monkeypatch `BitrixService._request`, вызов `update_deal_data`);
- некабинетный контекст (ключа нет) с `scenario_type='credit'` → в `F_TYPE`
  прежнее «Расчет кредита» — тест неизменности некабинетных сделок;
- контекст без ключа и без валидного сценария → ключ `F_TYPE` не отправлен;
- source-grep пин строки override в обеих точках (create/update) — по
  конвенции `tests/test_payload.py:141-152`.
**Verification:** оба поведенческих теста зелёные; полный набор без падений.

### U3. Сквозной тест двух исходов

**Goal:** интеграционно закреплено: submit-путь даёт «Анкета …»,
таймаут-путь — «Авторизация …», recovery сабмит-захвата — «Анкета …».
**Dependencies:** U1, U2.
**Files:** `tests/test_cabinet_handoff.py`.
**Approach:** реальные `attempt_handoff`/`build_conversion_snapshot`,
застабленная конверсия, фиксирующая снапшот (паттерн
`tests/test_cabinet_handoff.py:511-534`); для recovery — захват без
`handoff_done` + `_recover_stuck_handoffs`.
**Test scenarios:**
- сабмит-триггер при отправленной анкете → значение «Анкета {сценарий}»;
- таймаут-триггер при черновике → «Авторизация {сценарий}»;
- recovery после сабмит-захвата (submitted_at задан) → «Анкета {сценарий}» —
  закрепляет выбор признака по submitted_at, не по триггеру.
**Verification:** три сценария зелёные.

### U4. Дозапись поля при поздней отправке (условный — по O1)

**Goal:** если владелец решит «поздняя отправка обновляет поле» — ветка
`late_submit` дописывает «Анкета {сценарий}» в сделку.
**Dependencies:** U1, U2; решение O1 = «да».
**Files:** `cabinet_service.py` (`attempt_handoff`, ветка
`cabinet_service.py:2176-2183`), `tests/test_cabinet_handoff.py`.
**Approach:** в ветке поздней отправки добавить `crm.deal.update` одного
поля тем же путём `_bitrix_call_or_enqueue` (паттерн
`_send_timeline_comment`, `cabinet_service.py:2110-2117`); значение — из
того же словаря U1.
**Test scenarios:** таймаут-передача → поздний сабмит → в вызовах Bitrix
есть обновление поля на «Анкета {сценарий}»; при O1 = «нет» юнит не
выполняется.
**Verification:** тест ветки зелёный; поведение `late_submit` в остальном
не изменено (существующие тесты ветки не падают).

## Scope Boundaries

- Не трогаем: `_map_type` и его словарь, записи чат-пути
  (`main.py:641,643,1130,1132`), аварийный мост, `filter_cabinet_owned_fields`.
- Существующие сделки со старыми значениями не мигрируются (факт для
  владельца, решение его же).
- Защита от перезаписи чат-путём — вне скоупа до решения O4 (требует правки
  чат-пути, запрещённой ограничением 2).

## Open Questions (владельцу)

- **O1. Поздняя отправка после таймаут-передачи.** Конверсия одна; сабмит
  после неё дописывает только UF анкеты (`cabinet_service.py:2176-2183`).
  Поле останется «Авторизация {сценарий}», хотя анкета отправлена.
  Варианты: (а) оставить как есть — поле фиксирует исход на момент передачи;
  (б) дозаписывать «Анкета {сценарий}» (юнит U4).
- **O2. Сценарий вне тройки** (stock/consult/refusal/other_model/'unknown'/
  пусто) в кабинетной конверсии — возможен по коду (факты). Варианты:
  (а) прежнее значение `_map_type` (stock → «Подбор авто в наличии», …);
  (б) не отправлять ключ вовсе (поле не трогается);
  (в) значение без сценария — «Анкета» / «Авторизация».
  Выбор не делаю.
- **O3. Источник сценария.** Снапшот берёт `context_json` (актуальное
  состояние чата), профиль — только пробелы; `profile.scenario_type`
  фиксируется при выдаче/обновлении ссылки. Они могут расходиться
  (переквалификация в чате после выдачи). Что авторитетно для подписи:
  (а) текущее поведение снапшота (context_json приоритетен);
  (б) `cabinet_profile.scenario_type` (сценарий, под который выдана ссылка).
- **O4. Защита от перезаписи чат-путём.** После кабинетной конверсии
  `handle_n8n_callback` со статусом visit/call перезапишет поле («Визит в
  салон»/«Звонок по телефону») — кода, запрещающего это, нет; закрытие чата
  обеспечивается только промптом. Нужна ли защита (например, гейт по факту
  кабинетной передачи, симметричный `filter_cabinet_owned_fields`)? Любой
  вариант нарушает ограничение «чат-путь не трогаем» — потому только вопрос.

## Оценка объёма

U1 ~1 ч, U2 ~1 ч, U3 ~45 мин, U4 ~30 мин (условный). Всё — один заход
`ce-work` после ответов на O1–O3 (O4 не блокирует: скоуп зафиксирован без
защиты).
