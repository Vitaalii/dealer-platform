# ARCHITECTURE.MD: UnifiedBot v3.1.0 (Multi-Channel Edition)

## 1. Высокоуровневая архитектура (High-Level Design)
Система представляет собой монолитное асинхронное приложение (Модульный Монолит) на базе `aiohttp`. Бот работает как автономный веб-сервер, который маршрутизирует данные между тремя каналами (MAX, Telegram, Web-виджет) и внешними сервисами (NocoDB, Dialogflow, Bitrix24, n8n). Режим "Живого чата" с перехватом сообщений менеджерами полностью исключен.

### Основные компоненты (Services)
* **MAX Webhook Server:** Ядро приложения. Слушает входящие POST-запросы на порту 8080 (эндпоинт `/max_webhook`). Оснащён фильтром устаревших событий: вебхуки, опоздавшие более чем на 60 секунд, отбрасываются без обработки.
* **MAX Bot Client:** Микро-клиент для отправки REST-запросов к платформе MAX (сообщения клиентам, алерты в группы дилеров, парсинг vCard, управление тайпинг-индикатором).
* **Telegram Bot Client (`telegram_client.py`):** Клиент для канала Telegram. Поддерживает inline-кнопки, ReplyKeyboard для сбора контакта, удаление кнопок через `editMessageReplyMarkup`. Не участвует в алертах дилерам — они всегда идут через MAX.
* **Web Bot Client (`web_client.py`):** Клиент для кастомного веб-виджета. Работает через асинхронные очереди (`asyncio.Queue`) на каждую сессию. Не поддерживает ремайндеры, нативную кнопку контакта и удаление клавиатуры. При финализации сессии отправляет событие `chat_close` в очередь.
* **Base Bot Client (`base_client.py`):** Абстрактный базовый класс (`ABC`) для всех каналов. Определяет интерфейс: `send_message`, `send_typing`, `send_alert_to_group`, `remove_inline_keyboard`. Флаги возможностей: `supports_contact_button()`, `supports_reminders()`, `supports_keyboard_removal()`.
* **Channel Router (`get_client`):** Функция-роутер `get_client(channel: str) -> BaseBotClient`. Возвращает нужный клиент по значению `channel` (`"max"`, `"telegram"`, `"web"`). Алерты дилерам и технические алерты всегда идут напрямую через `max_client`, минуя роутер.
* **CORS Middleware + Catalog Proxy:** Middleware добавляет CORS-заголовки ко всем ответам. Эндпоинты `/catalog/{dealer_code}` и `/catalog-colors` проксируют запросы к NocoDB — NocoDB-токен никогда не передаётся в браузер.
* **SSE Endpoint (`/chat_stream/{session_id}`):** Server-Sent Events для веб-виджета. Держит соединение открытым, пушит сообщения из `asyncio.Queue`. Keepalive-ping каждые 30 секунд. Виджет использует `fetch + ReadableStream` (не нативный `EventSource` — тот не поддерживает кастомные заголовки, необходимые для ngrok).
* **Static Widget Server:** Файлы `widget-custom/widget.js` и `widget-custom/avatar.jpg` раздаются напрямую из Python через `aiohttp.add_static`. URL виджета динамически задаётся через `window.UNIFIEDBOT_URL` на странице Tilda до загрузки скрипта.
* **Dialogflow ES (NLU):** Первичная квалификация лида, извлечение параметров (платеж, госномер) и определение интента.
* **NocoDB Cache:** Внешняя база данных (Master). Хранит настройки дилеров (`Max_Group_ID`, тип связи) и каталог/сток авто. Данные кэшируются в памяти на 10-15 минут.
* **NocoDB Data Warehouse (Archive):** Параллельная аналитическая таблица (`Dialogues_Archive`). Накапливает 100% стенограмм диалогов — включая диалоги, завершённые на уровне Dialogflow без участия ИИ-агента.
* **Dynamic Prompt Engine:** Модуль скачивания и склейки промптов из NocoDB. Позволяет управлять поведением ИИ-ассистентов без вмешательства в код n8n.
* **Bitrix24 (CRM):** Интеграция для создания Контактов и Сделок. Работает в неблокирующем фоновом режиме. Дополнена дельта-выгрузкой стенограмм диалогов в Таймлайн сделок.
* **n8n AI Handoff:** Внешний оркестратор LLM-агентов. Принимает контекст после первичной квалификации и ведёт дальнейший диалог в stateless-режиме.
* **Contextual Python Logger:** Встроенный сборщик системных логов. Аккумулирует логи выполнения бизнес-логики по каждой сессии (`python_logs`), изолирует их внутри контекста пользователя и уничтожает из памяти строго после успешной выгрузки сессии в Data Warehouse.

## 2. Схема базы данных (PostgreSQL + SQLAlchemy)
В Production-среде используется PostgreSQL (асинхронный драйвер `asyncpg`), подключаемый через переменную `DATABASE_URL`. Для локальной разработки предусмотрен автоматический фолбэк на SQLite.

### Таблица: `users`
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | Integer (PK) | Внутренний ID. |
| `platform_user_id` | String (Unique) | Уникальный идентификатор пользователя на платформе (MAX user_id, Telegram chat_id, или web session_id). |
| `channel` | String | Канал пользователя: `"max"`, `"telegram"`, `"web"`. По умолчанию `"max"`. |
| `full_name` / `username` | String | Контактные данные профиля. |
| `phone` | String | Номер телефона (собирается через regex-перехватчик или vCard). |
| `active_deal_id` | String | ID текущей сделки в Bitrix24. |
| `context_json` | Text | JSON-кэш сессии. Хранит бизнес-данные (марка, платеж, тип воронки), массив `chat_history` (обрезается до 100 записей при сохранении), `last_interaction_time`, курсоры `bitrix_synced_index` / `nocodb_synced_index` и флаг `is_finalized`. |
| `is_smartbot_active` | Boolean | Флаг маршрутизации. `True` — работает n8n, `False` — работает Dialogflow. |

### Таблица: `pending_sync` (Очередь)
Обеспечивает гарантированную доставку данных в Bitrix24 при падении сети или ошибках API.

## 3. Логика состояний и маршрутизации (State Machine)

### Точка входа (Deep Link & Payload Split)
Пользователь переходит по ссылке вида `https://max.ru/id781424127394_bot?start=991211PW_HAVAL_DARGO`.

Архитектура **Payload Split**:
1. MAX присылает событие `bot_started` с payload `991211PW_HAVAL_DARGO`. Событие классифицируется как `input_type = "deeplink"`.
2. Бот заменяет подчеркивания на пробелы и пропускает строку через Regex.
3. Код `991211PW` уходит в фоновую задачу для поиска сделки в Bitrix24.
4. Название авто `HAVAL DARGO` сохраняется в контекст (`raw_model_text`) для точного поиска цен в NocoDB.
5. В Dialogflow отправляется очищенное слово `"start"` — гарантирует 100% срабатывание интента `00_Start_Lead_Request`.

### Классификация типа ввода (`input_type`)
Перед передачей в ядро каждое событие получает тип:
- `"text"` — `message_created` (обычное сообщение)
- `"button"` — `message_callback` (нажатие кнопки)
- `"deeplink"` — `bot_started` (переход по ссылке)

| `/chat_message` (POST) | `"text"` или `"deeplink"` | Входящее сообщение или старт сессии веб-виджета |

Тип `"deeplink"` исключает событие из логики перехвата текстовых возражений (`Immediate Objection Intercept`), предотвращая ошибочный запуск ИИ-агента при повторном переходе клиента по ссылке с другой моделью.

### Дерево маршрутизации (Message Pipeline)
1. **Global Fallback:** Нет активного `start_code` → просьба перезапустить по корректной ссылке.
2. **State `is_smartbot_active == True`:**
   - Текст складывается в буфер (`delayed_sender`, 10 сек). Параллельно активируется тайпинг-индикатор.
   - Текст пересылается в n8n (`/chat` action) со склеенным промптом из NocoDB.
3. **State `is_smartbot_active == False` (Квалификация):**
   - Текст летит в Dialogflow.
   - По результату проверяется `Communication_Type` дилера в NocoDB.
   - **Сценарий A (Call):** Запрос телефона, алерт в группу, завершение. Диалог архивируется в NocoDB немедленно.
   - **Сценарий B (Smartbot):** Флаг `is_smartbot_active = True`, отправка `INIT_AI_HANDOFF` в n8n.

### Динамические тексты по сценарию
Тексты запроса контакта и таймаута адаптируются под активный сценарий воронки:

| Сценарий | Текст запроса контакта | Текст таймаута |
| :--- | :--- | :--- |
| `credit` / `tradein` / `combo` | "Для получения **расчета**, подтвердите Ваши контакты" | "Вы также можете получить **расчет** онлайн" |
| `stock` | "Для получения **информации**, подтвердите Ваши контакты" | "Вы также можете получить **информацию** онлайн" |
| `consult` | "Для получения **консультации**, подтвердите Ваши контакты" | "Вы также можете получить **консультацию** онлайн" |

### Фоновая синхронизация и защита от дублей (Deal Hunt)
Трёхступенчатая система синхронизации с Bitrix24:
1. **Мгновенный перехват:** При `bot_started` вызывается `check_and_link_deal`.
2. **Перехват на финише:** Повторная проверка в `final_sync_wrapper`.
3. **Временная сделка + Охота:** Если сайт медлит — создаётся временная сделка, запускается `background_deal_hunt` (8 попыток × 15 мин).

### Умное логирование и Аналитический Архив (Smart Transcripts)

1. **Накопление и Курсоры:** Каждое сообщение складывается в `chat_history`. Два курсора: `bitrix_synced_index` (дельта для CRM) и `nocodb_synced_index` (прогресс архивации).
2. **Фоновая финализация (`finalize_transcript_archive`):** Выгрузка запускается строго после отправки клиенту последнего сообщения. После успешной выгрузки: `is_finalized = True`, `USER_CONTEXT.pop()`.
3. **DF-архивация:** Диалоги, завершённые в Dialogflow, архивируются немедленно в момент финализации ветки B с динамическим `Final_Status`.
4. **Брошенные диалоги:** `sync_worker` проверяет раз в 30 минут. Курсор `nocodb_synced_index` обновляется только после успешной архивации. `python_logs` очищаются вместе с курсором.
5. **Idempotency:** `is_finalized == True` блокирует повторную архивацию воркером.

### Многоканальная маршрутизация (Multi-Channel Routing)

Бот поддерживает три канала одновременно. Канал определяется при первом входящем событии и сохраняется в `USER_CONTEXT[user_id]['channel']` и в БД (`User.channel`).

| Канал | Точка входа | Идентификатор сессии | Алерты дилеру |
| :--- | :--- | :--- | :--- |
| `max` | `/max_webhook` | MAX `user_id` (int) | MAX группа |
| `telegram` | `/tg_webhook` | Telegram `chat_id` (int) | MAX группа |
| `web` | `/chat_message` | Web `session_id` (строка) | MAX группа |

**Правило алертов:** Алерты дилерам и технические алерты ВСЕГДА идут через `max_client` напрямую, независимо от канала клиента. Это гарантирует получение уведомлений даже если клиент пришёл через Telegram или веб-виджет.

**Ремайндеры и farewell:** `reminder_worker` и `sync_worker` проверяют `get_client(channel).supports_reminders()` перед отправкой сообщений. Веб-канал (`WebBotClient`) возвращает `False` — ремайндеры и прощальные сообщения для веб-сессий не отправляются.

**Farewell-текст:** Для канала `web` убрана фраза "перейдите на сайт" — клиент уже на сайте.

**Текст "Другая модель":** Для канала `web` заменяется на инструкцию закрыть чат и выбрать авто заново, вместо ссылки на сайт.

### Многоуровневая система удержания (Retention System)
* **Soft Handoff:** Перехват текстовых возражений (пауза 1.5 сек + тайпинг + 3.5 сек → ИИ). При молчании 30 сек — кнопки "ПРОДОЛЖИТЬ" / "ОТМЕНА".
* **Двухступенчатые ремайндеры:** +30 мин → AI-рерайт (`__SYSTEM_REMINDER__`). +90 мин → медиа-напоминание. Защита тихих часов (21:00–09:00).
* **TTL 48 часов:** `sync_worker` принудительно закрывает зависший ИИ-диалог, отправляет прощальное сообщение и переводит сделку в статус "Проиграна".
