# ТЗ для Alex_refactoring: данные оценки трейд-ина для личного кабинета

Дата: 2026-08-10. Адресат — CE проекта Alex_refactoring. Контекста кабинета у тебя
нет — этот документ самодостаточен, читать код кабинетного репозитория не нужно.

**Минимум контекста.** У бота появился клиентский личный кабинет (страница на
Tilda + API бота): клиент подтверждает телефон кодом и заполняет анкету, а с
недавнего времени — видит кредитный калькулятор, который считает в браузере на
тех же формулах `calc_engine.js`, что и твой Calc Engine в n8n. Входные данные
расчёта (позиция, цена, ставки, программа) бот **замораживает в снапшот** в
момент выдачи ссылки и на каждом ходе диалога — чтобы клиент видел те же цифры,
что называл Александр, даже если живые ставки сменятся. Для анкет трейд-ина и
комбо кабинету нужны данные оценки auto.ru — сейчас они до бота не доходят.
Отсюда две задачи ниже.

## 1. Задача 1 — доставить данные оценки auto.ru в бот

### Что сейчас

Результат оценки (`found_info` из ответа
`apiauto.ru/1.0/stats/partner/predict_by_vin_or_lp`) и посчитанная сумма зачёта
живут только внутри n8n: как observation тула `evaluate_auto` (контекст LLM) и
в tool-ответе Combo Calculator (`tradein_evaluation` в `combo_prepare.js`).
Наружу, в бот, ничего из этого не уходит — ни в колбэк Save-to-CRM, ни в
`json_cache`.

### Канал доставки — уже работает

Нода **Final Response** в `AI Agent v3.0.json` возвращает боту
`{ text, json_cache, session_context_update }`; `json_cache` бот сохраняет как
есть (`n8n_cache` в контексте пользователя) и возвращает тебе же в
`qualification_context.cached_json` на следующем ходе. Сейчас `json_cache`
наполняется только результатами Car Search (цепочка Cache Gate → Attach
Cache). Нужно класть в этот же объект данные оценки — приёмная сторона бота
уже готова и ждёт **два ключа верхнего уровня** `json_cache`:

| Ключ | Тип | Что это |
|---|---|---|
| `found_info` | object | Блок `found_info` из ответа auto.ru **целиком, как отдаёт сервис** (mark, model, year, steering_wheel, mileage, photos, owners_count, pts_original и всё прочее — не фильтруй) |
| `ti_valuation` | number | Сумма оценки трейд-ина (та, что сейчас `estimated_value` / `tradein_price_to` в combo-ветке) |

Точки чтения на стороне бота (для справки, лезть туда не нужно):
`cabinet_service.py:2733–2735` — `n8n_cache.get("found_info")` /
`n8n_cache.get("ti_valuation")` при заморозке снапшота; из `found_info` кабинет
рендерит блок «Ваш автомобиль» по ключам `mark`, `model`, `year`,
`steering_wheel` (код LEFT/RIGHT — бот сам переводит в «Левый/Правый»),
`mileage`, `plate`, `photos.main`; отсутствующие ключи просто не показываются.

### Госномер — отдельно, иначе потеряется

**В ответе auto.ru госномера нет** — он был только во входных параметрах твоего
запроса к сервису (клиент продиктовал его Александру). Если положить в
`json_cache` только сырой ответ, клиент увидит блок «Ваш автомобиль» без
госномера. Удобнее всего — **вложить его внутрь `found_info` под ключом
`plate`** (именно этот ключ ждёт фронт кабинета). Ожидаемая структура целиком:

```json
{
  "user_request": { "...": "как сейчас" },
  "complectations": [ "...как сейчас..." ],
  "found_info": {
    "mark": "KIA",
    "model": "Rio",
    "year": 2019,
    "steering_wheel": "LEFT",
    "mileage": 87000,
    "photos": { "main": "//avatars.mds.yandex.net/get-verba/..." },
    "owners_count": 2,
    "pts_original": true,
    "plate": "А123БВ777"
  },
  "ti_valuation": 890000
}
```

(`found_info` — сырой ответ сервиса плюс один добавленный ключ `plate`;
остальные поля auto.ru, не показанные в примере, оставляй как есть.)

### Чего делать НЕ надо

- **Не нормализуй URL фото.** `photos.main` приходит протокол-относительным
  (`//avatars.mds.yandex.net/...`) — бот дополняет до `https:` сам при
  заморозке. Нормализация на стороне n8n не нужна и не следует её делать.
- Не переименовывай и не «причёсывай» ключи `found_info` — контракт «как отдал
  сервис», любые преобразования на стороне бота.
- Не клади данные оценки в `ai_payload` колбэка Save-to-CRM — этот канал бот
  не разбирает на эти поля, работать не будет.

### Сценарии без трейд-ина — не сломать

Оценка выполняется не в каждом диалоге (чисто кредитные и стоковые сценарии её
не имеют). Контракт на этот случай: **ключей просто нет** в `json_cache`
(или `null` — бот трактует одинаково: `found_info` не-dict → null). Ничего
не подставляй, пустые объекты не клади — кабинет в этом случае показывает
редактируемые поля «Ваш автомобиль» (текущее поведение), это штатно.
Правка не должна затронуть наполнение `json_cache` Car Search'ем: `found_info`
/ `ti_valuation` — добавка к существующему объекту, не замена.

Обрати внимание на Cache Gate: `json_cache` пересобирается не на каждом ходе
(`fresh_cache || cached_json`). Данные оценки должны переживать этот механизм —
появившись после `evaluate_auto`, оставаться в `json_cache` на последующих
ходах (иначе бот заморозит снапшот без них на следующем же ходе).

**Страховка от пересборки — уже на стороне бота (реализовано 2026-08-10).**
На rebuild-ходе (TTL каталога 10 мин или переход стадии) бот шлёт
`cached_json = null` — источника для переноса из старого кэша у тебя нет.
Поэтому бот на **каждом** ходе дополнительно присылает
`qualification_context.evaluation_carryover`:

```json
{
  "found_info": { "...как ты положил в json_cache..." },
  "ti_valuation": 890000,
  "request": { "plate": "А123БВ777", "mileage": 87000 }
}
```

Правило для Final Response: собирая свежий `json_cache` (после перезапуска
Car Search), вливай `found_info`/`ti_valuation` из `evaluation_carryover`,
если своих, более свежих, нет. Ключ отсутствует вовсе (не пустой объект),
когда оценки ещё не было. `request` — входные параметры прошлой оценки:
задел под кэширование платного вызова на твоей стороне (сверка «тот же
госномер и пробег → не вызывать auto.ru повторно»).

## 2. Задача 2 — промпт: сначала комплектация, потом ссылка

Калькулятор кабинета считает по снапшоту, а снапшот замораживается по
**выбранной комплектации** (`user_request.selected_complectation_id` в
`json_cache`). Если Александр выдаёт ссылку на кабинет до того, как клиент
выбрал конкретную комплектацию, снапшота нет: клиент получает кабинет без
калькулятора, с ручным вводом трёх полей. Формально это штатная деградация,
фактически — потеря главной новой функции.

Нужна правка промпт-блока: **довести подбор до выбора конкретной комплектации,
и только после этого предлагать ссылку на кабинет.** Готовая формулировка — в
`docs/CABINET_PROMPT_NOTE.md` кабинетного репозитория (раздел «Дополнение
2026-08-10», прилагаю вместе с этим ТЗ); там же — базовая вставка про
`cabinet_url`/`cabinet_status`, если она ещё не внесена. Промпт-блоки живут в
NocoDB; у тебя есть `Prompts.csv` и папка `nocodb/` — где именно править,
решай по своим конвенциям.

## 3. Проверка результата

Проверяй на своём тест-контуре с `[TEST]`-копиями воркфлоу, не на боевых.

1. **Данные доехали до контекста бота.** После диалога с оценкой (сценарий
   трейд-ин/комбо, госномер продиктован) — запрос к дев-базе бота:

   ```sql
   -- SQLite (дев):
   SELECT json_extract(context_json, '$.n8n_cache.found_info'),
          json_extract(context_json, '$.n8n_cache.ti_valuation')
   FROM users WHERE platform_user_id = '<id клиента>';

   -- PostgreSQL:
   SELECT context_json::json #> '{n8n_cache,found_info}',
          context_json::json #> '{n8n_cache,ti_valuation}'
   FROM users WHERE platform_user_id = '<id клиента>';
   ```

   Правильный результат: первый столбец — JSON-объект с `mark/model/year/
   steering_wheel/mileage/plate/photos`, второй — число. Оба `NULL` — данные
   не доехали (смотри, кладёт ли их Final Response и переживают ли Cache Gate).

2. **Заморозка подхватила.** В логе бота на ближайшем ходе после появления
   данных: `cabinet: снапшот калькулятора user=<id> заморожен: item_id=...`
   (строка без исключений). Содержимое снапшота:

   ```sql
   SELECT json_extract(calc_snapshot, '$.found_info.plate'),
          json_extract(calc_snapshot, '$.ti_valuation')
   FROM cabinet_profile WHERE user_id = <PK users.id>;
   ```

   Непустые значения = контракт выполнен целиком. (Замечание: снапшот
   замораживается по выбранной комплектации — в тестовом диалоге доведи подбор
   до выбора, см. Задачу 2.)

3. **Сквозная проверка (по желанию):** клиент проходит верификацию в кабинете →
   `GET /cabinet/api/me` отдаёт `calc.found_info` и `calc.ti_valuation`; в
   анкете трейд-ина появляется read-only блок «Ваш автомобиль» с фото
   (протокол-относительный URL уже дополнен до `https:` ботом), в комбо —
   строка «Зачёт вашего автомобиля — 890 000 ₽».

## 4. Диалоговая тактика (план бота 2026-08-14-001) — что видно вашей стороне

Реализовано ботом 2026-08-15, парный план вашей стороны:
`docs/plans/2026-08-14-001-feat-cabinet-dialog-tactic-plan.md`.

### Завершение диалога при передаче заявки кабинета

Бот завершает сессию Александра в момент ДОВЕДЁННОЙ передачи заявки в CRM
(любой из трёх триггеров: submit анкеты / таймаут бездействия 10 мин /
потолок 60 мин от верификации). Проверяемо вашей стороной: **после передачи
исполнений по session_id больше нет** — ни chat-ходов, ни
`__SYSTEM_REMINDER__`. ОБЫЧНЫЙ chat-ход, бывший в полёте в момент передачи,
завершается штатно (его ответ доставляется ДО прощания), после — тишина.
Оговорка: на `__SYSTEM_REMINDER__`-ход эта гарантия НЕ распространяется —
если передача завершила сессию, пока ремайндер-ход летел, его ответ будет
тихо отброшен ботом (исполнение у вас состоится, доставки клиенту не будет).
Гонка неустранима (HTTP уже ушёл), окно узкое — фиксируем как контракт.

Дополнительно: в окне «номер подтверждён, анкета заполняется» (верификация →
передача) ремайндеры бота подавлены — `__SYSTEM_REMINDER__`-исполнений в этом
окне тоже не будет. До верификации ремайндеры идут как раньше, с полями
`last_bot_message` / `cabinet_url` / `cabinet_status` (ветвление текста
напоминания по cabinet_status работает без изменений).

### Стадия после полученной оценки — ЗА ВЫКЛЮЧЕННЫМ флагом

Бот-половина механизма готова и покрыта тестами: при валидной оценке
(`ti_valuation` > 0) ставится персистентная защёлка, и `current_stage`
приходил бы `closing` для tradein/combo вместо повторного пути к
`tool_needed`; новый госномер В ТЕКСТЕ сообщения снимает защёлку (повторная
оценка не блокируется). Правило гейтится env-флагом `STAGE_EVAL_RULE`
(дефолт ВЫКЛ) и **не включено**.

Условие включения — готовность вашей стадийной половины, вопрос обострён
фактом из кода бота: эвристика бота для tradein/combo НИКОГДА не выдаёт
`tool_needed` (обязательный слот mileage в боте не заполняется никем) —
значит, «tool_needed на каждом ходе» после оценки рождается на вашей
стороне (переопределение стадии по инструментальным интентам). Вопрос к вам:
**что именно у вас выставляет tool_needed после успешной оценки, и перестанет
ли оно перебивать closing от бота** (+ подтверждение, что closing-промпт при
phone_collected=false добывает телефон/ведёт в кабинет, а не финализирует).
Включение флага — совместный шаг после этого ответа.

## 5. Маркер [CABINET_LINK] — ссылка кабинета больше не печатается адресом

Дата: 2026-08-19 (план бота 2026-08-19-001, код выкачен в U1/U2). Меняется
контракт ТЕКСТА ответа Александра в сценариях с кабинетом; payload к вам
не меняется (`qualification_context.cabinet_url` / `cabinet_status` — как были).

### Контракт для промптов (три блока BLK_*_CABINET_CHOSEN)

- Модель **никогда не печатает адрес кабинета**. В месте ссылки внутри фразы
  ставится маркер `[CABINET_LINK]` — не больше одного на сообщение.
- Бот заменяет маркер на HTML-гиперссылку `<a href="…">личный кабинет</a>`
  во всех трёх каналах (MAX `format=html`, Telegram `parse_mode=HTML`,
  веб-виджет). Анкор по умолчанию — «личный кабинет» (форма совпадает в
  им. и вин. падежах); промпт строит фразу под него: «откройте [CABINET_LINK]»,
  «в [CABINET_LINK] вы можете…» → «откройте личный кабинет».
- Расширенная форма `[CABINET_LINK:свой текст анкора]` парсером поддержана
  (анкор — непустой, до первой `]`, без вложенных скобок; HTML-экранируется
  ботом), но в промпт-инструкции НЕ выдаётся — использовать только если
  фиксированный анкор окажется грамматически тесен.
- Правило «если `cabinet_url` пустая (null/отсутствует) — кабинет не
  упоминать вовсе» остаётся в силе. Если маркер всё же придёт без URL, бот
  деградирует его в фразу без ссылки и пишет warning — ссылки-пустышки и
  литерала маркера клиент не увидит, но это нарушение контракта.
- Прежняя правка «после адреса не ставить точку» **удаляется** — адреса в
  тексте больше нет, пунктуация вокруг маркера свободная.
- В few-shot-примерах блоков не должно остаться ни одного захардкоженного
  URL кабинета — только маркер.

### Рерайт-сценарии (важно, находка ревью)

В `chat_history`/`recent_history` и `last_bot_message` бот кладёт вместо
маркера **голый URL** (фактическое состояние диалога). Любой промпт, который
переписывает прошлые реплики — в первую очередь рерайт `__SYSTEM_REMINDER__`
по `last_bot_message`, — обязан следовать тому же правилу: **URL из истории
не перепечатывать**, при необходимости сослаться на кабинет — ставить
`[CABINET_LINK]`. Перепечатка руками возвращает класс ошибок «искажён один
символ токена → мёртвая ссылка», ради которого маркер и введён.

Обратная сторона нормализации: если подстановка деградировала (URL был
недоступен в момент отправки), в истории остаётся **фраза «личный кабинет»
без URL рядом** — отдельного флага в payload нет. Для промпта это читается
так: реплика Александра упоминает кабинет, но URL в том же сообщении истории
отсутствует → клиент ссылку, скорее всего, НЕ получил; повторный маркер на
следующем уместном ходе — правильное поведение (выдача идемпотентна, придёт
та же ссылка).

### Страховка на стороне бота

Если модель нарушит контракт и напечатает адрес, бот по точному вхождению
известного URL обернёт его той же гиперссылкой (тихо). Искажённый адрес бот
распознать не может — он уйдёт клиенту как есть. Страховка — сетка, не
разрешение печатать адрес.

### Порядок включения и отката

Блоки переписываются и передаются заранее; живое переключение промптов —
после приёмки U1+U2 на стенде. Откат: пока маркерные промпты активны,
код бота ниже U1 не откатывается; сначала вернуть до-маркерные промпты.

## 6. recent_history начинается с момента передачи — транскрипт воронки к вам больше не приходит

Дата: 2026-08-21 (план бота 2026-08-21-001, код в U1/U2). Контракт производной
`recent_history` в payload; сами поля payload не меняются.

### Что изменилось

- В момент AI handoff бот пишет в свою историю маркер границы (строка
  `role=system, type=ai_handoff`; писатель — `main.py`, точка активации
  ветки A, между включением `is_smartbot_active` и INIT-запросом).
- `recent_history` собирается **от последнего маркера**: на `INIT_AI_HANDOFF`
  приходит **пустой массив** — это норма, а не сбой; все данные квалификации
  (payment, plate, модель, cabinet_url и т.д.) — в структурных полях payload.
  На последующих ходах — только диалог клиента с Александром.
- Из среза исключены строки-кнопки (`type=button`): это служебная механика
  запуска сценариев. Важно: кнопки типа «ПО ТЕЛЕФОНУ» при дилерах
  Call/Smartbot нажимает САМ БОТ (авто-запуск сценария), клиент их не видел —
  ссылаться на «вы выбрали по телефону» модель не должна, и теперь не сможет.
- Полная история (включая воронку, кнопки и маркер границы) живёт в архиве
  бота и стенограммах NocoDB/Bitrix — для разборов инцидентов обращайтесь
  к ним, не к `recent_history`.

### Гарантии и границы

- `msg_count` и флаги `session_context` продолжают считаться по ПОЛНОЙ
  истории — стадийная эвристика не изменилась.
- `last_bot_message` после первого УСПЕШНОГО ответа Александра — его же
  реплика. Оговорка: при сбое INIT (единственная попытка, без ретраев)
  ремайндер может рерайтить последнюю реплику воронки — существующее
  поведение, не следствие этого изменения.
- Intercept-путь (клиент ответил возражением вместо телефона): реплика
  клиента-триггер в историю не пишется вовсе (подменяется служебной командой
  до точки записи) — на этом пути Александр стартует без последней фразы
  клиента. Тоже существующее поведение, фиксируем для ясности.
- Легаси-диалоги, переданные до выката, маркера не имеют — для них срез
  не применяется (прежнее окно последних 8 строк) до конца сессии.
