# Паритет формулы без паритета области поиска

## Problem

Кабинет ищет строку каталога NocoDB по `Complectation id` из снапшота —
формулой, дословно скопированной из `car_search_prepare.js:86`
(`Complectation id || Complectation_id || Id`), с комментарием о паритете.
Но `Complectation id` — только комплектационная часть идентификатора
(«16»), уникальная лишь внутри одной модели. По фактической выгрузке
каталога дилера 99 (26 строк, 6 моделей): id 11 и 12 несут по 7 строк
разных моделей; уникален один id 16 из шести. Поиск шёл `next(...)` по
всему каталогу — клиент, выбравший JOLION Comfort (id 11), получал карточку
первой попавшейся модели с id 11. Молча. Ручной тест прошёл только потому,
что выбранный 16 случайно уникален.

## Root cause

В n8n формула корректна, потому что применяется к массиву, УЖЕ
отфильтрованному по одной модели (нода Get Catalog возвращает строки модели
запроса — id внутри модели уникален). Бот скопировал формулу, но не область
поиска: сравнение по всему каталогу, где id не уникален. Однозначная
идентификация в остальной системе — склейка Model id + Complectation id
(«1416»), но n8n кладёт в `complectations[].id` только комплектационную
часть, и она замораживается в снапшот as is.

## Solution

Первая итерация снимала коллизию сужением по названию модели из снапшота
(`item_name`). **Обход снят на следующий же день**: идентичность на
человекочитаемой строке ломается при переименовании в источнике — название
меняется в NocoDB независимо от снапшота, снапшот живёт до 30 дней, а
формула названия была продублирована в двух местах (заморозка и поиск).

Итоговое решение — настоящий уникальный ключ, доступный боту без правки
n8n: пара (Model id, Complectation id). Она уникальна по таблице (проверено
по той же выгрузке дилера 99: 26 строк, ни одного повтора пары), и model_id
уже присутствует в эхе `qualification_context`, которое Car Search
возвращает внутри ответа (`car_search_prepare.js:220`), а бот сохраняет как
`json_cache` целиком. Заморозка кладёт model_id в снапшот (схема v2),
`_find_catalog_row` ищет по паре; снапшоты v1 без model_id деградируют к
поиску по одной комплектационной части (уникален → работает, коллизия →
честный 404 до ближайшей перезаморозки). Тест коллизии намеренно даёт обеим
строкам ОДИНАКОВЫЙ Model title — пройти его можно только парой, не именем.

## Prevention

- Копируя формулу сравнения из другой системы, копировать и **область
  применения**: над каким множеством она гарантирует уникальность и кто это
  множество сузил. Комментарий «паритет с X» обязан говорить об области,
  не только о формуле.
- Ключ, уникальный в отфильтрованном массиве, не уникален в полной таблице —
  проверять уникальность по фактической выгрузке, а не по удачному примеру.
- Совпадение «первое попавшееся» при неуникальном ключе — молчаливая выдача
  чужих данных; неоднозначность должна давать явный отказ (404/дефолты).
- **Идентичность не строится на отображаемых строках** (названиях,
  заголовкам): их переименовывают в источнике независимо от сохранённых
  ссылок на них. Если настоящего ключа «не хватает» — сначала поискать его
  в данных, которые системе уже доступны (здесь model_id лежал в эхе
  qualification_context собственного исходящего payload бота).
