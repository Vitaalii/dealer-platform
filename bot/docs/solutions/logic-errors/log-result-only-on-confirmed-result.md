# Лог результата — только по подтверждённому результату

## Problem

Четыре независимых места писали «результат», фиксируя лишь «попытку»:

1. `send_alert_to_max_group` ничего не возвращала → проверка `_ok` в
   `final_sync_wrapper` всегда получала `None` → «NOT delivered» логировался
   на каждой доставленной карточке. Метрика потерь не измеряла ничего.
2. Ремайндер писал `reminder_level=1` и реплику в контекст ДО отправки, а
   «Sent to» — безусловно после; при FATAL от MAX клиент ничего не получал,
   но история и уровень росли (фантомная реплика в стенограмме).
3. Техалерт ProstoSMS уходил в чат без парной строки в логе: два 627 за
   09-08 существовали только в мессенджере — в системе следа нет.
4. `reliable_send` при отказе MAX писал «Возможно 503» — фактический статус
   и тело ответа не логировались нигде.

Каждый случай стоил времени разбора: три ошибочные версии за день выросли
из ложных записей.

## Solution (план 2026-09-08-002)

- Отправляющие функции возвращают фактический статус: `send_alert_to_max_group`
  и `send_smartbot_reply` → bool «доставлено» (U2).
- Порядок у ремайндера: отправка → фиксация. «Sent», `reminder_level`,
  запись в историю — только при подтверждённой доставке, иначе «retry на
  следующем тике» (U3).
- Любое уведомление владельцу имеет парную строку в логе с тем же текстом
  ДО отправки в чат — грепается `TECH_ALERT` (U1).
- Отказ MAX логирует статус и тело ответа — грепается `MAX_API_ERROR` (U2).
- `check_balance` логирует любой не-ok независимо от того, ушёл ли алерт (U1).

## Урок

Попытка, результат и канал — три разных факта; строка лога обязана называть
тот, который проверен. «Sent»/«NOT delivered» без возврата статуса из
отправляющей функции — это лог намерения, замаскированный под лог результата;
он хуже отсутствия лога, потому что уводит диагностику в уверенно-неверную
сторону. Фиксация состояния (уровни, история, стадии) — только после
подтверждённого результата, иначе ретрай невозможен, а данные искажены.
