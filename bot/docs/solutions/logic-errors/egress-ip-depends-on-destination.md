# Внешний IP зависит от направления: замер «а какой у нас адрес?» бессмыслен без указания получателя

## Problem

Разбирая 627 от ProstoSMS, мы замерили «внешний адрес бота» запросом к
api.ipify.org: стабильные 103.112.69.233, которых нет в белом списке
45.92.179.192/28. Вывод «адрес вне списка» лёг в диагноз, а первая версия
починки сторожа (U4 плана -002) вшила этот же замер в текст алерта.

Ответ поддержки Dockhost (контейнер 5d2b8906-92d8-4d61-bf5f-51c00dd9666e)
опроверг посылку: у контейнера ДВА исходящих канала — основная сеть
45.92.179.192/28 и зарубежная (адреса не публикуются и могут меняться);
выбор канала определяется НАПРАВЛЕНИЕМ трафика. api.ipify.org стоит за
Cloudflare → запрос к нему всегда уходит зарубежной дорогой и показывает
адрес той дороги. Контрольный замер: ifconfig.me → 45.92.179.194 (РФ-пул),
api.ipify.org → 103.112.69.233 — одновременно. Выделенного статического
исходящего адреса Dockhost не даёт.

То есть 103.112.69.233 — адрес на пути к ipify, а не к ssl.bs00.ru.
Сторож с таким замером сообщал бы неверный адрес увереннее прежнего.

## Solution

- Замер через сторонние сервисы из алерта убран полностью; сборка алерта
  не делает HTTP-запросов (тест-пин: TestConfigAlertText).
- Алерт честно объясняет: «внешний адрес на пути к ProstoSMS изнутри не
  определить: два исходящих канала, выбор по направлению, адрес видит
  только получатель» (sms_gateway.EXTERNAL_IP_EXPLANATION).
- У API ProstoSMS метода «адрес вызывающего» нет (методы: push_msg,
  get_msg_report, get_profile, get_prices, wait_call) — единственный
  источник правды об адресе — access-логи провайдера, запрашиваются
  через поддержку. Алерт называет этот следующий шаг явно
  (sms_gateway.NEXT_STEP_HINT, Р13).
- Устойчивость к повторам (Р11/Р12, cabinet_service): при 602/627 —
  один повтор get_balance через паузу (CABINET_ALERT_RETRY_DELAY, 90с)
  перед алертом; повторные отказы в окне 6ч подавляются
  (TECH_ALERT_SUPPRESSED в лог), на 3-м подряд — один эскалационный
  алерт «ПОВТОРЯЕТСЯ»; успешная проверка закрывает окно.

## Финал инцидента (ответ поддержки ProstoSMS, 2026-09-08)

«Проблема была с ip адресом 202.133.219.44, именно по нему не проходили
запросы. На нашей стороне он был пересохранён». Виновный адрес —
**202.133.219.44** — не принадлежит НИ подсети Dockhost 45.92.179.192/28,
НИ зарубежному 103.112.69.233 из замера ipify: третий адрес, о котором не
знали ни мы, ни хостинг. Ни один способ замера изнутри его бы не показал:

- локальный адрес соединения одинаков для всех направлений
  (10.160.53.190, проверено прогоном из прод-контейнера);
- traceroute в образе отсутствует;
- эхо-сервисы отвечают про дорогу к себе, не к получателю.

Рабочий путь диагностики — **запрос access-логов у получателя** (поддержка
провайдера): только они показывают фактический адрес пары «мы → они».
Формулировка провайдера «должна решиться» — не «решена»: отказы были
редкими (два за сутки), тишина в ближайшие часы ничего не доказывает.

Три ложные версии по дороге (каждая опровергнута фактом — не повторять):

1. «Клиент запрашивал код подтверждения» — за час до алертов не было ни
   одного запроса кода (access-логи).
2. «Сломана доставка карточки дилеру» — карточка сделки 51503 дошла,
   владелец предъявил её; «NOT delivered» в логе был ложью (U2 плана -002).
3. «Вебхук MAX — триггер обращения к ProstoSMS» — причинность обратная:
   ответ 342 — эхо СОБСТВЕННОГО алерт-сообщения бота в группе.

## Урок

«С какого адреса мы выходим наружу?» — некорректный вопрос при
policy-based routing у хостера: адрес существует только в паре
«мы → конкретный получатель». Замер через произвольный эхо-сервис отвечает
про дорогу к эхо-сервису и ни про что больше; за CDN (Cloudflare) дорога
почти гарантированно другая. Если надёжного способа узнать адрес именно
нашей пары нет — честное «определить не удалось» в алерте лучше уверенного
чужого адреса: ложный адрес уже дважды за день уводил диагностику.
