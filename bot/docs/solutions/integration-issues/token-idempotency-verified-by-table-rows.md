# Идемпотентность выдачи: проверка — содержимое таблицы, не ветка кода

## Problem

Дев-стенд 2026-08-12, дилер 99: три токена одной связки (user, dealer,
deal) — два revoked, один active. Ход диалога → токен 9; ручной запуск
`scripts/issue_cabinet_link.py` → токен 10, токен 9 отозван; верификация
номера (bound_phone заполнен); следующий ход диалога → токен 11, токен 10
отозван вместе с подтверждённым номером. Ссылка из раннего сообщения —
«Ссылка недействительна». Код ветки выдачи при этом выглядел корректно:
«активный токен той же связки → тот же URL (R19)» — и юнит-тест этой ветки
был зелёным.

## Root cause

Два процесса — два разных дев-ключа HMAC. Бот без `CABINET_HMAC_KEY` в
`.env` использовал дефолт cabinet_service (`dev-insecure-cabinet-key`),
а скрипт выдачи ставил СВОЙ (`os.environ.setdefault(..., 
"dev-issue-script-hmac-key")`). URL токена восстанавливается детерминированно
из ключа и nonce (plaintext в БД не хранится); при чужом ключе выведенный
токен не совпадает с token_hash, и код уходил в ветку «ротация ключа»:
отозвать, выдать новый. Каждая выдача «с другой стороны» границы
бот↔скрипт отзывала живой токен — включая уже привязанный к номеру.

Ветка ротации была самостоятельной ошибкой дизайна: отзыв уносит
bound_phone (TOFU) и убивает ссылку из ранних сообщений, ХОТЯ ОНА РАБОТАЕТ —
`/auth/init` сверяет sha256 предъявленного токена, ключ HMAC в проверке не
участвует.

## Solution

1. Скрипт выдачи использует тот же источник ключа, что бот: `load_dotenv()`
   + общий дев-дефолт cabinet_service; собственный ключ скрипта удалён.
2. Отзыв токена — ТОЛЬКО по исключениям R19 (другая сделка, другой дилер,
   перепривязка склейкой). Невоспроизводимость URL текущим ключом токен не
   отзывает: ссылка на этот ход не выдаётся (None), оператору — техалерт,
   ранее отправленная ссылка и bound_phone сохраняются.
3. Тест инцидента: несколько последовательных ходов одной связки → ровно
   одна строка cabinet_tokens, тот же token_hash, статус active,
   bound_phone сохранён; плюс тест несовпадения ключа (токен жив, ссылка
   None, алерт есть).

## Prevention

- **Идемпотентность выдачи проверяется по фактическому содержимому таблицы
  токенов после нескольких ходов** (сколько строк, какие статусы, что с
  bound_phone), а не по коду ветки выдачи и не по равенству URL в одном
  процессе. Зелёная ветка «тот же URL» ничего не говорит о поведении на
  границе процессов.
- Детерминированный вывод секрета из ключа означает, что ключ — часть
  контракта между ВСЕМИ процессами, пишущими в одну таблицу; у
  вспомогательного скрипта не может быть «своего» дефолта.
- Ветка «не удалось воспроизвести → отозвать и перевыпустить» превращает
  любое расхождение конфигурации в молчаливое разрушение данных; правильный
  ответ на невоспроизводимость — сохранить и просигналить, не уничтожить.
