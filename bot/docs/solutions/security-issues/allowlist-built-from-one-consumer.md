# Ограничение доступа проверяется на КАЖДОМ потребителе, а не на одном

## Problem

Гейт `/catalog` (закрытие дыры «любая таблица читается серверным токеном»)
собрал allowlist из двух источников: запросы ОДНОГО лендинга (статичная
тройка таблиц Haval/дев) и поля Dealers, которые читает САМ БОТ
(Sourse/Stock/Program/Rates). Проверка после выката тоже шла на одном
лендинге. Через два дня сломался боевой лендинг Geely: его таблица
оснащения лежала в колонке «Features table id», которую бот не читает, — и
не попала в allowlist. Заодно молча сломались цвета ВСЕХ брендов (их
таблицы не лежали ни в одной читаемой колонке — поп-ап открывается по
клику, при выкатной проверке не открывали).

## Solution

Источник истины — КОНФИГУРАЦИЯ, а не код или опрос одного потребителя:
правило данных «колонка Dealers `* table id` = публичная таблица». Сбор —
по шаблону ИМЕНИ колонки (`_dealer_table_columns`, нормализованное имя
оканчивается на `tableid`): будущие колонки попадают без правок кода.
Справочник перечитывается раз в 600 с (новая таблица/дилер — без рестарта).
Вместо жёсткого denylist — техалерт `catalog-allow-new` о каждой таблице,
которой не было в предыдущем прочтении (дедуп, первое прочтение молчит).

## Prevention

- Сужение доступа (allowlist, whitelist, CORS, гейт) — это ИЗМЕНЕНИЕ
  ПОВЕДЕНИЯ для всех потребителей: инвентаризовать потребителей (все
  лендинги всех брендов, кабинет, виджет) и проверять каждого, включая
  функциональность по клику (поп-апы, ленивые загрузки).
- Тест «второй потребитель с ДРУГИМ набором ресурсов» обязателен для любого
  allowlist — инцидентный случай именно такой.
- Если данные о ресурсах уже лежат в конфигурации (Dealers) — строить
  ограничение от неё целиком, а не от подмножества, которое читает код.
