# Боевые ключи доступа попали в историю git внутри обычных .py-файлов

## Problem

Перед первым пушем локального репозитория в приватный GitHub проверка нашла в истории боевой webhook-URL Bitrix24 (полный доступ к CRM на чтение и запись) и токен бота. Секреты лежали не в файлах с «секретными» именами, а внутри трёх обычных python-скриптов, поэтому `.gitignore`, составленный по именам файлов, их не остановил.

## Symptoms

- `git grep` по отслеживаемым файлам находит `WEBHOOK_URL = "https://b24-….bitrix24.ru/rest/1/<секрет>/"` в `check_bitrix_full.py:5` и `check_stages.py:5`, а также `token = "<секрет>"` в `activate_webhook.py:6`.
- Проверка истории по именам (`.env`, `credentials.json`, `google_key_dev.json`, `data/`, `back_up/`) проходит чисто — 74 пути во всех коммитах, ни одного совпадения.
- Секреты внесены первым же коммитом (снимок исходного состояния проекта), поэтому присутствуют в дереве каждого из 18 коммитов.

## What Didn't Work

- **Проверка только по именам файлов.** Первая проверка (`git rev-list --objects --all` + фильтр по путям) дала «чисто» и создала ложное ощущение безопасности. Она не могла поймать секрет, вписанный в тело `.py`-файла, — а именно так он и был вписан.
- **Расчёт на `.gitignore`.** Файл был составлен при инициализации репозитория и покрывал `.env`, ключи сервисных аккаунтов, `data/`, `back_up/`, `venv/`. Всё это отработало корректно, но `.gitignore` в принципе не является средством контроля секретов: он фильтрует по путям, а не по содержимому.
- **Ошибка в самой проверке.** Промежуточный вариант команды имел вид `(git rev-list … | while read c; do git grep … $c; done | head -5) && echo "НАЙДЕНО"`. Код завершения здесь принадлежит `head`, а не `grep`, поэтому ветка «найдено» срабатывала всегда, даже при нуле совпадений. Ложная тревога после уже выполненной чистки. Правильный вариант — писать результат в файл и проверять его непустоту через `[ -s ]`.

## Solution

Репозиторий ни разу не отправлялся наружу, поэтому утечки не произошло и ротация ключей не потребовалась — достаточно было почистить историю до первого пуша.

1. **Резервная копия перед разрушительной операцией:**

   ```bash
   tar czf ../unifiedbot_GIT_BACKUP_YYYYMMDD.tar.gz .git
   tar tzf ../unifiedbot_GIT_BACKUP_YYYYMMDD.tar.gz | wc -l   # проверить, что архив читается
   ```

2. **Переписывание истории.** `git-filter-repo` не установлен, для 18 коммитов достаточно встроенного `filter-branch`:

   ```bash
   FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch \
     --index-filter 'git rm --cached --ignore-unmatch activate_webhook.py check_bitrix_full.py check_stages.py' \
     --prune-empty -- --all
   ```

3. **Реальное удаление объектов** — без этого старые blob-ы остаются достижимы через рефлог:

   ```bash
   rm -rf .git/refs/original
   git reflog expire --expire=now --all
   git gc --prune=now
   ```

4. **Восстановление файлов на диск.** `filter-branch` в конце синхронизирует рабочую папку с новой историей и удаляет из неё файлы, которых больше нет в `HEAD`. Скрипты были нужны пользователю, поэтому их вернули из резервной копии:

   ```bash
   mkdir /tmp/restore && cd /tmp/restore && tar xzf …/unifiedbot_GIT_BACKUP_YYYYMMDD.tar.gz
   git --git-dir=.git show <старый-коммит>:activate_webhook.py > <проект>/activate_webhook.py
   ```

5. **Занесение в `.gitignore`** с пояснением, почему именно:

   ```gitignore
   # Разовые утилиты с захардкоженными ключами доступа (webhook Bitrix, токен бота).
   # Лежат на диске, но в репозиторий не попадают — удалить секрет из истории потом сложно.
   activate_webhook.py
   check_bitrix_full.py
   check_stages.py
   ```

6. **Повторная проверка обоими способами** — по путям и по содержимому всех версий всех файлов (см. Prevention), затем пуш.

## Why This Works

Корневая причина — не отсутствие правила в `.gitignore`, а отсутствие шага проверки содержимого перед первым коммитом. Секрет — это значение, а не имя файла: боевой webhook Bitrix выглядит как обычный URL в переменной и не отличим от безобидного кода ни по расширению, ни по пути. Любая проверка, работающая с путями, эту категорию пропускает по построению.

Переписывание истории здесь безопасно ровно потому, что репозиторий ещё не публиковался: ни у кого нет копии старой истории, форс-пуш не нужен, чужие клоны не ломаются. Это окно закрывается в момент первого пуша — после него удаление секрета требует форс-пуша, сотрудничества всех, у кого есть клон, и всё равно оставляет значение в кэше платформы, так что единственным надёжным ответом становится ротация ключа.

## Prevention

- **Проверять перед первым пушем в двух измерениях, а не в одном.** По путям:

  ```bash
  git rev-list --objects --all | awk '{print $2}' \
    | grep -E '(^|/)(\.env|credentials\.json|google_key_dev\.json)|^data/|^back_up/|^venv/|\.pem$|\.key$'
  ```

  По содержимому всех версий всех файлов:

  ```bash
  OUT=/tmp/scan.txt; : > $OUT
  for c in $(git rev-list --all); do
    git grep -IE 'rest/[0-9]+/[a-z0-9]{10,}|AIza[0-9A-Za-z_-]{20,}|sk-[A-Za-z0-9]{20,}|ghp_[A-Za-z0-9]{20,}|-----BEGIN' $c -- >> $OUT 2>/dev/null
  done
  [ -s $OUT ] && echo "СЕКРЕТЫ ЕСТЬ" || echo "чисто"
  ```

  Проверять непустоту файла через `[ -s ]`, а не код завершения конвейера с `head` — иначе проверка всегда «находит».

- **Шаблон запроса под конкретную интеграцию.** Для Bitrix24 признак секрета — `rest/<число>/<строка>` в URL; общие шаблоны вроде `api_key=` его не ловят. При добавлении новой интеграции добавлять её характерный шаблон в скан.

- **Разовые утилиты держать вне репозитория с самого начала.** Скрипты «проверить стадии», «активировать вебхук» пишутся быстро, часто с ключом прямо в коде, и живут в корне проекта. Либо сразу в `.gitignore`, либо переводить на чтение из `.env`, как основной код.

- **Резервная копия `.git` перед любым переписыванием истории.** Восстановление файлов на диск после `filter-branch` уже потребовало её один раз в этом инциденте.

- **Разделять «секрет вычищен» и «секрет отозван».** Чистка истории закрывает вопрос только до первой публикации. Если репозиторий уже пушился — ротация ключа обязательна, чистка её не заменяет.
