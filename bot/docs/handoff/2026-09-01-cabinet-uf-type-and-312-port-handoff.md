## 3. Установлено измерением (не из документации)

Помечено ⚠ — факт опроверг прежнее предположение.

**Поле «Тип обращения» (UF_CRM_666D69C9EEE1B):**
- Тип поля в Битриксе — `string`, не список (живой запрос
  `crm.deal.userfield.list`, 2026-08-31): текстовые подписи пишутся корректно.
- **Принятый признак исхода — `submitted_at` анкеты в момент конверсии, НЕ
  триггер передачи.** Обоснование, установленное чтением кода: (а) триггер
  до точки формирования поля не доезжает — `_run_conversion(user_id)`
  вызывается без него (`cabinet_service.py:2336-2338` на момент разведки);
  (б) recovery-воркер подменяет триггер на `"recovery"` при повторе
  зависшего захвата (`_recover_stuck_handoffs` → `_complete_handoff(user_id,
  "recovery")`) — конверсия сабмит-захвата приходит с чужим триггером,
  `submitted_at` из БД даёт верный ответ и там.
- Вторая конверсия при позднем сабмите не выполняется никогда — ветка
  `late_submit` в `attempt_handoff` делает только дозапись; поэтому поле
  дозаписывается отдельным `crm.deal.update` (решение O1, коммит `19017e1`).
- Сценарий в кабинетную конверсию НЕ ограничен тройкой credit/tradein/combo:
  выдача ссылки сценарием не гейтится, чат пишет в контекст
  stock/consult/refusal/other_model/'unknown'. «Три сценария» — правда
  только для UI анкеты.
- Чат-путь пишет поле безусловно при статусах visit/call
  (`main.py:641,643,1130,1132`) — кода, запрещающего запись после кабинетной
  передачи, нет; «Александр закрывает чат» обеспечивается только промптом.

**Валидаторы телефона (живой прогон обоих, 2026-09-01):**

| Вход | бот `database.is_valid_phone` | кабинет `cabinet_service.normalize_phone` |
|---|---|---|
| `+79001234567`, `89001234567`, `9001234567`, `8 (900) 123-45-67` | True | `+7…` |
| `84951234567`, `74951234567` (городские 11-значные) | **True** | **None** |
| `4951234567` (10 цифр не с 9) | False | None |
| `+375291234567`, `+380501234567` | False | None |
| `phone79001234567` (≥5 букв) | **False** | **`+79001234567`** |

  (сценарий, под который выдана ссылка), НЕ текущий `context_json`.
  Обоснование: клиент заполнял конкретную анкету; переквалификация в чате

## 6. Ловушки, на которые натыкался в этой сессии

- Страж медиа-запросов фронта читает первые 2500 символов от ПЕРВОГО
  `@media (max-width:600px)` в `app.js` — новый media-блок раньше
  канонического сдвигает точку отсчёта и роняет тест; новые мобильные
  правила — только в ХВОСТ существующего блока.
- `load_dotenv()` в `main.py` заражает env всего pytest-процесса боевыми
  значениями (любой тест, импортирующий main) — тестовые коды полей
  пиновать monkeypatch'ем, не полагаться на чистоту окружения.
- `CONSENT_TEXT` больше не единая константа — текст согласия собирается из
  четырёх кусков (`CONSENT_PREFIX`/`CONSENT_POLICY_PHRASE`/`CONSENT_MIDDLE`/
  `CONSENT_AGREEMENT_PHRASE` в `app.js`); при поставке юридического текста
  менять куски и тест `test_consent_pieces_recompose_canonical_text`.
- Снапшот-тест хендоффа сравнивает словарь ЦЕЛИКОМ
  (`test_handoff_feeds_real_snapshot_into_conversion`) — любой новый ключ
  снапшота требует правки ожидания.
- Точное сравнение строк в grep-тестах ловит и КОММЕНТАРИИ — негативный пин
  (`"_starts_ok" not in src`) упал о собственный комментарий с этим словом.
- В рабочем дереве могут лежать незакоммиченные правки владельца — перед
  началом работ проверять `git status` полностью (не `head -N`: длинный
  список неотслеживаемых файлов прячет модифицированные).
