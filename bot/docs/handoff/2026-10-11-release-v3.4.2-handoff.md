## 5. Отклонения от плана

- Сборка `Production/` закоммичена вместе с U2, а не в U3: без неё тест устаревшей сборки красный, коммит — только при зелёном pytest.
- Проверка `.br` вендорских файлов — через `tools/vendor-assets.mjs --check` (node) из pytest: пакета `brotli` в окружении Python нет.
- `retry_after` 429 в веб-сессии теперь — более позднее из двух ограничений (окно 10 мин и 45 с), раньше — только сработавшее первым.
  Нужно, чтобы обещанное время совпадало с моментом, когда 429 уходит.
- Шаг 5 живой проверки: подсказка «Код не пришёл?…» появляется вместе со ссылкой в ЧЧ:ММ, а не в момент истечения кода
  (опрос статуса останавливается через 5 минут после экрана — поведение прежнее).
- Исправление повторной отправки (план 2026-10-12-001): ожидание существующего теста `test_chat_fields_failed_stage_goes_to_queue_bypassing_debounce` дополнено ключом «было» в теле задачи очереди — по решению владельца 12.10; смысл теста прежний.
- Там же: таймаут 30 с — только для записи стадии; «Новая → Квалификация» при старте чата идёт прежним запросом (поля + стадия, 10 с), «было» добавляется только в задачу очереди.

## 6. Код-ревью выпуска (2026-10-12, v3.4.1..HEAD)

Три ревьюера: корректность, безопасность, надёжность. **P1 нет.** pytest: SQLite 1455 passed / 4 skipped, PostgreSQL 1459 passed.

P2 (не исправлялись, решает владелец):
- Второе сообщение клиента во время финальной синхронизации может запустить вторую синхронизацию: та прочитает «Отправлено» как «было» и снова поставит «Обогащение». Риск был и раньше, окно шире (при ложном таймауте ~40–50 с вместо ~20 с). Лечение — флаг «идёт финализация» или замок на пользователя.
- Перезапуск бота во время пауз условной смены стадии теряет стадию. В кабинете гард `handoff_stage` уже записан, подбор её не повторит. Лечение — ловить отмену и ставить задачу с «было» в очередь.
- Если «было» неизвестно (не удалось чтение перед записью) и запись применилась по таймауту, задача без ключа уходит в досылку прежним путём — возможен прежний дубль. Лечение — ограничитель «писать только из стадий до передачи».
- Досылка задач со стадией без ключа идёт с таймаутом 10 с (как в 3.4.1). Лечение — таймаут стадии по наличию `STAGE_ID`.
- Передача из кабинета по таймауту и подбор зависших идут внутри тика `otp_worker`: долгий Битрикс задерживает тик на минуты.
- Повторная финализация уже переданной сделки (`active_deal_id` в «Отправлено») по-прежнему переводит её в «Обогащение» — было и в 3.4.1.

P3:
- Запасной номер веб-входа без ограничения возраста последнего запроса.
- `_request` с attempts > 3 → IndexError, проглатывается.
- Задача стадии из кабинета при `fields_ok=False` почти всегда без ключа.
- «Было» совпадает с целевой стадией → возможна вторая запись.
- Долгий проход досылки при массовом сбое.
- Расхождение часов клиента и сервера / округление ЧЧ:ММ на экране 8h; 429 после F5 ведёт на 8g.
- Тестам не хватает сценариев: отмена в паузе, склейка с ключом «было», чужой токен для запасного номера.
