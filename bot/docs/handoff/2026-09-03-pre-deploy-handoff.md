## 3. Установлено измерением в этой сессии

Замеры по dev-порталу Bitrix `b24-mxici0` (webhook из `.env`,
read-only) и по коду:

- **Поле канала — строковое, не списочное** (замер
  `crm.deal.userfield.list`, ID 259): `USER_TYPE_ID: "string"`,
  `DEFAULT_VALUE: "По телефону"` на стороне CRM. Значит **опровергнуто**
  предположение постановки, что web/max/tg и «По телефону» должны быть
  элементами одного списка — никакого справочника нет.
- **Источники Тильды в CRM:** `web` — 429 сделок, `max` — 1583,
  `telegram` — 309, «По телефону» — 8424, «В MAX» — 143 (замер
  `crm.deal.list` по значениям поля). **Опровергнуто** раннее «tg=0»:
  правильное значение источника — `telegram`, не `tg` (уточнение
  владельца, подтверждено замером).
- **ИИ-квалификации за всю историю:** сделок с «Типом обращения»
  «Звонок по телефону» — 6, «Визит в салон» — 1; из них без телефона в
  контакте — 1 (**сделка 47011**) — живой пример кейса, который
  закрывает барьер Р4. Стадия «Обогащение» транзитная: на момент замера
  на ней 0 сделок (при 1219 на «Отправлено»).
- **Телефона в колбэке n8n нет по контракту:** Save-to-CRM шлёт только
  `user_id`, `deal_id`, `ai_payload` (узел HTTP Request в
  `N8N/Alex_refactoring/flow/TOOL_ Save to CRM.json`, ретраи 5×3с);
  агенту прямо запрещено писать номер (description `finalize_deal`,
  «AI Agent v2.0 MAX.json»). Номер попадает в карточку только из
  `User.phone` (main.py:1208-1213 области фоновой задачи колбэка).
- **Четыре причины потери номера рефлексом** (перехват из текста клиента
  во время ИИ-диалога, main.py:2297-2302): (1) формат вне регэкспа
  `payload_v2.PHONE_RE` (payload_v2.py:18) — точки-разделители, номер
  словами, разбивка на сообщения за пределами 3-секундного буфера;
  (2) строгая РФ-валидация `normalize_phone` (database.py:429-448);
  (3) страж кабинетного OTP `PHONE_WRITE_GUARD` не даёт перезаписать
  подтверждённый номер (database.py:435-440); (4) гипотеза: голосовое
  без текстовой расшифровки рефлексу не видно.
- **Рудимент условия финализации** (найден при внедрении барьеров):
  условие `if status in [5 статусов]` перед отключением ИИ после
  подстановки выполнялось ВСЕГДА — блок сделан безусловным (main.py,
  комментарий у блока «Отключение ИИ»), иначе сырые (Р3) и `working`
  (Р2) статусы перестали бы закрывать диалог и выгружать стенограмму.
  Поведение прежних случаев сохранено бит-в-бит.
- **Дефолт подстановки был ненаблюдаем по построению:** исходный статус
  не писался никуда, строка «Status (Fixed)» печатала уже подменённое
  значение и стояла всегда. Замер по всем 604 записям архива NocoDB
  (таблица `mnivr6uyf5ckzru`): нераспознанных сырых значений ноль, но по
  колбэк-пути их и не могло быть видно. Теперь наблюдаемость есть (Р1) +
  сырой статус доезжает до `Final_Status` архива при Р3.
- **Аварийный мост обрабатывает статусы иначе, чем колбэк** (факт,
  важно для отладки): дефолт при отсутствии ключа — `in_progress`
  (main.py, `smart_data.get("status", "in_progress")` в мосте), белого
  списка нет, неизвестные строки падают в `DEFAULT_STAGE`=«ОЖИДАНИЕ»
  (crm_mapping.py:18). После Р4 мост дополнительно гейтит visit/call по
  телефону.

## 4. Решения владельца — действующие правила (не переоткрывать)

По гейту канала (сессия 2026-09-02):
- **ОВ-1:** «По телефону» пишется всегда, когда в Битрикс уходит заявка
  с валидным номером — независимо от пути (чат или кабинет). Механизм
  единый, не два параллельных.
- **ОВ-2 (матрица получателей):** Битрикс-поле: телефон валиден →
  «По телефону», телефона нет → ключ не отправляется, значение Тильды
  нетронуто. Карточка-алерт и архив NocoDB: телефон валиден →
  «По телефону», телефона нет → фактический канал клиента в читаемом
  виде. Обоснование: в Битриксе источник уже записан Тильдой — боту
  дублировать нечего; алерт и архив бот создаёт сам и канал знает
  достоверно. ВАЖНО: вторая колонка (читаемый канал в алерте/архиве)
  НЕ реализована — см. §6, признана ненужной позже.
- **ОВ-3:** переходный хвост принят — payload'ы, уже лежавшие в
  `pending_sync`, доедут со старым «В MAX»; скраб очереди не делается.
- **ОВ-4:** источник `tg` не существует, правильное значение `telegram`.

По статусам n8n (сессия 2026-09-02/03):
- **В1:** барьер Р4 действует и в аварийном мосте — иначе честный
  visit/call без телефона уходит мостом на «Обогащение» и защита
  декоративна.
- **В2:** при уходе в «ОЖИДАНИЕ» данные пишутся полностью (смарт-поля,
  «Тип обращения», стенограмма, архив) — саппорту нужна полная картина;
  меняются только стадия и подавление карточки.
- **В3:** укрепление перехвата телефона из ИИ-диалога — отложено,
  отдельная задача, НЕ планировать без команды владельца.
- **В4:** при Р3 в реестр дедупликации регистрируется сырой статус.
- **Уведомления при барьерах:** «ОЖИДАНИЕ» — стадия ручной обработки
  саппорта; саппорт оповещается средствами Битрикса, бот дополнительных
  уведомлений не шлёт.
- **Обязательное требование:** эвристика `next_step` → visit — под тем
  же телефонным гейтом, что и подстановка (закрыто кодом и тестом).

## 6. Открыто и не решено

- **«Неизвестно» в «Типе обращения» при нераспознанном сценарии.** При
  пустом/не входящем в словарь `scenario_type` кабинетное значение не
  формируется, фолбэк `_map_type` для unknown пуст → ключ не
  отправляется, поле не трогается; в ветке позднего сабмита фолбэка нет
  вообще. Что писать — решение владельца не принято (тянется из
  хендоффа 2026-09-01 §5).
- **Укрепление перехвата телефона из ИИ-диалога** — отложено решением
  В3 (факты о четырёх причинах потери — §3). Не начинать без команды.
- **Реестр дедупликации не поднимается из базы:** обработчик берёт
  контекст как `USER_CONTEXT.setdefault(...)` — после рестарта процесса
  или очистки контекста реестр пуст, ретрай обработается как новый
  (main.py, начало `handle_n8n_callback`). Осознанно не чинилось —
  повторная обработка идемпотентна по стадии, но алерт может
  задублироваться.
- **Роут `/n8n_callback` не аутентифицирован** (main.py:3928 — регистрация
  роута): любой POST снаружи двигает сделки. Сегодня прикрыт только
  неизвестностью URL. Владельцу решать: секрет в заголовке/путь с
  токеном/IP-фильтр.
- **Матрица канала для алерта и архива (вторая колонка ОВ-2) не
  реализована и признана ненужной.** Причина: подписи каналов для
  менеджера требовали отдельного решения владельца (max/telegram/web —
  технические коды), а приёмка показала, что текущий вид алертов
  устраивает; отдельного поля канала в архиве NocoDB нет (замер колонок
  `mnivr6uyf5ckzru`), канал восстановим из `Final_Status`/стенограммы.
  Гипотеза-оговорка: если владелец вернётся к теме — предложение подписей
  лежит в переписке сессии 2026-09-02 (max→«MAX», telegram→«Telegram»,
  web→«Веб-чат») вместе с вопросом о призыве «свяжитесь с клиентом в
  MAX» (main.py:1032: без телефона он показывается у всех каналов,
  включая веб-чат, где связаться в MAX невозможно).
- Прочее открытое из хендоффа 2026-09-01 §5 (риск O4, расхождение версий
  Tilda, err 627 ProstoSMS, фоллоу-апы OTP-ревью) — без изменений.

## 8. Ловушки этой сессии

- `grep -r` по проекту через синхронизируемую папку Яндекс.Диска может
  молча не находить строки в `.env` — перепроверяй точечным `grep -c` по
  файлу.
- В тестах билдеров Bitrix: если после гейта в обновлении не остаётся
  полей, `crm.deal.update` не вызывается вовсе (main.py:411) — тестируй
  с нейтральным полем-довеском.
- `main.py` держит собственное имя `AsyncSessionLocal` с импорта
