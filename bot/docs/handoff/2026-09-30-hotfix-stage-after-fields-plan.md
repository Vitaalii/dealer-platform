# План срочного исправления для боя: смена стадии «Обогащение» после полей

Дата: 2026-09-30. Статус: **НЕ выкатывается** (решение владельца 2026-09-30) — исправление
`54dda75` выйдет вместе с веб-входом (ветка `feat/cabinet-web-entry`). План сохранён на случай,
если решение изменится.

## Проблема

Робот стадии «Обогащение» воронки 9 собирает «Текст письма (квалиф)» из полей сделки в момент
смены стадии и отправляет письмо дилеру. Кабинет ставит стадию раньше, чем пишет поля анкеты
(«SB Кредит …», «SB Трейдин …», «Кабинет: …»), поэтому письмо уходит с пустыми цифрами.

Живые сделки (проверено 2026-09-30, 890 сделок воронки 9, прошедших «Обогащение»):
- 52869 (Иваново, «Анкета трейд-ин») — «SB Трейдин» заполнены, в письме пусто: порядок записи;
- 51503 (Иваново, «Анкета трейд-ин») — порядок записи + «SB Трейдин» пусты и сейчас.

Затронуты только анкеты, отправленные из кабинета. Таймаут («Авторизация …»), путь через n8n
(колбэк, аварийный мост — поля и стадия одним вызовом) и чат по данным не затронуты.

## Пути смены стадии (прод 3.3.3 = `feat/multibot-brand-routing`, HEAD `d2e7489`)

| Путь | Порядок до исправления |
|---|---|
| Кабинет, сабмит | `_complete_handoff`: конверсия (`final_sync_wrapper` → `update_deal_data` со стадией) → `push_form_to_bitrix` |
| Кабинет, таймаут | конверсия со стадией → комментарий черновика |
| Чат без ИИ | `update_deal_data` со стадией → SB-поля трейд-ина из слотов |
| Охота | `update_deal_data` со стадией → `rebind_cabinet_on_merge` (переотправка анкеты) |
| Колбэк n8n, аварийный мост | поля и стадия одним `crm.deal.update` — гонки нет |

## Изменения

Ветка `hotfix/stage-after-fields` от `feat/multibot-brand-routing` (`d2e7489`). Перенос вручную
(коммит `54dda75` опирается на код веб-входа), без частей веб-входа.

`cabinet_service.py`:
- `setup(..., handoff_stage=None)`;
- `_set_handoff_stage(user_id, token_id, deal_id, platform_uid, fields_ok)` — стадия последней,
  однократно на сделку (гард-событие `handoff_stage`); поля ушли в очередь — стадия тоже в очередь;
- `_complete_handoff`: вызов после `push_form_to_bitrix` (ветка сабмита, `fields_ok = not
  outcome["enqueued"]`) и после комментария черновика (ветка таймаута).

`main.py`:
- `update_deal_data` возвращает признак успеха;
- `BitrixService.set_stage_after_fields(deal_id, stage, fields_ok, user_id)` — прямой вызов без
  своей постановки; неуспех или `fields_ok=False` — `enqueue_failed_request(..., skip_debounce=True)`;
- `final_sync_wrapper`: `update_deal_data` без стадии → SB-поля трейд-ина → `set_stage_after_fields`;
- `_cabinet_run_conversion`: `final_sync_wrapper(..., skip_stage=True)`;
- `setup_cabinet_service`: `handoff_stage=BitrixService.STAGE_QUALIFIED`;
- `background_deal_hunt`: `update_deal_data` без стадии → `rebind_cabinet_on_merge` →
  `set_stage_after_fields`;
- `replay_pending_sync`: `order_by(PendingSync.id)`; смена стадии сделки ждёт следующего прохода,
  если поля этой сделки в текущем проходе не дошли.

Тесты: перенести `tests/test_stage_after_fields.py` без веб-входа (кабинет — через токен чата),
поправить хелпер `_fields` в `tests/test_channel_field_gate.py` (отдельная смена стадии — последний
вызов). Объём кода ~90 строк. Миграций БД нет (новое событие — строка в `cabinet_events`).

## Риски

- Сделка на несколько секунд дольше остаётся в прежней стадии, пока пишутся поля; алерты
  дилеру в MAX не меняются.
- Незавершённые передачи на момент выката (без события `handoff_done`) при доведении новым кодом
  поставят «Обогащение» ещё раз; если сделка уже в «Отправлено», робот повторит письмо. Перед
  выкатом — проверить прод-БД чтением (только с разрешения владельца).
- Порядок реплея очереди меняется для всех записей Битрикса (только порядок и ожидание стадии).
- Битрикс не принимает поля — стадия приходит позже, с досылкой очереди, не раньше полей.

# Кандидат 2: чтения Битрикса в очереди досылки

Дата: 2026-10-02. Статус: **не выкатывается** (решение владельца 2026-10-02) — исправление
`6eb8d6f` выйдет с релизом веб-входа (ветка `feat/cabinet-web-entry`).

## Проблема (прод 3.3.3, проверено чтением кода, без правок)

`BitrixService._request` после трёх неудачных попыток ставит вызов в `pending_sync`
(`enqueue_on_failure=True` по умолчанию), проверки «чтение или запись» нет. В очередь попадают:

- `crm.deal.get` — `get_deal_by_id` в `final_sync_wrapper`;
- `crm.deal.list` — `find_deal_data_by_code`: `final_sync_wrapper`, `check_and_link_deal` (старт
  каждого диалога с кодом), `background_deal_hunt` (8 попыток по 15 мин);
- `crm.contact.list` — поиск контакта по телефону в `create_deal_with_contact`.

От дублей — только 30-секундный дебаунс на пару «пользователь + метод». Кабинет на бою ставит
в очередь только записи.

Пока Битрикс доступен, реплей повторяет чтение и выбрасывает результат — вреда нет. При долгом
сбое Битрикса строки доходят до `PENDING_SYNC_MAX_ATTEMPTS` (10) и уходят в fatal, по техалерту
на каждую строку. На дев-стенде так набралось 1380 строк и 147 алертов (2026-10-01…02).

## Изменения (как в `6eb8d6f`)

- `main.py`: `is_bitrix_read_method(method)` — суффикс `list`/`get`/`fields`;
  `enqueue_failed_request` не ставит чтение (предупреждение в лог) — единая точка для чата
  и кабинета (`_enqueue_nodebounce`).
- `replay_pending_sync`: при пустом `BITRIX_WEBHOOK_URL` проход пропускается целиком
  (на бою адрес задан — поведение не меняется).
- Тесты: `tests/test_pending_sync_reads.py`.

Перед выкатом (если решение изменится): прод-БД чтением — сколько строк `*.list`/`*.get` в
`pending_sync`; удалить их — только по команде владельца.

## Что на бою 3.3.3 (чтение кода, без правок)

`create_deal_with_contact` (`main.py:619`): `deal_id = str(res_d.get('result'))` — пустой ответ
Битрикса превращается в строку «None». Дальше:

1. **Очередь.** `_request` после трёх неудачных попыток ставит `crm.deal.add` в `pending_sync`
   (дебаунс 30 с на пару «пользователь + метод»). Реплей позже создаст сделку, но её ID никуда
   не записывается — к диалогу она не привязывается. Контакт: если `crm.contact.add` тоже не
   прошёл, он ставится в очередь отдельно, а сделка из очереди создаётся без `CONTACT_ID`
   (ключ с `None` отфильтрован) — сделка без телефона, контакт отдельно.
2. **Диалог.** `active_deal_id = "None"`. Охота (`background_deal_hunt("None", …)`) запускается:
   если в течение 2 ч находит сделку Tilda по коду в «Новой» — пишет в неё данные воронки
   (снапшот на момент запуска, без итогов ИИ), `sync_dialog_deal_refs` переводит
   `active_deal_id` с «None» на оригинал. Не нашла — `move_to_manual("None")` без эффекта.
3. **ИИ и передача.** До перепривязки агент n8n получает `deal_id: "None"`; `finalize_deal` →

   обращения», SB-поля, телефон в контакте и стенограмма в таймлайн в CRM не попадают.
   Карточка дилеру в MAX уходит (при телефоне), с «ID Сделки: None». Архив NocoDB — `Deal_ID`
