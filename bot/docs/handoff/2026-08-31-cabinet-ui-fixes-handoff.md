## 3. Установлено измерением (не из документации)

Факты этой сессии, добытые кодом/запросами. Помечено ⚠ — опровергло прежнее
предположение.

**Про гейт выката `63646c8`:**
- Коммит `63646c8` (2026-08-08, «init_db переживает PostgreSQL») меняет
  механизм применения схемы: каждый DDL — своя транзакция, инспектор вместо
  ожидаемых падений, «✅» только после проверки полноты. Он на
  `origin/feat/cabinet-calculator`, в основании текущей ветки (44 коммита ниже
  HEAD на момент разбора). В `main` его нет — `main` состоит из одного
  baseline-коммита `7305eb1`, вся работа живёт на фиче-ветках.
- Прод-копии `../unifiedbot_prd_ong_3.1.2` и `../unifiedbot_prd_stb_3.1.0` —
  НЕ git-репозитории; в их `main.py` кабинета нет, в `database.py` — старый
  однотранзакционный `init_db` с легаси-`RENAME` первым ALTER
  (`unifiedbot_prd_ong_3.1.2/database.py:54,58`).
- **Вывод (принят владельцем): отдельный выкат `63646c8` не нужен** — любой
  выкат кабинета автоматически его содержит; гейт актуален только для правки
  схемы прода в обход кабинет-ветки.
- ⚠ Допущение «прод-PostgreSQL ещё нет» опровергнуто владельцем: прод бота
  работает на PostgreSQL, база существует; но таблиц `cabinet*` в ней нет
  (проверено запросом из прод-контейнера) — схема кабинета создастся с нуля,
  миграции не нужны.

**Про код до правок (основание плана):**
- ⚠ Точек вызова `trigger_sms_fallback` в проде было две, не три: колбэк и
  страховочный таймаут; третья («ручной запрос») существовала только в
  докстринге и тестах.
- ⚠ `sms_msg_id` — не фолбэк-хвост: её пишет первичная SMS-отправка и по ней
  колбэк матчит SMS-записи (в текущем коде — `database.py:113`, матчинг в
  `process_status_callback`). Первая версия плана ошибочно записала её в
  удаляемые; исправлено до реализации.
- `check_secrets` проверяет только `CABINET_HMAC_KEY` — ни `PROSTOSMS_API_KEY`,
  ни (уже удалённую) `PROSTOSMS_SENDER_NAME` он не проверял и не проверяет.

**Из код-ревью (11 ревьюеров + валидаторы), главное:**
- **P1, воспроизведён эмпирически:** база, созданная схемой до `bc7ed47`,
  несёт `fallback_attempts INTEGER NOT NULL`; новая модель колонку не передаёт
  → каждая вставка OTP падает `NOT NULL constraint failed`, а обработчик гонки
  в `request_code` маскировал ЛЮБУЮ `IntegrityError` под 429 «попробуйте
  позже». Исправлено в `000a48b`: `init_db` удаляет легаси-колонки по карте
  `SCHEMA_COLUMN_DROPS` (`database.py:297`), 429 отдаётся только по индексу
  `uq_cabinet_otp_inflight_token`, прочие `IntegrityError` всплывают.
  Регрессионный тест — `tests/test_legacy_schema_upgrade.py`.
- SQLite (3.45.1) не умеет `DROP COLUMN` для UNIQUE-колонки — поэтому
  `sms_external_id` НЕ удаляется на легаси-базах (nullable, вставкам не
  мешает; комментарий `database.py:294-296`).
- Кап дилера `CABINET_DEALER_DAILY_CAP=0` (kill-switch) ронял бы
  `request_code` с TypeError на пустом `min(sent_at)` — исправлено, тест
  `test_dealer_cap_zero_is_kill_switch_not_crash`.
- Фронтовые гонки (все валидированы независимыми агентами и исправлены):
  инлайн-429 не перезапускал отсчёт повтора; `#cab-code-error` — DOM-сосед
  `#cab-auth-body`, перезапись последнего баннер не чистит; отклонённый нашим
  лимитом запрос смены канала мутировал `state.channel` до fetch — полинг
  обещал «звонок выполняется» без звонка.
- Транспорт-ошибка `ProstoSmsGateway` возвращается результатом (`SendResult`),
  не исключением — подтверждено интеграционным тестом с реальным шлюзом на
  недоступный адрес (`tests/test_cabinet_wiring.py`).

**Миграция дев-базы (2026-08-28):**
- До: все три легаси-колонки на месте, `fallback_attempts notnull=1`;
  34 строки `cabinet_otp`, 31 токен. После `init_db`: `fallback_at` и
  `fallback_attempts` удалены, данные целы (`PRAGMA integrity_check` = ok).
- Живой прогон после миграции: `POST /cabinet/api/auth/request-code` →
  HTTP 200 `{"status":"ok","retry_after":30}`, `send-status` → `sent`,
  строка `cabinet_otp id=35 status=sent` — вставка, которая до фикса падала.
- ⚠ **`ix_cabinet_otp_phone_channel` на дев-базе НЕ создан**: индекс объявлен
  на модели (`database.py:101`), а `create_all` не добавляет индексы к уже
  существующим таблицам. По указанию владельца на месте не чинил. Влияние —
  только скорость лимитных выборок по номеру (строк десятки). То же ждёт
  любую легаси-базу.
- Дев-базу держали 6 осиротевших инстансов `main.py` из прежних агент-сессий
  (часть запущена системным Python, `pgrep venv/bin/python` их не видит) —
  остановлены перед миграцией.

## 4. Открыто и не решено

Ждут решения владельца:
- Чинить ли `init_db`, чтобы он создавал `ix_cabinet_otp_phone_channel` на
  существующих таблицах (перенести в идемпотентный DDL-список рядом с
  `SCHEMA_PARTIAL_UNIQUE_INDEXES`), или пренебречь до пересоздания баз.
- Фоллоу-апы код-ревью, осознанно отложенные. В документах репозитория этот
  список нигде больше не зафиксирован (в `docs/residual-review-findings/`
  лежат находки других фич) — полный перечень:
  - Агентная паритетность: бот не видит суточные 429-тупики клиента —
    `cabinet_status` отдаёт `not_visited` для застрявшего в лимите на сутки;
    кандидат — состояние `rate_limited`/`stuck_send` или событие
    `send_limited` с `limit_source`.
  - Перевыдача ссылки бесполезна при `limit_source=phone` (лимит привязан к
    номеру), но бот об этом не знает и его стандартное средство помощи
    молча не работает.
  - UX: полноэкранный 429 по номеру при первичной отправке звонка — тупик на
    10 минут, путь «получить код в SMS» с этого экрана недоступен (SMS при
    этом разрешена лимитами).
  - Тесты точных границ окон: ровно 10 мин для голосового лимита, ровно 24 ч
    для суточных SMS-лимитов; граница 24-часового окна сверки мёртвых кодов
    в `verify_code`.
  - aware_db-варианты для суточных SMS-лимитов (ссылка/номер) и капа дилера —
    сейчас на aware-фикстуре гоняются только голосовое окно и мёртвые коды.
  - Явный ассерт, что неуспешная отправка (`failed_send`) не входит в кап
    дилера — поведение верно по коду, но не закреплено тестом.
  - Лимиты по номеру не атомарны при конкурентных запросах с разных токенов
    (check-then-insert без блокировки по номеру) — класс известного остатка
    однопроцессности; при переходе на несколько реплик пересмотреть.
  - Тест сброса лимита «2 SMS на ссылку» при перевыдаче токена (R19-исключения)
    с проверкой по строкам таблицы — урок
    `docs/solutions/integration-issues/token-idempotency-verified-by-table-rows.md`.
  - Легаси-колонка `sms_external_id` остаётся на старых SQLite-базах (SQLite
    не дропает UNIQUE-колонку) — безвредна, уйдёт с пересозданием базы.
  - Честный `retry_after` дилерского капа — слабый кросс-арендный оракул
    активности дилера для любого держателя ссылки (security P3, принят);
    вариант — огрубить `retry_after` для `limit_source=dealer`.
- Отклонённая находка ревью (решение владельца оставить как есть): `voiceUsed`
  прячет «Получить код звонком» до перезагрузки страницы, хотя бэкенд-окно —
  10 минут; R13 сформулирован как «одноразовая в пределах сессии страницы».

Гипотезы, не проверено:
- Механизм выката кода в прод-контейнер Dockhost (сборка образа вручную из
  прод-директории?) — в репозитории не описан, знает только владелец.
- Какая из прод-копий (`prd_ong_3.1.2` / `prd_stb_3.1.0`) соответствует
  живому контейнеру.

Прод-блокеры перед включением трафика (вне кода):
- Живые прогоны владельцем из прод-контейнера: SMS + звонок БЕЗ `sender_name`
  (если провайдер отобьёт push_msg без имени — эскалация в поддержку);
  посимвольная сверка SMS-текста с шаблоном в ЛК провайдера; проверка по
  операторам.
- Env прод-контейнера: удалить `PROSTOSMS_SENDER_NAME` и
  `CABINET_FALLBACK_TIMEOUT` (код их больше не читает).
- Прогон набора на дев-PostgreSQL (`TEST_DATABASE_URL`) — новые лимитные окна
  делают обязательным.
- Прежние: дизайн Tilda и UF-поля, тексты юриста, промпт NocoDB, ротация
  секретов ProstoSMS/ngrok.

## 5. Ловушки репозитория (натыкался в этой сессии)

- `create_all` не добавляет индексы существующим таблицам — новый индекс на
  модели молча отсутствует на легаси-базах.
- SQLite не дропает UNIQUE-колонку — `ALTER ... DROP COLUMN` падает.
- Осиротевшие `main.py` держат SQLite-базу; часть запущена системным Python —
  искать `lsof <файл базы>`, а не `pgrep venv`.
- Grep-тесты фронта (`tests/test_cabinet_frontend.py`) пиновают точные строки
  `app.js` — рефакторинг формы строки роняет тест при живом поведении.
- Текст SMS-шаблона в `sms_gateway.py` набран escape-последовательностью
  `—` намеренно (видимость подмены тире в диффе); менять только вместе с
  перерегистрацией шаблона у провайдера.
- `DevLogGateway` включается `CABINET_OTP_DEV_LOG=1` и недоступен при
  `ENVIRONMENT=production`. Факт: запрос `get_profile` к ProstoSMS с машины
  владельца 2026-08-31 вернул `err_code=627`. **Причина не установлена** —
  два варианта: незарегистрированный у провайдера исходящий IP машины либо
  несовпадение ключа в `.env` дев-стенда с ключом прод-контейнера. Проверки,
  которые не делались: сверить внешний адрес машины с подсетью, заявленной в
  поддержку провайдера (заявлена 45.92.179.192/28,
  `docs/plans/2026-07-31-001-context.md`); сравнить значение ключа в `.env`
  дев-стенда со значением в прод-контейнере (значения — не в документы).
- Все сравнения времени — только через `_utcnow()`/`_aware()`; naive-значения
  зелёные на SQLite и ломаются на PostgreSQL (два урока в
  `docs/solutions/database-issues/`).
- Одноразовые скрипты с `database.engine` не завершаются без
  `await engine.dispose()` — процесс висит и держит базу.
