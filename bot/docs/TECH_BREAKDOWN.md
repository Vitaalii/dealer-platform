# UnifiedBot (MAX Messenger Edition) — Deep Tech Breakdown

## 1. Ядро приложения и Сетевой слой (Core Engine)
Бэкенд написан на Python с использованием асинхронного фреймворка `aiohttp`. Приложение работает как монолитный веб-сервер, обрабатывающий высокие нагрузки в режиме non-blocking.

**Global Error Middleware:** Любое необработанное исключение на сервере перехватывается `@web.middleware`. Система не просто логирует ошибку, но и автоматически формирует алерт с traceback-кодом и отправляет его в выделенную группу техподдержки MAX (`TECH_ADMIN_ID`), возвращая серверу статус 500 для повторной попытки.

**Многоканальный транспортный слой:** Вместо единственного `MaxBotClient` реализована иерархия клиентов на базе абстрактного класса `BaseBotClient` (`base_client.py`). Три реализации: `MaxBotClient` (MAX), `TelegramBotClient` (Telegram), `WebBotClient` (веб-виджет). Роутер `get_client(channel)` выбирает нужный клиент по каналу из контекста сессии. Алерты дилерам и технические алерты всегда идут через `max_client` напрямую.

**MAX API Client (`max_client.py`):** Кастомная обертка над REST API мессенджера MAX.
- Поддерживает отправку текстовых сообщений, inline-кнопок и специальных системных кнопок (например, `request_contact`).
- Реализует метод `remove_inline_keyboard`: при клике на кнопку отправляется PUT-запрос с пустым массивом `attachments`, что визуально "схлопывает" кнопки у клиента для чистоты истории чата.

**Фильтр устаревших вебхуков:** Входящие события MAX проверяются по полю `timestamp`. Если событие опоздало более чем на 60 секунд (например, застрявший в очереди `bot_started`), оно игнорируется с записью в лог. Это предотвращает ложные срабатывания логики перехвата при повторной доставке старых событий.

## 2. База данных и управление состоянием (State & Context)
Используется асинхронная алхимия (`sqlalchemy.ext.asyncio`) с PostgreSQL (прод) / SQLite (дев). Подключение определяется переменной окружения `DATABASE_URL`. База хранит минимально необходимый стейт, оставляя тяжелые данные (массивы авто) в оперативной памяти (Context).

**Защита от Race Condition (`get_or_create_user`):** При одновременном поступлении нескольких сообщений от нового пользователя используется перехват `IntegrityError` с автоматическим откатом (`rollback`) транзакции и повторным чтением. Это предотвращает дублирование записей.

**USER_CONTEXT (In-Memory + DB Sync):**
- Все бизнес-данные сессии (платеж, госномер, выбранная модель, стенограмма `chat_history`) живут в оперативной памяти словаря `USER_CONTEXT`.
- При каждом изменении контекст сериализуется в JSON и синхронизируется с полем `context_json` в БД для отказоустойчивости при перезагрузке сервера.
- **Обрезка `chat_history`:** При сохранении через `save_context_to_db` массив истории обрезается до последних 100 записей (на копии контекста). Полная стенограмма всегда доступна в Bitrix24 и NocoDB. Это предотвращает неограниченный рост `context_json` в БД.
- **Очистка из памяти:** После финальной архивации сессии (`finalize_transcript_archive` или DF-архивация) запись удаляется из `USER_CONTEXT` через `pop()`. При повторном обращении контекст восстанавливается из БД через `load_context_from_db`.

**Многоканальный контекст:** Поле `channel` в `USER_CONTEXT` и в БД (`User.channel`) определяет транспорт для всех исходящих сообщений. Устанавливается при первом входящем событии через соответствующий webhook-хэндлер (`handle_max_webhook`, `handle_tg_webhook`, `handle_chat_message`). Для веб-канала идентификатором пользователя служит `session_id` (числовая строка `Date.now()`).

**Управление ИИ-режимом (`is_smartbot_active`):** Флаг в БД. Если `False` — сообщения летят в NLU (Dialogflow). Если `True` — перенаправляются в n8n.

## 3. Модуль защиты и безопасности (Security & Anti-Spam)
Реализован технический антиспам на уровне ядра приложения (`process_input`):

**Счетчик (Rate Limiting):** Отслеживается количество сообщений в 60-секундном окне (`spam_control`).

**Глухой Бан (Time-out):** Если клиент отправляет более 10 сообщений в минуту, бот выдает предупреждение, принудительно отключает ИИ-агента (`is_smartbot_active = False`) и блокирует обработку любых сообщений от пользователя на 15 минут (900 секунд).

## 4. Оркестрация ИИ и Транспорт данных (AI Handoff & Debounce)
Самый сложный модуль, отвечающий за бесшовную передачу клиента от кнопочного бота к n8n-агенту.

**Динамическая сборка Промптов:** При старте сервера бот скачивает из NocoDB сырые блоки промптов, оборачивает их в XML-подобные теги (например, `<ROLE>...</ROLE>`), склеивает базовые (General) и сценарные блоки, после чего кэширует в `PROMPTS_CACHE`. Готовый промпт передается в n8n в теле вебхука.

**Буферизация ввода (Debouncing):** Люди часто пишут сообщения кусками ("Привет" → "Сколько стоит").
- Используется `asyncio.create_task` с задержкой 10 секунд (3 сек ожидания + активация тайпинг-индикатора + 7 сек).
- Если в течение этого времени приходит новое сообщение, старый таймер отменяется (`cancel()`), а текст склеивается с предыдущим.
- В n8n уходит один большой, осмысленный текст.
- Тайпинг-индикатор (`TYPING_ON`) активируется через 3 секунды ожидания и держится до момента отправки запроса в n8n.

**Тип ввода (`input_type`):** Каждое входящее событие классифицируется перед передачей в ядро:
- `"text"` — обычное текстовое сообщение (`message_created`)
- `"button"` — нажатие кнопки (`message_callback`)
- `"deeplink"` — переход по стартовой ссылке (`bot_started`)

Классификация используется в логике перехвата возражений: события типа `"deeplink"` не интерпретируются как текстовые возражения клиента.

**Каскадный Фолбэк ИИ (Long Retry System):** Если n8n не отвечает:
1. Таймаут 90 сек: ожидание первичного ответа.
2. Проверка телефона: если номер уже есть — извиняемся, отключаем ИИ, переводим сделку менеджеру.
3. Ожидание 180 сек: если телефона нет, бот пишет "вернусь через пару минут" и повторяет вызов.
4. Финальный сброс: если вторая попытка упала — просит номер для ручного звонка.

## 5. Интеграция с Bitrix24 (CRM Engine & Deal Hunt)
Модуль обеспечивает 100% доставку лида в CRM даже при задержках со стороны сторонних систем.

**Охота за дублями (Background Deal Hunt):**
- Сайт может передать лид в Битрикс с задержкой. Бот проверяет CRM при старте (`bot_started`).
- Если оригинальной сделки нет — бот создаёт временную, чтобы менеджер мог начать работу.
- Параллельно запускается фоновая корутина `background_deal_hunt`: 8 попыток × 15 минут = 2 часа.
- Как только сайт досылает оригинал, бот склеивает данные и закрывает временную сделку как дубль.

**Архивация Стенограмм (Transcript Sync):**
- Массив `chat_history` накапливает каждое сообщение (роли: `system`, `user`, `bot`).
- При финализации массив форматируется в BBCode и отправляется в `crm.timeline.comment.add`.

### Автоматический подшив внешних и внутренних логов (Deep Logging)
Перед отправкой payload в таблицу `Dialogues_Archive` (NocoDB) выполняются две операции обогащения данных:
1. Вызывается `fetch_n8n_logs_for_archive` — получает детальный JSON-лог выполнения нод n8n с Dockhost по ID сессии (таймаут 10 сек, заглушка `"no_n8n_data"` при недоступности).
2. Извлекается массив `python_logs` из контекста текущей сессии.
Оба лога сохраняются в текстовые поля записи архива, обеспечивая 100% прозрачность отладки LLM и бэкенда из единого интерфейса NocoDB.

### Архивация Dialogflow-диалогов (DF Archive)
Диалоги, завершённые на уровне кнопочной воронки Dialogflow (без передачи в n8n), архивируются немедленно в момент финализации (ветка B). Поле `Final_Status` заполняется динамически:
- `"По телефону"` — клиент оставил номер через кнопку `request_contact`
- `"В MAX"` — клиент выбрал мессенджер
- `"refuse"` — нажал "НИЧЕГО НЕ НУЖНО"
- `"other_model"` — выбрал другую модель
- `"DF_Finalized"` — иные сценарии завершения

Сессия маркируется флагом `is_finalized = True`, после чего запись удаляется из `USER_CONTEXT`.

**Сборщик брошенных диалогов (Sync Worker):**
- Воркер просыпается каждые 30 минут и сканирует всех пользователей с активной сделкой.
- Условие архивации: есть новые сообщения (`len(history) > nocodb_synced_index`) И прошло более 30 минут тишины И сессия не финализирована.
- После успешной архивации курсор `nocodb_synced_index` обновляется и массив `python_logs` очищается. Курсор обновляется строго внутри блока архивации — не безусловно.

### Защита от гонок и дублирования данных (Idempotency Filter)
Маркер `is_finalized` предотвращает двойную архивацию при параллельном закрытии диалога ИИ-агентом и фоновым воркером. `sync_worker` пропускает пользователей с `is_finalized == True`.

**Отказоустойчивая Очередь (PendingSync):** При ошибке 5xx от Битрикса запрос сериализуется в БД. `sync_worker` повторяет попытки каждый час.

## 6. Внешние базы данных (NocoDB Data Warehouse)
Система динамически переключает базы и таблицы на основе кода дилера из Deep Link.

- При старте скачивается конфигурация (`CACHED_DEALERS`) с ID таблиц и `Max_Group_ID`.
- Каталог авто кэшируется в `DICT_STOCKS` на 10 минут (`CACHE_TTL`).
- Все завершённые диалоги складываются в архив через `upsert_dialogue_archive` (Smart Upsert: `POST` при создании, `PATCH` при обновлении).

## 7. Автономный CRM-перехватчик (Fallback Bridge) и режим Manager
При `comm_type == "Manager"` ядро перестраивает логику финала:
- Текст заменяется на `"Принято! Ваш запрос отправлен специалисту ⚡"`
- Инлайн-клавиатура блокируется (`kb = None`)
- Сессия немедленно переходит в `AI_HANDOFF`

Если в тексте ответа ИИ обнаруживаются теги `<function_calls>`, но вебхук финализации от n8n не поступил — включается аварийный мост: Python самостоятельно выполняет `crm.deal.update`, переводя сделку на нужную стадию на основе внутренней карты смарт-полей.

## 8. Веб-виджет и SSE-транспорт (Web Widget)

**Кастомный виджет:** Файлы `widget-custom/widget.js` + `widget-custom/avatar.jpg` раздаются статически из Python-бота. `BOT_URL` динамически задаётся через `window.UNIFIEDBOT_URL` на странице Tilda.

**Архитектура SSE (Server-Sent Events):**
- Виджет открывает соединение на `GET /chat_stream/{session_id}`.
- Бэкенд держит соединение через `asyncio.wait_for` в цикле чтения из `asyncio.Queue`.
- Keepalive-ping (`data: ping`) отправляется каждые 30 секунд для предотвращения разрыва соединения.
- Виджет использует `fetch + ReadableStream` вместо нативного `EventSource` — `EventSource` не поддерживает кастомные заголовки (необходимы для ngrok и авторизации).
- При сворачивании чата SSE-соединение сохраняется (FAB восстанавливает сессию без переподключения).

**Каталог-прокси:**
- Эндпоинты `GET /catalog/{dealer_code}` и `GET /catalog-colors` проксируют запросы к NocoDB.
- NocoDB-токен никогда не передаётся в браузер — только через серверный прокси.
- CORS-middleware добавляет нужные заголовки ко всем ответам.

**Особенности веб-канала:**
- `WebBotClient.supports_contact_button()` → `False`: кнопка `request_contact` не используется, телефон собирается через regex-перехватчик.
- `WebBotClient.supports_reminders()` → `False`: ремайндеры и TTL-farewell не отправляются.
- При финализации сессии в очередь помещается событие `{"type": "chat_close"}` — виджет закрывает чат.
- Typing-индикатор реализован через `{"type": "typing_on"}` в очереди + задержка `_web_delayed_typing`.
