# AI_HANDOFF.MD: Технический паспорт системы UnifiedBot (MAX Edition v2.0)

**Current Version:** v2.0 (MAX Messenger API)
**Architecture:** Модульный монолит `main.py` (Aiohttp Webhook Server) + `database.py` (SQLAlchemy Async).
**Routing Model:** Strict Deep Link Routing. Маршрутизация мульти-дилеров основана строго на 6-значном коде из Payload.

## 🚨 Critical: Упразднение Топиков и Telegram
В версии 2.0 произведен полный отказ от Telegram Business API и таблицы `dealer_connections`. 
Живое общение сведено к минимуму. Уведомления менеджерам теперь приходят в виде **системных алертов** в группы мессенджера MAX через метод `max_client.send_alert_to_group()`. 
Идентификация пользователей в БД ведется исключительно по строковому полю `max_user_id`.

## 1. Архитектурный обзор
Система представляет собой асинхронный веб-сервер на базе `aiohttp`, выступающий интеллектуальным шлюзом между мессенджером MAX, NocoDB и Bitrix24.

**Ключевые компоненты:**
- **MAX Webhook API:** Обработка входящих событий (`bot_started`, `message_created`, `message_callback`).
- **Dialogflow ES:** NLU-движок для классификации намерений и сбора параметров (платеж, госномер).
- **Bitrix24 REST API:** Фоновое управление сделками (очередь PendingSync).
- **SQLite (SQLAlchemy):** Хранение профилей пользователей (`max_user_id`, `active_deal_id`, `context_json`).
- **NocoDB (Multi-Table):** Внешняя база данных. Хранит ключи `Max_Group_ID` для отправки уведомлений, а также настройки для AI-агентов (`Program_Table_ID`, `Rates_Table_ID`).

## 2. Логика связки и жизненный цикл сделки

### 🔗 Инициализация и привязка (Linking)
Процесс начинается с детекции Кода заявки (regex: `КОД ЗАЯВКИ:\s*([a-zA-Z0-9а-яА-Я]+)`).
- **Поиск в Bitrix:** При получении кода бот ищет сделку в стадии C9:NEW.
- **Жесткая фиксация:** Найденный ID записывается в локальную БД (users.active_deal_id). Это критично: все последующие обновления данных (платеж, госномер, телефон) отправляются строго по этому ID, что исключает дублирование.
- **Управление стадиями:** После связки сделка переводится в STAGE_SUCCESS.

### 🕵️‍♂️ Охота за сделками (background_deal_hunt)
Если сделка не найдена сразу (задержка сайта), запускается фоновая задача:
1. Делает 3 попытки поиска с интервалами 120, 240 и 360 секунд.
2. In case of success links data, in case of failure — moves temporary deal to STAGE_MANUAL.

### 🚫 Двухэтапная логика отказов (v1.17 Reference)
Внедрена строгая защита от преждевременного закрытия сделок ("Нет, не актуально" != "Отказ").

**Этап 1: Промежуточный (Навигация)**
- **Триггер:** Интент `09_Refusal_NoNeed`.
- **Действие:** Бот предлагает альтернативы ("Авто в наличии", "Другая модель").
- **Статус сделки:** НЕ меняется. `is_final_step = False`. Сделка остается активной.

**Этап 2: Финальный (Закрытие)**
- **Триггеры (Strict Match):**
  1. Текст строго: `"НЕ НАДО звонить/писать"`
  2. Текст строго: `"НИЧЕГО НЕ НУЖНО"`
  3. Текст строго: `"ДРУГАЯ МОДЕЛЬ"`
  4. Интент: `93_Refusal_Final`
- **Действие:** 
  1. `is_refusal = True`, `is_final_step = True`.
  2. Сделка переводится в стадию **C9:LOSE** (Отказ).
  3. **Обязательные обновления:**
     - `F_TYPE` -> "Отказ" или "Другая модель".
     - `F_SITE_SOURCE` -> Сохраняется (если есть код).
     - `active_deal_id` -> **Сбрасывается в None** (Hard Reset сессии).

## 3. Логика управления шлюзом (v1.39 Multi-Channel)

**Multi-Channel Architecture:**
Теперь каждый пользователь может иметь несколько активных диалогов с разными дилерами одновременно. Связь хранится в таблице `dealer_connections`.

### Алгоритм маршрутизации (Smart Routing)
1. **Code Input:** Пользователь вводит код -> Бот создает/обновляет запись в `dealer_connections` -> Эта связь становится "Активной".
2. **Text Input:** Бот находит **самую свежую** запись в `dealer_connections` (сортировка по `updated_at DESC`). Сообщение уходит в топик этого дилера.
   - *Failover:* Если отправка в топик не удалась (Topic dead), бот помечает запись как неактивную (`topic_id = NULL`) и останавливает маршрутизацию (Safety Stop).

### Deprecated Legacy Fields (v1.39.2)
"Legacy fields `support_group_id` and `business_connection_id` in Users table are now STRICTLY IGNORED for notification routing. The bot enforces a Fail-Fast policy: if no valid Group ID is found in the context (derived from DealerConnection or Cache), notification is blocked."

### Logging Trace (v1.39.1)
Use these logs to verify routing path:
1. `🌪 [BG] Thread {id} identified connection for dealer {code}: Group {id}` (Worker identification)
2. `📣 ROUTING REPORT: Dealer {code} -> Target Group {id} (Topic: {id})` (Manager Notification)

### Обратная связь (Manager -> User)
Менеджер отвечает в топике. Бот ищет получателя **строго по topic_id** в `dealer_connections`. Это гарантирует, что ответ уйдет от имени правильного бизнес-аккаунта (Business Connection ID).

Режим "Шлюза" (когда бот пересылал сообщения менеджеру 1-к-1) **удален**. Теперь обслуживание делится на 2 автономных трека в зависимости от поля `Communication_Type` в NocoDB:

1. **Режим Call (Авто-диспетчер):** Бот отсекает кнопки перехода в мессенджер, форсирует сбор номера телефона, создает карточку-алерт с призывом "☎️ Перезвоните клиенту" и завершает сессию.
2. **Режим Smartbot (AI Agent):** После сбора параметров бот замораживает Dialogflow, формирует JSON с контекстом (`qualification_context` + `data_routing`) и передает диалог во внешний оркестратор n8n через Webhook.

- **Синхронизация:** Номер обновляется в объекте db_user мгновенно для корректной передачи в метод update_contact.

## 5. Интеграция с Bitrix24 (Field Mapping)


| Поле в коде | Описание | Источник в боте |
|---|---|---|
| F_CODE | Код заявки | ctx['start_code'] |
| F_PAYMENT | Сумма платежа | ctx['payment'] |
| F_TRADEIN | Госномер авто | ctx['plate'] |
| F_TYPE | Тип сценария | Маппинг через _map_type() |
| F_CHANNEL | Канал связи | "В Telegram" / "По телефону" |
| F_SITE_SOURCE | Сайт дилера | Поиск по префиксу кода в NocoDB |

**Важно:** Для консистентности данных, ссылка на сайт в чате (теги `[website]`, `[СЮДА_ВСТАВЬТЕ_ВАШ_САЙТ]`) и поле `F_SITE_SOURCE` в CRM берутся из **одного источника** — кэша NocoDB по префиксу Кода Заявки.

**Важно:** Телефон передается в Bitrix в формате множественного поля: `fields["PHONE"] = [{"VALUE": phone, "VALUE_TYPE": "WORK"}]`.

### 🛡 Отказоустойчивость (Retry Mechanism v1.27)
Для защиты от сетевых сбоев метод отправки данных в Bitrix24 (`_request`) оснащен автоматической системой повторов:
- **Количество попыток:** 3.
- **Стратегия (Backoff):** 
  1. Попытка №1: Мгновенно.
  2. Попытка №2: Через 1 секунду (если первая упала).
  3. Попытка №3: Через 3 секунды (если вторая упала).
- **Триггеры:** Любая сетевая ошибка или JSON-ответ, содержащий ключ `error`.
- **Failure:** Если после 3 попыток отправка не удалась, бот записывает ошибку `[Bitrix FATAL]` в лог и **не создает задачу** для менеджеров (данные не отправляются в топик).

### 🛡 Таблица 6: Гарантированная доставка (Persistence Queue v1.28)
Если Retry-механизм не справился (например, Bitrix лежит более 5 секунд), заявка попадает в очередь:

| Этап | Механизм | Длительность | Действие при сбое |
|---|---|---|---|
| **1. Retry** | In-Memory Async | 5 сек | Переход в Queue |
| **2. Queue** | SQLite (PendingSync) | 24 часа | Алерт в TECH_GROUP + Повтор раз в 10 минут |
| **3. Fatal** | Dead Letter | ∞ | Финальный Алерт + Статус 'fatal' |
 
 **Оптимизация (v1.28.1):** 
 1. Финальный запрос в CRM выполняется в фоне (`asyncio.create_task`), не блокируя ответ пользователю.
 2. Технические алерты изолированы в отдельную группу `TECH_ADMIN_ID`.
 
 **Воркер (Sync Worker):**
 - Запускается в фоне при старте бота.
 - Проверяет очередь каждые 1 час (3600c).
 - Удаляет задачу только после **успешного** ответа от Bitrix (200 OK).
 
 **Оптимизация мониторинга (v1.28.7):** Система переведена в режим «максимальной тишины» для предотвращения усталости от уведомлений (alert fatigue).
- **Мгновенные алерты:** Полностью отключены в методе `_request`. Теперь `enqueue_failed_request` выполняет только запись в SQLite без отправки сообщений в Telegram.
- **Smart Monitoring:** Оповещения делегированы фоновому воркеру `sync_worker`.
- **Интервал:** Проверка очереди происходит раз в 1 час (3600 сек).
- **Условие отчета:** Суммарный отчет в тех. канал (`-5081268491`) отправляется только при наличии записей в очереди. Если проблемных заявок нет — воркер работает бесшумно.

## 6. Логика динамических стоков (v1.26.1)

### 📈 Этап 1: Определение дилера (Routing Strategy)
Система не использует единую таблицу с машинами. Таблица определяется в рантайме:

1. **Priority 1 (Lead Code):** Если в `USER_CONTEXT` есть код заявки, бот берет первые 2 цифры (префикс). В словаре `CACHED_DEALERS` производится поиск дилера с соответствующим кодом.
2. **Priority 2 (Business Connection):** Если кода нет, бот использует `business_connection_id` текущего сообщения для поиска дилера.
3. **Fallback:** Если дилер не определен, используется ID по умолчанию из `NOCODB_TABLE_ID_CARS`.

### 🔄 Этап 2: Умное кэширование (Smart TTL Caching)
Для минимизации запросов к NocoDB используется механизм `DICT_STOCKS`:
- **Структура:** `{table_id: [список машин]}`
- **TTL (Time-To-Live):** 600 секунд (10 минут).
- **Логика:** При запросе данных бот проверяет `STOCK_LAST_UPDATED`. Запрос к API выполняется ТОЛЬКО если кэш устарел или пуст.

### 💉 Этап 3: Асинхронная инъекция (Async Injection)
Функция `inject_prices_and_capture_model` переведена в асинхронный режим. Она:
1. Определяет целевую таблицу (`target_table_id`) по логике Routing.
2. Асинхронно получает список машин через `get_cars_from_nocodb_dynamic(target_table_id)`.
3. Ищет модель внутри полученного списка для обогащения ответа ценами.

## 7. Работа с персоналом (Support Group)

### Forum Topics & Topic Reuse
Бот создает тему в супергруппе менеджеров только если выбран канал связи "В Telegram".
- **active_topic_id:** Управляет текущим состоянием шлюза (куда пересылать прямо сейчас).
- **permanent_topic_id:** Неизменяемый адрес ветки чата клиента. Обеспечует принцип **"Один клиент — один топик"** (Anti-Duplicate). Если поле заполнено, бот пишет в старый топик, а не создает новый.

11. Режим "Smartbot": AI-Квалификация и Динамическая Маршрутизация (v1.58+)
В версии 1.58 введен третий тип обработки лидов — Smartbot. Это фундаментальное изменение архитектуры: теперь после квалификации диалог не обрывается и не передается человеку-оператору сразу. Вместо этого управление передается AI-Агенту (n8n), который обладает инструментами для работы с базой данных (склад, кредиты).

11.1. Общая логика работы (High-Level Logic)
Ранее система работала бинарно: либо чат с менеджером (Chat), либо звонок (Call). Режим Smartbot создает "прослойку" интеллектуального обслуживания:

Сбор контекста: Пользователь проходит стандартный опрос (Dialogflow) в Python-боте (бюджет, модель, Trade-in).

Заморозка Шлюза: При завершении опроса, если тип дилера — Smartbot, система не включает режим is_in_gateway. Сообщения не летят менеджеру.

Handoff Webhook: Python-бот формирует "Богатый Payload" (Rich Context) и отправляет его в n8n.

AI-генерация:

n8n получает контекст (кто клиент, что хочет, ID дилера).

n8n получает карту данных (в каких таблицах искать машины именно этого дилера).

AI формирует персонализированный ответ (расчет кредита, наличие авто) и возвращает его в Telegram.

11.2. Функционал, добавляемый к текущему боту
Python-бот перестает быть просто "маршрутизатором сообщений". Он становится агрегатором контекста:

Context Extraction: Бот научился "вынимать" из Dialogflow параметры: payment (желаемый платеж), model_id (выбранная модель), complectation_id (конкретная комплектация).

Dynamic Routing Injection: Бот сам ходит в базу дилеров, узнает ID таблиц (где лежат машины, где ставки) и вкладывает эти технические ID в запрос к AI.

Secure Image Proxy: Бот умеет (опционально) отправлять картинки, полученные от AI, как нативные медиа-файлы Telegram, скрывая источник (NocoDB).

11.3. Изменения в Базе Данных и Коде
Изменения в БД (NocoDB -> Dealers Table)
Для поддержки мультибрендовости в таблицу Дилеров добавлены поля для маршрутизации:

Program_Table_ID (String): ID таблицы, где лежат условия кредитных программ (Мин. взнос, Срок) для этого дилера.

Rates_Table_ID (String): ID таблицы с кредитной матрицей (Ставки vs Сроки) для этого дилера.

Изменения в Коде (main.py)
final_sync_wrapper: Добавлена ветка elif communication_type == "Smartbot". Она блокирует создание тикета в Bitrix (или создает его в фоне) и вызывает send_handoff_webhook.

send_handoff_webhook: Новая функция. Собирает JSON-объект, объединяя:

user_data (Имя, телефон).

qualification_context (Ответы пользователя).

data_routing (ID таблиц NocoDB).

11.4. Сущность AI Agent в n8n (Архитектура)
Новая сущность в n8n — это AI Agent, работающий в связке с кастомным инструментом (Tool) "Car Search & Credit Calc".

Архитектура n8n Workflow:
Webhook (POST) -> AI Agent -> Tool (JavaScript Code) -> Response

Webhook: Принимает Payload от Python-бота.

AI Agent (LangChain):

Роль: "Менеджер автосалона".

Инструкция: "Используй инструмент Car Search, чтобы найти машины. Не придумывай цены сам. Передавай data_routing в инструмент без изменений".

Tool "Car Search" (Node.js/JavaScript):

Это "мозг" системы. Он не привязан к конкретному дилеру.

Он принимает data_routing из входа и делает динамические запросы к NocoDB API.

Функционал Тула:

Catalog Match: Поиск комплектаций по ID или названию.

Stock Check: Проверка наличия с разбивкой по статусам (in_stock, in_transit) и цветам.

Smart Credit Calculation:

Scenario 1 (Reality Check): Проверка, реален ли платеж клиента.

Scenario 2 (Light Entry): Расчет мин. взноса на 84 мес.

Scenario 3 (Fast Pay): Расчет макс. взноса на 12 мес.

Image Processing: Генерация прямых ссылок на фото.

Output: JSON с готовым текстом для пользователя, который Python-бот просто пересылает в чат.

**Ключевые конвенции кабинета** (подробности — в `CABINET_HANDOFF.md`):
* Модули `cabinet_service.py` / `cabinet_api.py` / `sms_gateway.py` / `log_masking.py` — строгие листья, `main.py` не импортируют. Связь только через `cabinet_service.setup(...)`; в `main.py` — тонкая проводка, запинованная source-grep-ассертами.
* Время в кабинете — timezone-aware: `_utcnow()` = `datetime.now(timezone.utc)`, всё прочитанное из БД нормализуется через `_aware(dt)` перед сравнением.
* Схема БД — по конвенции v1.34 (без Alembic): `create_all` + идемпотентные `ALTER`/`CREATE UNIQUE INDEX IF NOT EXISTS` в `init_db()`.
* Постановка кабинета в `pending_sync` — недебаунсимая и ровно одна: боевой Bitrix-вызов кабинета идёт через `_cabinet_bitrix_request` (`enqueue_on_failure=False`), чтобы `_request` не поставил вторую запись.
