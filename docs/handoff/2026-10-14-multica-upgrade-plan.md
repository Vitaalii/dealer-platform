## Защита входа по коду без Redis (анализ кода v0.6.2, без изменений)

| Механизм | Есть? | Где |
|---|---|---|
| Длина/алфавит кода | 6 цифр, `crypto/rand`, 10^6 вариантов | `server/internal/handler/auth.go:124-131` |
| Срок жизни | 10 минут | `auth.go:380` |
| Лимит попыток на код | 5: код с `attempts >= 5` больше не выбирается | `server/pkg/db/queries/verification_code.sql:6-13`; инкремент `auth.go:425-426` |
| Частота выдачи кодов на email | 1 раз в 60 с, через БД — **работает и без Redis** | `auth.go:364-366` |
| Блокировка аккаунта после неудач | **нет** — только исчерпание конкретного кода | — |
| IP rate limit (5/мин send-code, 20/мин verify) | **выключен без Redis**: middleware пропускает всё | `server/internal/middleware/ratelimit.go:60-64`, `server/cmd/server/router.go:1500-1509` |
| Dev-код (фиксированный код для любого email) | выключен: `APP_ENV=production` в контейнере, `MULTICA_DEV_VERIFICATION_CODE` пуст (проверено) | `auth.go:50,133-148`; compose `APP_ENV: ${APP_ENV:-production}` |

**Риск.** Атакующему нужен email существующего пользователя (он один).
- Последовательный перебор: не больше 5 попыток на код, не больше 1 кода в минуту → около 7200
  попыток в сутки, вероятность успеха около 0,7 % в сутки (~20 % за месяц непрерывной атаки).
  Атака шумная: ~1440 кодов в сутки в таблице и в логе, но почты нет, и владелец её не увидит.
- **Гонка (по коду, не измерял):** проверка `attempts < 5` (SELECT), сравнение и инкремент — три
  отдельных шага без блокировки. Параллельные запросы к одному коду читают `attempts` до того, как
  инкременты применятся, так что попыток на код может быть заметно больше 5. Без IP-лимита
  параллелизм ограничен только пулом БД (25 соединений) и CPU. Насколько это ускоряет перебор,
  без нагрузочного теста не знаю.
- Вывод: риск реальный, но не мгновенный. Основной усилитель — отсутствие IP-лимита, из-за
  которого работает гонка.

**Варианты защиты:**
1. **Redis в `compose.override.yml`** (сервис `redis:7-alpine` без публикации портов +
   `REDIS_URL=redis://redis:6379`). Включает лимиты 5/мин и 20/мин. За `Caddy → Next.js → backend`
   при пустом `RATE_LIMIT_TRUSTED_PROXIES` backend видит один IP (контейнер frontend), поэтому лимит
   фактически глобальный — для инстанса с одним пользователем это даже строже: 20 попыток verify в
   минуту на всех, гонка сводится к 20 в минуту. **Побочные эффекты:** Redis переключает realtime и
   другие компоненты из in-memory в режим relay через Redis (`SELF_HOSTING.md`, раздел WeCom/relay),
   плюс ещё один сервис и ~10–30 MB памяти (свободно ~3 GB). Оценка: эффективно, умеренный риск
   изменения поведения; делать отдельным изменением с проверкой.
2. **Лимит в Caddy:** в установленном Caddy 2.11.7 модуля rate limit нет (`caddy list-modules` —
   0); нужен сторонний `caddy-ratelimit` и сборка через xcaddy вместо пакета apt — ломает
   обновление Caddy через apt. Оценка: не рекомендую.
3. Без изменения стека: следить за ростом `verification_code` и кодов в логе (сигнал атаки);
   держать email пользователя непубличным. Оценка: только обнаружение.

Рекомендация: вариант 1 отдельной задачей после пилота (или раньше, если email публичен).
