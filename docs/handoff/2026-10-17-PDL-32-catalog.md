# PDL-32 — каталог марок в новой базе (этап 5.5), запуск 1

План: ИТОГ Разработчика в PDL-34 и одобрение Координатора там же (17.10). Ветка задачи построена поверх ветки
5.1 `agent/agent/76db8b17676d` (PR #31, ещё не слит), поэтому дифф PR против `main` включает и коммит 5.1 —
мои файлы перечислены ниже.

## Что сделано

- `infra/db/catalog/gen_migration.py` — генератор миграции. Читает `schema/<марка>/<таблица>.columns.json`
  (свой формат или как в мета-API NocoDB: `colOptions.options[].title`) и пишет
  `infra/db/migrations/0002_catalog_brands.py`:
  - таблица `catalog."<марка>_<таблица>"` на каждый файл; правило имени — только в `pg_table_name()`;
  - имена колонок — `title` поля NocoDB в кавычках, побайтно; отказ при `"`, `\`, NUL, пробелах по краям и
    длине больше 63 байт (PostgreSQL молча обрезал бы имя);
  - типы: текстовые и SingleSelect/MultiSelect → `text` без CHECK, Number → `bigint`, Decimal/Currency/Percent →
    `numeric`, Checkbox → `boolean`, Date → `date`, DateTime/CreatedTime/LastModifiedTime → `timestamptz`,
    Attachment → `text` (JSON), ID → `bigserial PRIMARY KEY`; вычисляемые (Links, Lookup, Rollup, Formula и др.)
    и неизвестные типы — ошибка;
  - служебные `platform_meta.catalog_columns` (марка, таблица, поле, позиция, uidt, тип, варианты) и
    `platform_meta.catalog_imports` (журнал); GRANT/ALTER DEFAULT нет;
  - `--check` сверяет файл миграции с описаниями.
- `infra/db/catalog/load.py` — загрузчик: сверка `manifest.json` с файлами и числом записей, сверка полей с
  `platform_meta.catalog_columns`, подготовка строк с проверкой типов, сравнение с базой, по таблице в одной
  транзакции — INSERT/UPDATE по исходному id, `--prune` — DELETE, перестановка счётчика, строка журнала.
  Повтор того же файла — «вставлено 0, обновлено 0». `--dry-run` ничего не пишет. Вложения: остаются `path`,
  `title`, `mimetype`, `size`; `signedUrl`, `signedPath`, `thumbnails` убраны; `--photo-base-url` даёт `url`;
  без него пути печатаются строками `photo: …`. Служебное поле API `ncRecordHash` пропускается (его же убирает
  бот, `bot/main.py:2772`). Работа с базой — класс `PgStore`, отдельно от подготовки строк.
- `infra/db/catalog/__init__.py`, `infra/db/catalog/schema/README.md` (куда класть файлы CE).
- `infra/tests/fixtures/catalog_sample/` — выдуманная марка `demo`, 8 таблиц, 2–3 строки: `Сonsumption` с
  кириллической «С», пробелы в именах, SingleSelect, вложения с `signedUrl`, `Active`, `Active_1`, запись без
  поля, ответ в виде `{"list": [...]}`.
- `infra/tests/test_catalog_gen.py` (13 тестов), `infra/tests/test_catalog_load.py` (16 тестов).
- `infra/README.md` — строки в таблице «Что здесь лежит» и раздел 13 «Каталог»: формат выгрузки, 12 команд
  владельца с ожидаемым выводом.

## Риски

- **Имя таблицы `<марка>_<таблица>`** задано в одном месте — `pg_table_name()` в `gen_migration.py`. На стенде
  5.6 может выясниться, что граберу нужны исходные имена таблиц (например, `catalog` в отдельной базе или схеме
  на марку). Тогда менять только эту функцию и перегенерировать `0002` (до первого применения на тесте).
- Формат `*.columns.json` от CE может отличаться от ожидаемого (`title`, `uidt`, `options`/`colOptions`).
  Генератор в этом случае остановится с понятной ошибкой; подстроить разбор — в запуске 2.
- Системные поля NocoDB с типами не из списка (например `CreatedBy`) дадут ошибку «unknown type» — решать по
  факту файлов CE, без догадок.
- Дата-время без часового пояса в записях → отказ загрузчика (не угадываем пояс).
- Колонка, которой нет только в части записей, считается пустой; колонка, которой нет ни в одной записи, —
  отказ. Если CE отдаёт записи без пустых полей, это может потребовать правки в запуске 2.

# Запуск 3 (17.10): решения получены, миграция `0002` сгенерирована

Решения — комментарий Координатора в PDL-32 (ответ владельца «1а, 3б, 4а»; вопрос 2 — решение Координатора).

## Что сделано

- **Генератор.** Типы `CreatedBy`, `LastModifiedBy`, `Order` (системные поля старой NocoDB) и `Links`,
  `LinkToAnotherRecord` (связи со складом) не переносятся: колонка не создаётся, в `platform_meta.catalog_columns`
  строка с `role = 'skipped'` и `pg_type` NULL. Остальные вычисляемые типы (Lookup, Rollup, Formula…) — по-прежнему
  ошибка. Таблица без колонки типа ID берёт ключ из `schema/keys.json`: поле — `text NOT NULL UNIQUE`
  (`role = 'key'`), колонку `"Id" bigserial PRIMARY KEY` создаёт база (`role = 'generated'`). Без записи в
  `keys.json` — ошибка, как раньше. В `catalog_columns` добавлена колонка `role` с CHECK по трём значениям.
- `infra/db/catalog/schema/keys.json`: `geely/credit_programs` → `Program_id`, `geely/credit_rates` → `Rate_id`.
- `infra/db/migrations/0002_catalog_brands.py` — сгенерирована: 43 таблицы в `catalog`, без GRANT.
- **Загрузчик.** Сверка и upsert по ключу из `catalog_columns` (исходный `Id` или поле из `keys.json`);
  пропущенные поля в записях игнорируются (могут быть, могут не быть); `Id`, созданный базой, в записях —
  лишнее поле. Счётчик переставляется только для исходного `Id`. `--prune` удаляет по ключу нужного типа.
- **Фото (решение 4а).** Без `--photo-base-url` исходная `url` сохраняется; с ключом `url` = адрес + `path`, а если
  `path` нет — путь из исходной `url` (часть после домена, вместе с именем бакета, если ссылка вида
  `storage.yandexcloud.net/<бакет>/…`). В список «к переносу» попадают только вложения без `url`.
- Образец дополнен: системные поля и связи в `demo/catalog`, вложение только с `url`, таблица
  `demo/credit_programs` без `Id` с ключом `Program_id` в `keys.json`.
- Тесты: на пропуск полей, ключ без `Id`, ошибки `keys.json`, фото по `url`, реальные схемы CE
  (43 таблицы, 4 марки, `Сonsumption` в каждом каталоге, ключи geely, нет `nc_*` и связей в DDL, `0002`
  совпадает с генерацией).
- README, раздел 13: что перенесено и что нет, `keys.json`, поведение фото, вывод загрузчика.
