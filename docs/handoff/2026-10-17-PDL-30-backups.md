# PDL-30 — Этап 5.3: бэкапы и мониторинг

Задача: PDL-30, план одобрен Координатором в PDL-36. Ветка — от `agent/agent/76db8b17676d` (PR #31, 5.1),
PR в `main`, сливать после #31.

## Что сделано

- `infra/postgres/Dockerfile`: в образ добавлены `pgbackrest`, `rclone`, `openssl`, конфиг pgBackRest и скрипт
  дампа; каталоги `/var/spool/pgbackrest`, `/var/backups/dealers-dump`, `/restore` принадлежат `postgres`.
- `infra/postgres/pgbackrest/pgbackrest.conf`: S3 Yandex (`storage.yandexcloud.net`, `ru-central1`, path-style),
  хранение 30 дней (`repo1-retention-full-type=time`), шифрование `aes-256-cbc`, `zst`, `process-max=1`,
  асинхронный архив с очередью не больше 4 ГиБ. Секретов нет — только переменные `PGBACKREST_*`.
- `compose.yaml` и `compose.test.yaml`: `archive_mode=on`, `archive_timeout=60`, `archive_command` — в обоих;
  у `postgres` — переменные бэкапов (`:?` — обязательные) и тома `pg_spool`, `pg_dump`.
- `infra/postgres/bin/dealers-dump.sh` (внутри контейнера): `pg_dumpall --globals-only` + `pg_dump -Fc` трёх баз,
  шифрование `openssl -aes-256-cbc -pbkdf2` сразу при записи, `rclone copy` в `dump/<дата>/`,
  `rclone delete --min-age <DUMP_RETENTION_DAYS>d` (по умолчанию 30), на диске — только последний дамп.
- `infra/backup/` (на хосте, crontab пользователя `deploy`): `backup.sh full|diff`, `wal-check.sh`
  (`pgbackrest check` раз в час), `dump.sh`, `restore-check.sh`, `disk-check.sh` (< 80 %), общий `lib.sh`
  (сигналы Healthchecks `<PLATFORM_ENV>-<задание>`, ключ — через stdin curl; общий замок `flock` для тяжёлых
  заданий), `crontab` (копия 03:00 → дамп 04:00 → проверка пн 05:00; журнал :45, диск :50).
- `restore-check.sh`: точка восстановления + число строк всех таблиц `catalog`, `content`, `platform_ro`,
  `platform_meta` в одном снимке → `pgbackrest check` → `restore` во временный том `/restore` с
  `--archive-mode=off` → временный PostgreSQL отдельным `docker run` (512m, без портов, `listen_addresses=`)
  → проверки (а)–(д) из плана → удаление контейнера и тома через `trap`.
- `infra/.env.example`: 7 новых переменных, пустые. `infra/README.md`: раздел 13 (регистрации, ключи, первый
  запуск, ручное пробное восстановление по шагам, журнал, «если что-то не так»), правки шагов 9 и 12.
- Тесты: `infra/tests/test_backup_config.py`, `infra/tests/test_backup_scripts.py`; в `test_env_example.py`
  разрешены переменные, которые скрипты бэкапов читают из `.env` сами (`env_get`).

## Отличия от плана

- Дамп хранится 30 дней (решение Координатора, В2), а не 14; срок — переменная `DUMP_RETENTION_DAYS`.
- Ключ rclone не отдельный: скрипт дампа берёт те же `PGBACKREST_REPO1_S3_KEY*` (меньше секретов).
- Временный PostgreSQL запускается `docker run` образа, а не `docker compose run`: `compose run` подключил бы
  рабочий том `pg_data` к второму контейнеру. Ручная инструкция — так же.
- Явный `pg_switch_wal()` не вызывается: его делает `pgbackrest check` (pgbackrest.org/command.html, check).
- Автосоздание проверок Healthchecks (`?create=1`) не используется: проверки создаются вручную с расписанием
  Cron (README 13.1), иначе у автосозданных был бы период по умолчанию.

## Проверено

- `python3 -m unittest discover -s infra/tests -t infra` → `Ran 70 tests … OK (skipped=1)`; пропущен только
  `test_shellcheck` — shellcheck не установлен.
- `bash -n` всех `infra/backup/*.sh` и `infra/postgres/bin/dealers-dump.sh` — без ошибок (и в тестах).
- Скрипты запущены с фальшивыми `docker`, `curl`, `df`, `flock`, `pg_dump`, `openssl`, `rclone`: успех и сбой
  дают сигналы `/start` и `/<код>`; при сбое восстановления временные контейнер и том удаляются; ключи и пароли
  не попадают в командную строку; сбой `pg_dump` — ничего не загружено, прошлый дамп остался.
- `docker-compose --env-file <временный файл с x вместо значений> config --quiet` (Compose v2.40.3,
  `COMPOSE_FILE=compose.yaml:compose.test.yaml`) — без ошибок, в итоговом `command` теста есть архив журнала.
- Документация сверена: pgbackrest.org/command.html (`--archive-mode` off/preserve, `--type=name`,
  `--target-action=promote`, `check` вызывает `pg_switch_wal`, переменные `PGBACKREST_*`);
  healthchecks.io/docs/http_api/ (форматы URL, тело до 100 кБ); rclone.org/docs (переменные
  `RCLONE_CONFIG_<ИМЯ>_*`, суффикс `d`), rclone.org/s3 (`provider=Other`, `no_check_bucket`,
  `force_path_style`), rclone.org/filtering (`--min-age`), yandex.cloud/ru/docs/storage/tools/rclone
  (endpoint, регион).

## Не проверено

- Сборка образа (`docker compose build postgres`): локально нет Docker-демона, и по «Границам» без обращения
  к внешним сервисам. Есть ли пакеты `pgbackrest` и `rclone` для версии Debian текущего `postgres:17` —
  проверит владелец на сервере (README 13.3; при ошибке — остановиться и прислать вывод).
- Всё, что требует хранилища и живой базы: `stanza-create`, архив, копии, дамп, восстановление, `verify`, сигналы
  Healthchecks — владелец по README 13.3–13.4.
- Хватит ли памяти теста на временную базу 512m: сумма лимитов 4,4 ГиБ + 512 МиБ ≈ 4,9 ГиБ из 6 ГБ — расчёт,
  не замер. Если не хватит — NocoDB и n8n не останавливать, написать в задачу.
- Не мешает ли `pgbackrest check` (каждый час в :45) идущей копии — в документации про это не нашёл; на тесте
  будет видно по сигналам `test-wal` в ночь копии.
- Провайдер rclone для Яндекса: использован общий `Other` с endpoint и регионом Яндекса; отдельного значения
  для Яндекса в прочитанной части rclone.org/s3 не нашёл.
- Названия пунктов интерфейса Healthchecks (ping key в настройках проекта, расписание Cron) — по памяти о
  сервисе, сверить при настройке.
- shellcheck и gitleaks не установлены; дифф просмотрен вручную — ключей, паролей и ping key нет (в тестах —
  только заведомо фальшивые строки).
