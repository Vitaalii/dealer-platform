Источники: снимки `bot/`, `n8n/`, `landing/`, документы `docs/`, ответы CE старой системы (вложения к PDL-14:

Как читать ссылки:

- «со слов CE грабера» / «со слов CE кабинета» — из ответов CE, **по коду не проверено** (ссылки CE ведут в

## Вывод коротко

1. **Рекомендую вариант Б**: одна база PostgreSQL новой платформы — источник истины для всего; NocoDB подключена
   к ней как «окно» для просмотра и ручной правки. Деньги, заявки и учётные записи в NocoDB только на чтение
   или не видны вовсе; каталоги, промпты и справочники — на правку.
2. **Как ограничить правку.** В бесплатной самостоятельной NocoDB права на отдельные таблицы и поля
   недоступны (они в платных планах). Поэтому разделяем данные на две схемы PostgreSQL и подключаем их в
   NocoDB двумя источниками: «правка» и «только чтение». Плюс отдельная роль базы, у которой на денежные
   таблицы есть только право чтения. Тогда запрет держит сама база, а не настройка интерфейса.
3. **Бот, лендинг и n8n читают PostgreSQL напрямую, не через NocoDB.** Тогда падение NocoDB (как 06.10 в старой
   системе) не останавливает сайты и бота. Это потребует правок в боте и n8n при переносе — мест немного,
   они перечислены ниже.
4. **Каталоги в новую систему**: на время разработки — разовая копия (выгрузка таблиц владельцем). Грабер
   переключается на новую базу по марке, в день переезда марки, сменой файла окружения. Писать в две базы
   сразу грабер не умеет (со слов CE грабера), а дорабатывать его ради разработки не нужно.
5. **Главный риск варианта Б не проверен**: примет ли грабер NocoDB поверх внешней PostgreSQL (те же имена
   колонок, типы SingleSelect, вложения-фото). Это надо проверить на тестовом стенде до решения «окончательно».
   Если не примет — запасной путь: вариант А только для таблиц грабера.

## 3. Грабер каталогов

Всё в этом разделе — **со слов CE грабера, по коду не проверено**.

- Четыре марки, у каждой своя база NocoDB. Источник — PDF-прайсы с сайтов импортёров.
- Прогон по cron (GEELY 05:00, BELGEE 06:00, TENET 07:00, HAVAL 08:00 МСК; 1-го числа и раз в 5 дней) на боевом
  VPS Hostkey, код в `/opt/site_graber`. Прогон каталог не меняет: пишет в `parsed_prices` и шлёт оператору
  карточки NEW/CHANGED в Telegram.
- В каталог строка попадает **только по кнопке оператора**. Upsert по ключу
  Model + Complectation + Engine + Transmission + Drivetrain, по одной строке за запрос; пустые поля не
  отправляет.
- Не пишет `Active`, `Active_1`, `Pics`, `Title_pic`, `slug`. Новая строка рождается неактивной. `Active` читает
  (для сообщений о пропавших комплектациях).
- Выгоды пишет; у TENET и BELGEE может очищать выгоды, если их нет в прайсе (тоже по кнопке). Цену, исправленную
  руками, перезапишет первая подтверждённая карточка CHANGED.
- Пропавшие модели не удаляет и не выключает — только сообщение оператору.
- Адрес NocoDB, ключ и id таблиц — из окружения (`/etc/site_graber/<марка>.env`). В новой базе нужны все 8 таблиц
  с той же схемой и **побайтно теми же именами колонок** (в том числе `Сonsumption` с кириллической «С»), с
  вариантами SingleSelect. Писать в две базы сразу не умеет.
- Читает не больше 1000 записей за запрос, без постраничной выборки.

## 4. Варианты хранилища

### А. PostgreSQL для денег и заявок + отдельная NocoDB со своей базой для каталогов и промптов

Похоже на нынешнюю схему: каталоги, промпты, справочники живут в таблицах NocoDB; деньги, заявки, учётные
записи и база бота — в PostgreSQL платформы.

Плюсы:
- грабер переключается сменой окружения, схема та же (со слов CE грабера) — самый простой путь для каталогов;
- бот и n8n продолжают читать каталог через REST и узлы NocoDB — меньше правок при переносе;
- владелец правит каталоги в привычном интерфейсе.

Минусы:
- два хранилища — два бэкапа и две проверки восстановления (`docs/REQUIREMENTS.md:176-181`);
- каталог (в NocoDB) и настройки дилера по комплектациям (видимость, скидки — в PostgreSQL,
  `docs/REQUIREMENTS.md:82`) нельзя связать одним запросом: итоговую цену собирает код из двух источников. Это
  прямо противоречит цели «итоговая цена одинакова везде» (`docs/REQUIREMENTS.md:78`, `:83`) — риск расхождений;
- NocoDB на критическом пути: лендинг, бот и n8n читают каталог через неё. Урок 06.10 (падение по памяти
  остановило каталог лендингов и бота, `bot/CABINET_CONTEXT.md:16-17`) повторяется.

### Б (основной). Одна PostgreSQL, NocoDB подключена к ней как внешний источник

Все данные — в PostgreSQL платформы. NocoDB подключается к ней функцией «Connect External Data» и даёт
интерфейс просмотра и правки. Служебные данные самой NocoDB (виды, настройки) — в её отдельной служебной базе.

Что даёт NocoDB для внешнего источника (официальная документация,
[Connect to a Data Source](https://nocodb.com/docs/product-docs/data-sources/connect-to-data-source), обновлено
09.10.2026):
- права задаются **на весь источник**: «Allow Data Edit» (вставка, правка, удаление записей; по умолчанию
  включено) и «Allow Schema Edit» (по умолчанию выключено). Правку данных можно выключить только при выключенной
  правке схемы. Без правки данных остаются просмотр, фильтры, сортировка, группировка;
- при выключенной правке схемы можно добавлять виртуальные колонки (Lookup, Rollup, Formula), виды и вебхуки;
- PostgreSQL рекомендуется версии 14 и новее.

Права на отдельные таблицы и поля в NocoDB есть, но платно: «Field permissions are available on NocoDB Cloud (Plus
plan and above) and licensed self-hosted deployments (Business plan and above)»
([Field Permissions](https://nocodb.com/docs/product-docs/roles-and-permissions/field-permissions)); то же для
записей таблицы ([Table Permissions](https://nocodb.com/docs/product-docs/roles-and-permissions/table-permissions)).
Поэтому разделение «правка / только чтение» делаем схемами PostgreSQL и правами ролей базы
(`GRANT SELECT`, [PostgreSQL: GRANT](https://www.postgresql.org/docs/current/sql-grant.html)), а не настройками
NocoDB.

Плюсы:
- один источник истины, одна база для бэкапа и проверки восстановления;
- каталог, настройки дилера, тарифы, заявки — в одной базе: итоговая цена считается одним запросом, проверка
  паритета цен (`docs/REQUIREMENTS.md:83`) проще;
- деньги и заявки защищены правами самой базы: даже при ошибке в настройке NocoDB роль её подключения не может
  их изменить;
- если бот, лендинг и n8n читают PostgreSQL напрямую, падение NocoDB не останавливает сайты и бота.

Минусы:
- правки при переносе: бот читает NocoDB в 6 местах (`bot/main.py:2509`, `:2680`, `:2753`, `:2788`, `:3057`,
  `bot/bot_registry.py:215`), n8n — 15 узлов NocoDB в 6 воркфлоу (раздел 2). Альтернатива — оставить им REST
  NocoDB поверх новой PostgreSQL: правок почти нет, но NocoDB снова на критическом пути (решение владельца, вопрос 2);
- в PostgreSQL придётся держать колонки с именами, как у грабера (пробелы, кириллица) — иначе грабер не
  запишет. Это неудобно для кода, но работает через имена в кавычках (предположение: проверить на стенде);
- **не проверено**, что грабер (REST NocoDB, SingleSelect, проверка колонок `UndeclaredColumnsError` со слов CE
  грабера) работает с таблицами внешнего источника так же, как со своими таблицами NocoDB. Как NocoDB хранит
  SingleSelect и вложения (фото) во внешней PostgreSQL — в найденной документации не описано (предположение:
  как текст / JSON в колонке);
- лицензия: с 2026 года NocoDB распространяется по Sustainable Use License — использование разрешено «only for
  your own internal business purposes» ([LICENSE.md в репозитории nocodb/nocodb](https://github.com/nocodb/nocodb/blob/develop/LICENSE.md),
  «Updated on: January 29, 2026»). Касается вариантов А и Б одинаково. Использование как внутреннего
  инструмента владельца, без доступа дилеров к NocoDB, по смыслу подходит (предположение, не юридическая оценка).

#### Таблицы в NocoDB: правка и только чтение

Предлагаемое разделение (предложение для документа архитектуры; имена схем условные):

| Схема / источник в NocoDB | Таблицы | Почему |
|---|---|---|
| `catalog` — **правка** | каталоги марок; оснащение (Features); цвета; склад; кредитные программы и ставки; служебные таблицы грабера (`sites` и др.) | их правит владелец (видимость, фото, выгоды GEELY и HAVAL — со слов CE грабера) и пишет грабер |
| `content` — **правка** | промпт-блоки бота, Prompt_Blocks, Intents, Intent_Block_Map; реестр ботов (без токенов, только имена переменных — как сейчас, `bot/main.py:4296-4298`) | сейчас правятся владельцем и скриптами в NocoDB |
| `platform_ro` — **только чтение** | заявки и их статусы доставки; отклонённые заявки; движения денег, балансы; счета и акты; тарифы и переопределения; чёрные списки; дилеры и их сайты, контент, Hero; настройки дилера по комплектациям (видимость, скидки) | меняются только через кабинет и админку: у денег запись нельзя менять задним числом (`docs/REQUIREMENTS.md:117`), видимость и скидки ведёт дилер (`docs/REQUIREMENTS.md:78`), дилеров и тарифы — админка (`docs/REQUIREMENTS.md:149-155`) |
| **не подключать** | учётные записи (пароли — хэши), сессии кабинета, OTP, токены кабинета, согласия, данные клиентов из кабинета (`bot/database.py:114-348`) | секреты и персональные данные; просмотр через NocoDB не нужен |

Заметки:
- деньги и заявки — только чтение, как и предполагал владелец. Тарифы и чёрные списки тоже — через админку,
  чтобы любое изменение шло через код с журналом;
- **Предположение**: общая колонка `Active` в каталоге нужна и дальше — её читает грабер (со слов CE грабера);
  колонки `Active_N` по дилерам заменяются таблицей настроек дилера (`docs/REQUIREMENTS.md:82`).

### В. Только PostgreSQL, без NocoDB, правка в админке платформы

Плюсы: один компонент меньше; нет вопроса с лицензией и памятью NocoDB; права — только в коде платформы.

Минусы:
- нужно строить в админке экраны правки каталогов, фото, промптов, справочников — этого нет в перечне экранов
  (`docs/REQUIREMENTS.md:147-157`);
- грабер пишет только в NocoDB (со слов CE грабера): нужна его доработка или отдельный синхронизатор;
- владелец теряет привычный интерфейс; владелец уже выбрал NocoDB как интерфейс (описание PDL-14).

### Оценка

Оценка качественная: «+» хорошо, «±» средне, «−» плохо.

| Критерий | А | Б | В |
|---|---|---|---|
| Надёжность денег и заявок | + | + (защита правами базы) | + |
| Одна цена для трёх потребителей | − (два источника) | + | + |
| Падение NocoDB не останавливает сайты и бота | − | + (если читают PostgreSQL напрямую) | + |
| Бэкап и восстановление | ± (две базы) | + | + |
| Подключение грабера | + (смена окружения) | ± (не проверено на стенде) | − (доработка) |
| Правки бота и n8n при переносе | + (мало) | ± (умеренно) | ± (умеренно) |
| Удобство владельца | + | + | − |
| Объём новой разработки | + | + | − (экраны правки) |

## 5. Как получить каталоги в новой системе

| Путь | Как | Плюсы | Минусы и риски для боя |
|---|---|---|---|
| 1. Разовая копия | владелец выгружает таблицы каталогов из интерфейса NocoDB (CSV) и отдаёт для загрузки в новую базу; фото — отдельно | без нагрузки на бой (десятки строк, по одной таблице); старое не меняется | копия устаревает; фото надо переносить файлами и менять ссылки (домен NocoDB в n8n, `n8n/flow/Tool - Car Search.json:6`) |
| 2. Синхронизатор старая → новая | отдельная программа периодически читает боевую NocoDB и пишет в новую | копия свежая | постоянное чтение боевой NocoDB, которая один раз уже падала (`bot/CABINET_CONTEXT.md:16-17`); нужен ключ старой системы в новой — запрещено (`CLAUDE.md`, раздел «Секреты») |
| 3. Двойная запись грабера | доработка грабера на запись в две базы | обе базы свежие | правка боевого сервиса старой системы; старая система заморожена (`docs/REQUIREMENTS.md:31`) |
| 4. Переключение грабера по марке | в день переезда марки — свежая копия (путь 1) и смена файла окружения грабера марки на новую базу | просто; совпадает с переездом по марке (`docs/REQUIREMENTS.md:172`) | после переключения старый каталог марки больше не обновляется — переключать только вместе с переездом марки; новая база должна принимать запись грабера (проверка на стенде) |

Ещё по граберу (со слов CE грабера, выводы мои):
- в новой базе нужны все 8 таблиц грабера, включая служебные, с теми же именами колонок;
- грабер работает на боевом VPS старой системы. Если после переезда он пишет в новую NocoDB по сети, ей нужен
  открытый наружу адрес и ключ новой системы на старом сервере. Перенос грабера на новый VPS — отдельное решение
  (вопрос 1).

## 6. Рекомендация

Отдельно от фактов; это моё предложение.

1. **Хранилище — вариант Б.** Одна PostgreSQL; NocoDB — внешний источник, две схемы на правку (`catalog`,
   `content`) и одна только на чтение (`platform_ro`); секреты и персональные данные в NocoDB не подключать.
   Роль базы для NocoDB: запись только в схемы на правку, в `platform_ro` — только `SELECT`.
2. **Бот, лендинг и n8n читают PostgreSQL напрямую** (через код платформы), а не через REST NocoDB. Правки
   делаются при переносе бота и n8n (этапы 7–8). Если владелец хочет меньше правок — промежуточно оставить REST
   NocoDB, но тогда держать NocoDB отдельным контейнером с запасом памяти и не делать через неё массовых чтений.
3. **Каталоги**: сейчас — путь 1 (разовая копия для разработки); при переезде марки — путь 4.
4. **До окончательного решения — проверка на тестовом стенде** (этап 5): NocoDB поверх внешней PostgreSQL с
   таблицами каталога одной марки; грабер (копия, тестовая база) пишет в неё строку по кнопке; проверить
   SingleSelect, вложения-фото, ошибки колонок. Если не проходит — **запасной вариант**: таблицы грабера в
   собственной базе NocoDB (как в А), а остальное как в Б; цену собирает код платформы.

Когда рекомендация меняется:
- проверка на стенде не прошла → запасной вариант из п. 4;
- владелец решает переписать или заменить грабер → вариант Б без ограничений на имена колонок;
- владелец отказывается от NocoDB → вариант В.

## 7. Вопросы владельцу

1. Грабер после переезда: остаётся на старом VPS и пишет в новую NocoDB по сети, или переносится на новый VPS?
   Кто его дорабатывает, если понадобится (сейчас его ведёт CE старой системы)?
2. Бот и n8n в новой системе: читают каталог из PostgreSQL напрямую (больше правок, NocoDB не на критическом
   пути) или через REST NocoDB (меньше правок)?
3. Фото каталога: где хранить файлы в новой системе — в NocoDB или в файловом хранилище платформы?
4. Разовая копия каталогов: кто выгружает таблицы из боевой NocoDB — вы вручную из интерфейса или CE по одной
   таблице? Мне подключаться нельзя.
5. Цвета, склад, оснащение, программы и ставки — кто их сейчас заполняет (грабер их не пишет, кроме оснащения;
   в репозитории не описано)? Нужен ли склад в новой системе?
6. Нужна ли в новом каталоге общая колонка `Active` (её читает грабер) рядом с таблицей настроек дилера?
7. Устраивает ли лицензия NocoDB (Sustainable Use License: только для внутренних целей) — дилеры в NocoDB доступа
   не получают?
8. Разрешаете ли включить в план этапа 5 проверку «грабер + NocoDB поверх внешней PostgreSQL» на тестовом стенде?
