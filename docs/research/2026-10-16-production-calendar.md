# Производственный календарь РФ для срока апелляции

Задача: PDL-22, план — PDL-21 (комментарий с планом, разделы «Что сделаю» 1–5). Ответы владельца
на вопросы плана — в описании PDL-22: разрешён один открытый GET-запрос без ключа к каждому
кандидату за 2026 год; только федеральный календарь; сокращённые дни подробно не исследуем.

Дата исследования: 2026-10-16. Все страницы читались в этот день. Три запроса к API кандидатов
сделаны в 2026-10-16 11:10 UTC (раздел 3). Ничего не регистрировалось, ключей нет, ничего не
устанавливалось.

Обозначения: **[допущение]** — не подтверждено источником; **[проверено]** — сверено мной по
данным или первоисточнику; «не найдено» — на открытых страницах этого нет.

## Вывод коротко

1. **Подходят два сервиса из трёх: Kuzyak Calendar API и isDayOff.** Их данные за 2026 год
   совпали с официальным календарём день в день: 365 дней, 118 нерабочих, 247 рабочих.
   Официальный календарь — это ст. 112 Трудового кодекса плюс постановление Правительства
   от 24.09.2025 № 1466.
2. **BasicData не подходит.** Его API отдаёт данные только за 2003–2017 годы. Главная
   страница сайта отвечает ошибкой 500, сертификат HTTPS просрочен.
3. **Календарь на следующий год появляется в сентябре–октябре.** Постановление о переносах
   выходных выходит за 2,5–4,5 месяца до нового года. Постановление на 2027 год уже есть:
   от 17.09.2026 № 1187, опубликовано 18.09.2026. Kuzyak добавил 2027 год через 5 дней
   после публикации. В открытый репозиторий isDayOff 2027 год добавлен 11.10.2026, но на
   странице состава базы isDayOff пока указаны годы только до 2026.
4. **Календарь можно надёжно вычислить самим.** Нужны выходные (суббота и воскресенье),
   праздники из ст. 112 ТК, правило переноса из той же статьи и 2–3 переноса из постановления.
   Я так вычислил 2026 и 2027 годы, и результат совпал с обоими сервисами. Значит, запасной
   вариант простой: раз в год вручную внести 2–3 строки из постановления.
5. **Сроки для заявок в конце декабря зависят от календаря следующего года.** Пример
   **[допущение о правиле отсчёта]**: если заявку доставили 30.12.2026, первые три рабочих
   дня — 11, 12 и 13 января 2027 года. Поэтому копия на следующий год нужна к декабрю.
   По опыту последних пяти лет постановление к этому времени уже есть.

Рекомендация — в отдельном разделе, после фактов. Вопросы владельцу — в конце.

## 1. Что нужно платформе

- Дилер оспаривает заявку в течение 3 рабочих дней от доставки. Календарь получаем по API
  бесплатного сервиса и храним свою копию на год (`docs/REQUIREMENTS.md:103`).
- В «На анализ»: выбрать сервис, проверить данные на текущий год, найти запасной вариант
  (`docs/REQUIREMENTS.md:237`).
- По ответам владельца в PDL-22 нужен только признак «рабочий / нерабочий день» по
  федеральному календарю для пятидневной недели. Региональные праздники и сокращённые
  предпраздничные дни не нужны: сокращённый день для срока считается рабочим.

## 2. Официальный источник

**Праздники — ст. 112 ТК РФ** ([КонсультантПлюс][tk112]):
- нерабочие праздничные дни: 1–6 и 8 января (новогодние каникулы), 7 января (Рождество),
  23 февраля, 8 марта, 1 мая, 9 мая, 12 июня, 4 ноября;
- если выходной совпал с праздником, он переносится на следующий рабочий день после праздника;
- исключение — выходные, совпавшие с 1–8 января. Два таких выходных Правительство
  постановлением переносит на другие дни года.

На странице КонсультантПлюс указано, что у статьи есть изменения, которые ещё не вступили в
силу. Какие именно, я не проверял. Список праздников на 2026 год, по которому составлен
календарь КонсультантПлюс на 2026 год, совпадает с перечнем выше ([КонсультантПлюс,
календарь 2026][cons2026]).

**Переносы — постановления Правительства** (официальный портал publication.pravo.gov.ru,
тексты прочитаны по PDF):

| 2027 | от 17.09.2026 № 1187 ([pravo][p2027]) | 18.09.2026 | сб 2 января → пт 5 ноября; вс 3 января → пт 31 декабря; сб 20 февраля → пн 22 февраля |

## 3. Сверка 2026 года

**Как сверял.** Эталон я вычислил по правилам из раздела 2: суббота и воскресенье, праздники
ст. 112, перенос выходных, совпавших с праздниками (8 марта → 9 марта, 9 мая → 11 мая),
переносы из постановления № 1466. Затем сравнил с данными кандидатов. Эталон совпал с
календарём КонсультантПлюс на 2026 год: по месяцам 15, 19, 21, 22, 19, 21, 23, 21, 22, 22,
20, 22 рабочих дня, всего 247 ([КонсультантПлюс][cons2026]).

**Запросы** (по одному на кандидата, без ключа, 2026-10-16 11:10 UTC):

| Кандидат | Запрос | Ответ |
|---|---|---|
| isDayOff | `GET https://isdayoff.ru/api/getdata?year=2026&cc=ru&pre=1` | 200, текст из 365 цифр |
| Kuzyak | `GET https://calendar.kuzyak.in/api/calendar/2026` | 200, JSON: только сводка по месяцам и реквизиты постановления |
| BasicData | `GET http://basicdata.ru/api/json/calend/` | 200, JSON с годами 2003–2017, 2026 года нет |

Запрос к Kuzyak `/api/calendar/2026` вернул только число рабочих и нерабочих дней по месяцам,
без дат. Поэтому даты Kuzyak я сверил по файлам данных из его открытого репозитория. По
описанию на сайте API отдаёт эти файлы как статические JSON ([calendar.kuzyak.in][kuzyak]).
Второй запрос к API я не делал: его не разрешают границы задачи.

**Итог по всему году [проверено]:**
- isDayOff: 0 расхождений по 365 дням. Код `1` (нерабочий) стоит ровно на 118 нерабочих днях
  эталона. Сокращённые дни (код `2`): 30 апреля, 8 мая, 11 июня, 3 ноября — совпадают с
  КонсультантПлюс.
- Kuzyak: сводка API по месяцам совпала с эталоном (рабочие и нерабочие дни по всем 12
  месяцам). Список нерабочих дат в файле репозитория `src/data/consultant/2026.json` совпал
  с эталоном без расхождений. Постановление в ответе API указано верно: № 1466, ссылка на
  pravo.gov.ru.
- BasicData: 2026 года нет, сверять нечего.

**2027 год — только по открытым файлам, без запросов к API [проверено]:** я вычислил эталон по
ст. 112 и постановлению № 1187. Он совпал с файлом Kuzyak `src/data/consultant/2027.json`
и с файлом isDayOff `db/2027/ru2027.json`. Рабочих дней — 247. Попал ли файл 2027 года в
сам API isDayOff, я не проверял.

## 5. Запасной вариант

Что делать, если сервис недоступен или перестал обновляться.

| Вариант | Как работает | Плюсы | Минусы | Оценка |
|---|---|---|---|---|
| А. Своя копия на год | раз в сутки (или реже) загружаем год и храним у себя; срок считаем только по копии | уже в постановке; сбой сервиса на время не влияет | если сервис перестал обновляться, копию на следующий год взять неоткуда | обязательна при любом выборе |
| Б. Второй сервис как сверка | грузим год из Kuzyak и из isDayOff и сравниваем; расхождение или нет данных — уведомление владельцу | ошибка одного сервиса видна сразу | два источника вместо одного; у isDayOff 2027 год появляется позже | хорошо, недорого |
| В. Ручной ввод из постановления | владелец вносит 2–3 переноса из постановления; остальное платформа считает сама по ст. 112 | не зависит ни от кого; 2–3 строки в год; правила проверены на 2026 и 2027 годах (раздел 3) | нужен человек раз в год; ошибку ввода никто не проверит, если сервисы не работают | хороший последний рубеж |
| Г. Развернуть Kuzyak у себя | его код открыт (MIT); данные берутся с КонсультантПлюс | не зависим от его хостинга | ещё один сервис в поддержке; зависим от вёрстки страницы КонсультантПлюс | избыточно для 2–3 строк в год **[допущение]** |

**Если данных на следующий год ещё нет.** До постановления можно считать по одной ст. 112: в
праздники и в перенос выходных с праздников она даёт верный ответ. Неизвестны только переносы
двух январских выходных и редкие переносы вроде 20 февраля 2027. По постановлениям за
2023–2027 годы они появлялись не позже начала октября (раздел 2). Значит, к концу декабря,
когда срок апелляции начинает заходить в новый год, данные уже есть.

## Рекомендация

Это моё мнение по фактам выше, решение за владельцем.

1. **Основной источник — Kuzyak**, запрос `/api/calendar/{year}/holidays` (формат ответа знаю
   по README, сам этот адрес не запрашивал). В нём есть даты,
   переносы с пометкой «откуда» и ссылка на постановление. Следующий год он добавил быстрее
   всех. Лицензия MIT.
2. **Второй источник для сверки — isDayOff**, один запрос `/api/getdata?year=YYYY&cc=ru` на год.
   Расхождение источников — уведомление владельцу, копия при этом не меняется.
3. **Своя таблица нерабочих дней на текущий и следующий год.** Срок апелляции считаем только по
   ней. Сервисы её пополняют, но на расчёт срока не влияют.
4. **Ручной ввод переносов из постановления** — на случай, если оба сервиса не обновились.
   Проверка: если к 1 ноября нет следующего года, напомнить владельцу **[допущение: дата
   выбрана с запасом после самой поздней публикации — 4 октября]**.
5. **BasicData не использовать.**

Это пойдёт в документ архитектуры (этап 4) и в биллинг (этап 9).

## Вопросы владельцу

1. **Как считать 3 рабочих дня?** Вариант: день доставки не считается, срок истекает в конце
   третьего рабочего дня после него. По какому времени: московскому или по часовому поясу
   дилера? От этого зависит пример в выводе (30.12.2026 → до конца 13.01.2027).
2. **Подходит ли схема** «Kuzyak основной + isDayOff для сверки + ручной ввод из постановления
   как запасной»? Или достаточно одного сервиса и ручного ввода?
3. **Кто вносит переносы вручную**, если оба сервиса не обновились? Предлагаю владельца через
   админку платформы, раз в год, по напоминанию.
