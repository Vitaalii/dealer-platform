# Доставка заявок: письмо, CallTouch, Яндекс Метрика

Задача: PDL-20, план — PDL-19 (комментарий с планом, разделы «Что сделаю» 1–6). Ответы владельца
на вопросы плана и скриншоты настроек — в описании PDL-20 (16.10.2026).
Дата исследования: 2026-10-16. Все страницы документации открыты в этот день.
Ничего не регистрировалось, к API, Битриксу, Albato и сервисам старой системы агент не обращался —
только репозиторий, скриншоты из задачи и открытые страницы официальной документации.

Обозначения: **[допущение]** — не подтверждено источником; **[вывод]** — моё заключение из
приведённых фактов; «не найдено» — на прочитанных страницах этого нет. Источники — в конце, по меткам
`[M…]` (Метрика), `[C…]` (CallTouch), `[P…]` (Postbox), `[R…]` (репозиторий и задача).

## Вывод коротко

1. **Всё, что сейчас делают роботы Битрикса и Albato, платформа может делать сама, кодом.**
   Письмо — через Postbox, заявка — прямым запросом в CallTouch, конверсия — загрузкой в Метрику
   дилера. Ручной работы под каждого дилера не остаётся. Дилер один раз вводит данные в кабинете
   и выдаёт доступ.
2. **Метрика.** Дилер добавляет логин платформы в своём счётчике с уровнем «Редактирование»
   (Настройки → Доступ). Код платформы проверяет это одним запросом (`my_grant`, ответ
   `perm = edit`). Затем платформа сама создаёт цель «JavaScript-событие» и загружает
   конверсии файлом по идентификатору посетителя (ClientID) или по метке Директа (yclid).
   Есть ограничения:
   - конверсия засчитывается, только если с визита прошло не больше 21 дня;
   - в отчётах она появляется примерно через 3 часа;
   - на один логин платформы — 5 000 запросов к API в сутки на всех дилеров. Загрузки надо собирать
     пачками.
3. **CallTouch.** Заявка отправляется одним запросом на адрес с id сайта дилера. **Токен для
   отправки по документации не нужен**, только id сайта. Токен нужен, чтобы проверить подключение:
   запросом журнала заявок. Чтобы CallTouch понял, с какой рекламы пришёл клиент, сайт должен
   передать идентификатор сессии CallTouch.
4. **Главный риск задвоения — Метрика.** Сам CallTouch умеет передавать заявки в Метрику
   как офлайн-конверсии. Если у дилера это включено, а платформа тоже шлёт конверсию, одна заявка
   засчитается дважды. Решение: платформа шлёт свою цель со своим идентификатором, а в кабинете
   дилеру прямо сказано, какую цель использовать для Директа. Вторая точка — повторы заявок
   внутри CallTouch: он сам отмечает «уникальные» заявки по телефону.
5. **Одно письмо нескольким адресатам в Postbox делается штатно.** Все адреса дилера кладутся
   в «Кому», до 200 получателей в письме. Оплата при этом — **за каждого получателя**, а не за
   письмо: письмо на 4 адреса стоит как 4 письма. Отказы доставки Postbox сообщает по каждому
   адресу отдельно, так что «Состояние доставки» может показывать статус по каждой почте.
6. **Заявки из мессенджеров без захода на сайт в Метрику не попадут.** У такого клиента нет
   ClientID, и конверсию не к чему привязать. Это ограничение Метрики, а не платформы
   [вывод из M5, M6].

## 2. Яндекс Метрика

### 2.1. Доступ: OAuth и уровни доступа

- **OAuth-приложение** создаётся на oauth.yandex.ru, вариант «Для доступа к API или отладки» [M1].
  Права (scopes):
  - `metrika:read` — чтение;
  - `metrika:write` — создание и изменение счётчиков и «загрузка любых данных»;
  - `metrika:offline_data` — офлайн-конверсии, звонки, CRM-данные; не нужен, если есть
    `metrika:write` [M1].

  Токен передаётся заголовком `Authorization: OAuth <токен>` [M1].
- **Срок жизни токена.** Есть «продлеваемые» токены: «устаревает после нескольких месяцев, но
  продлевается при каждой авторизации с этим токеном». При регистрации показывается
  минимальный срок, например «не менее, чем 1 год» [M2]. Отдельного refresh-токена на этой
  странице нет [M2]. Токен перестаёт работать после смены пароля аккаунта [M1].
- **Ошибка 403** бывает, если «у аккаунта токена нет доступа к счётчику» [M1]. Значит, доступ
  определяется аккаунтом, на который выписан токен. Один токен логина платформы работает со всеми
  счётчиками, где дилеры выдали доступ этому логину **[вывод]**.
- **Уровни доступа** [M3], [M4]:

  | Уровень | `perm` в API | Что может |
  |---|---|---|
  | Редактирование | `edit` («полный доступ») | управлять счётчиком, кроме удаления и переноса; создавать и удалять цели; **загружать данные** |
  | Аналитика | `analyst` | создавать цели и сегменты; **не может загружать данные** |
  | Только просмотр | `view` | смотреть; цели не трогает |
  | Публичная статистика | `public_stat` | — |
  | Аналитик через фильтр | `analyst_access_filter` | — |

  Загрузка данных (а офлайн-конверсии — это загрузка) в таблице доступов отмечена только
  у уровня «Редактирование» [M3]. Значит, уровень `edit` нужен **обязательно**.
- **Как дилер выдаёт доступ:** «Настройки → Доступ», блок «Индивидуальный доступ» →
  «Добавить пользователя» → логин → уровень → «Добавить» → «Сохранить» [M3].
  То же можно сделать через API: `POST /management/v1/counter/{counterId}/grants` [M4]. Но этот путь
  требует токена самого дилера, поэтому для платформы не подходит **[вывод]**.
- Квота «добавление представителей — 3 в час на счётчик» [M7] относится к представителям аккаунта,
  а не к гостевым доступам **[допущение по названию квоты]**.

### 2.2. Проверка уровня доступа кодом

- `GET https://api-metrika.yandex.net/management/v1/counter/{counterId}/my_grant` возвращает
  доступ текущего пользователя к счётчику: `grant.perm` = `public_stat` / `view` / `edit` /
  `analyst` / `analyst_access_filter`, плюс `created_at` [M5].
- Проверка при подключении дилера: ответ 200 и `perm = edit` — доступ подходит. Ответ 403 —
  доступа нет. Другой `perm` — уровень ниже нужного, и платформа просит дилера сменить его на
  «Редактирование» **[вывод]**. Как именно выглядит ответ при отсутствии доступа, не проверено:
  запросов к API не было.
- Проверку стоит повторять регулярно, например раз в сутки, и перед загрузкой. Дилер может
  отозвать доступ в любой момент **[рекомендация]**.

### 2.3. Цели

- Цель создаётся запросом `POST /management/v1/counter/{counterId}/goals` [M6]. Для офлайн-конверсий
  нужен тип `action` («JavaScript-событие») с условием `exact` («совпадает»). Идентификатор цели
  должен совпадать со значением `Target` в файле [M8], [M9].
- Типы целей: `action`, `url`, `phone`, `email`, `messenger`, `chat`, `file`, `number`, `search`,
  `social`, `step` (составная, до 5 шагов), `payment_system`, `visit_duration`. Название цели —
  до 255 символов [M6].
- Лимит числа целей на счётчик на странице метода не указан [M6] — не найдено.
- Какой уровень доступа нужен для создания цели: в таблице доступов это «Редактирование» и
  «Аналитика» [M3]. Для платформы он всё равно `edit` из-за загрузки.

### 2.4. Передача конверсий

**Офлайн-конверсии (основной путь)**
- Загрузка: `POST /management/v1/counter/{counterId}/offline_conversions/upload`, тело
  multipart/form-data с полем `file`. Файл — CSV в UTF-8, до 1 ГБ. Параметр `type` =
  `BASIC` / `CALLS` / `CHATS` [M10], [M9].
- Колонки CSV [M8], [M9]:
  - обязательные: `Target` — идентификатор цели; `DateTime` — Unix-время в секундах, только
    прошлое, в часовом поясе счётчика;
  - идентификатор, нужен хотя бы один: `ClientId`, `UserId`, `Yclid`, `PurchaseId`;
  - необязательные: `Price` (точка как разделитель) и `Currency` (ISO 4217). Если валюта не совпадает
    с валютой счётчика, сумма и валюта передаются нулями [M9].
- Привязка [M11]:
  - ClientId и UserId — к визиту, который был до конверсии;
  - yclid — к визиту с этого объявления Директа;
  - UserId работает, только если сайт вызывал `setUserID` [M8].
- **Окно — 21 день** между последним визитом и обработкой файла. Позже конверсия не привяжется
  [M11], [M9].
- **Время обработки — «в течение 3 часов»** [M9]. Сроки в источниках расходятся: в плане PDL-19
  были 2 и 24 часа, CallTouch пишет, что «по данным Яндекса, обработка может занимать до
  24 часов» [C6]. Закладываться стоит на сутки **[рекомендация]**.
- **Статус загрузки:** в ответе объект `uploading` со `status` = `PREPARED` / `UPLOADED` /
  `EXPORTED` / `MATCHED` / `PROCESSED` / `LINKAGE_FAILURE` и счётчиком строк `line_quantity`
  [M10]. Отдельный метод — `GET …/offline_conversions/uploading/{id}` [M8].
- **Внимание:** на странице метода загрузки стоит пометка «[*Deprecated]: No longer supported, please
  use an alternative and newer version», но замена не названа [M10]. Перед разработкой (этап 7)
  нужно перепроверить актуальный метод.
- **Повторная загрузка той же конверсии.** Как Метрика её обрабатывает (склеивает или считает
  дважды), на прочитанных страницах не описано [M8], [M9], [M11]. Поэтому платформа сама должна
  гарантировать «одна заявка — одна строка» **[рекомендация]**.
- Лимиты на число загрузок в сутки и строк в файле не найдены. Указан только размер файла до 1 ГБ
  [M9].

**Квоты API** [M7]:
- 30 запросов в секунду с IP;
- 3 одновременных запроса на пользователя;
- **5 000 запросов в сутки на пользователя**, сброс в 00:00 GMT;
- при превышении — HTTP 429.

Все дилеры через один логин платформы делят эти 5 000 запросов **[вывод]**. При 50 дилерах
и 30–200 заявках в месяц на дилера (`decisions.md`, «Почта») это до ~10 000 заявок в месяц,
~330 в сутки **[расчёт]**. Загрузка по одной заявке плюс проверка статуса укладывается в квоту.
Но надёжнее грузить пачками, например раз в 15–60 минут по каждому счётчику **[рекомендация]**.

**Measurement Protocol (запасной путь)** [M12]:
- Отправка событий на сервер Метрики `https://mc.yandex.ru/collect` по ClientID; нужен токен,
  который включается в настройках счётчика.
- Событие можно добавить к визиту только в течение **12 часов** после его окончания; дальше Яндекс
  предлагает офлайн-загрузку.
- История ClientID копится с момента включения, до 21 дня.
- Подходит для «события сразу», но требует отдельного токена Measurement Protocol у каждого
  счётчика и не покрывает заявки старше 12 часов **[вывод]**.

### 2.5. Почему это важно для дилера

Офлайн-конверсии нужны, чтобы Директ и отчёты Метрики видели настоящие заявки, а не только
нажатия на форме. Как именно Директ использует их в стратегиях, в этом исследовании не изучалось.

## 3. CallTouch

### 3.1. Отправка заявки

- Адрес: `https://api.calltouch.ru/calls-service/RestAPI/requests/{site_id}/register/`, GET или
  POST (`application/x-www-form-urlencoded`, UTF-8), одна заявка на запрос [C1].
- **«API-токен для создания заявок не требуется»** [C1].
- Поля [C1]:

  | Поле | Что | Обязательно |
  |---|---|---|
  | `fio`, `phoneNumber`, `email` | имя, телефон (11 цифр, приводится к 7XXXXXXXXXX), почта | хотя бы одно из трёх |
  | `subject` | название формы, до 256 символов | нет |
  | `requestNumber` | номер заявки, до 256 символов; без него — ID заявки в CallTouch | нет |
  | `requestDate` | `dd.mm.yyyy hh:mm:ss`; без него — текущее время | нет |
  | `sessionId` | сессия CallTouch на сайте; «если его не передавать, источник заявки не удастся определить» | нет, но без него нет источника |
  | `requestUrl` | адрес страницы | нет |
  | `comment`, `tags` | комментарий, теги через запятую | нет |
  | `customField[имя]` | до 20 своих полей; их надо заранее завести в настройках API в кабинете | нет |

- Ответ — JSON с `requestId`, `session`, `client`, `uniqueRequest`, `targetRequest`,
  `uniqTargetRequest` и др. `session = null`, если сессия не передана [C1].
- Ошибки [C1], [C2]:
  - пустой запрос — HTTP 200 с текстом ошибки (!);
  - 429 — превышение частоты;
  - 400 с кодами: 6 «Некорректный идентификатор сайта», 5 «Нет доступа к сайту», 2 «Передача данных
    по API отключена в настройках сайта», 3 «Сайт не активирован»;
  - 403 — неверный токен или нет прав.

  Ответ 200 ещё не значит успех: код должен проверять тело ответа **[вывод]**.

### 3.2. Доступ дилера и проверка кодом

- id сайта («ID личного кабинета») и API-токен дилер берёт в кабинете CallTouch: «Интеграции →
  Отправка данных во внешние системы → API» [C3]. Там же — `mod_id` (идентификатор счётчика
  CallTouch для скрипта на сайте) [C4].
- Мультисайтовый токен — «в настройках пользователя, во вкладке API», передаётся заголовками
  `Access-Token` и `SiteId` [C5]. Он нужен агентствам с несколькими проектами; дилеру хватает
  обычного токена **[вывод]**.
- **Проверка кодом.** Отдельного метода «проверить права токена» в документации не найдено.
  Рабочий способ — запрос журнала заявок за короткий период:
  `GET …/RestAPI/requests?clientApiId=<токен>&dateFrom=…&dateTo=…`, стоит 2 балла [C3], [C7].
  Ответ 403 или 400 с кодами из 3.1 говорит, что токен или id сайта неверны или API выключен.
  Это **[вывод]**: документация такую проверку прямо не предлагает.
- Токен только для чтения или с ограниченными правами — не найдено.
- **Следствие [вывод]:** раз для отправки токен не нужен, ошибка в id сайта дилера обнаружится
  только по ответу на первую заявку. Проверку с токеном стоит делать при подключении.

### 3.3. Лимиты

- 5 запросов в секунду с одного IP; сверх — HTTP 429 [C7].
- Система баллов: регистрация заявки — 2 балла, выгрузка журнала — 2. Суточный и часовой лимит
  задаётся на проект и виден в кабинете дилера в разделе API. Баллы списываются и за запросы
  с ошибкой. При исчерпании — 429, код 90001 [C7].
- Сколько баллов в сутки у типового проекта, не найдено: «лимит задаётся для каждого проекта» [C7].
  На 30–200 заявок в месяц это ~1–7 заявок в сутки на дилера **[расчёт]**, скорее всего мало
  **[допущение]**.

### 3.4. Как не задвоить

Задвоение возможно в трёх местах:

1. **Две заявки в CallTouch на одного клиента.**
   - Если на сайте у дилера включено автоматическое отслеживание форм CallTouch (статья
     «Отслеживание форм на сайте», не открывалась), заявку может зарегистрировать и скрипт,
     и платформа **[допущение]**.
   - В шаблоне платформы скрипт CallTouch нужен только для подмены номера и сессии; заявки
     шлёт сервер **[рекомендация]**.
   - Повторы самого клиента CallTouch отмечает: «уникальность номера определяется по номеру
     клиента, с которого он совершает свою первую заявку». Глубина настраивается в «Настройки →
     Статистика» [C8].
2. **Повторная отправка той же заявки платформой** (сбой, повтор).
   - `requestNumber` — это номер заявки в отображении [C1]. Что CallTouch отклоняет повтор
     с тем же номером, не найдено.
   - Защиту даёт сама платформа: одна заявка — одна успешная отправка, повтор только после ошибки
     **[рекомендация]**.
3. **Две конверсии в Метрике.**
   - CallTouch сам умеет передавать в Метрику «Все заявки» / «Уникальные» / «Целевые» /
     «Уникально-целевые» как офлайн-конверсии, раз в час, по своей цели [C6].
   - Если дилер это включил, а платформа тоже грузит конверсию, одна заявка даст две конверсии,
     на разные цели **[вывод]**.
   - Склейки между ними нет: цели разные **[допущение]**.
   - Выход — договориться, что для заявок с сайта источник конверсии один. См. рекомендацию.

### 3.5. Отправка из браузера (альтернатива)

CallTouch описывает отправку заявки прямо со страницы (jQuery AJAX на тот же адрес с `sessionId`)
[C9]. Для платформы это хуже серверной отправки:
- статус не виден на экране «Состояние доставки»;
- нет повтора;
- заявка уходит в CallTouch до проверки на спам и чёрный список (`REQUIREMENTS.md:94–95`)
**[вывод]**.

## 4. Письмо нескольким адресатам — Yandex Cloud Postbox

- **Как отправить.** Метод SendEmail, `Destination` с полями `ToAddresses`, `CcAddresses`,
  `BccAddresses`. В ответе один `MessageId` [P1].
- **Сколько получателей.** Квота «Получателей в одном письме» — 200, меняется по запросу [P2].
- **Как считается в тарифе:** «Если одно письмо отправляется нескольким получателям, количество
  исходящих писем считается по количеству получателей». Платится каждое принятое письмо,
  «независимо от того, будут они фактически доставлены или нет» [P3].
  - Первые 2 000 писем в месяц бесплатно [P3].
  - Цена за 1 000 с НДС: 80,32 ₽ (2 001–10 000), 70,15 ₽ (10 001–50 000), 59,98 ₽ (50 001–65 500)
    [P3]. Это совпадает с `docs/research/2026-10-16-mail-and-backups.md` (раздел 2.1).
  - Итог: письмо на 4 адреса = 4 письма в тарифе. Объём ~3 000–95 000 «писем» в месяц
    из `decisions.md` уже посчитан по числу адресов.
- **Квоты нового облака:** 1 письмо в секунду и 200 писем в сутки. Поднимаются через консоль
  квот или поддержку [P2]. Как считается 1 письмо в секунду для письма на несколько адресов,
  не найдено.
- **События доставки** уходят в Yandex Data Streams (JSON) [P4]:
  - типы: Send, Delivery, Bounce, Complaint, DeliveryDelay, Rendering Failure, Open, Click,
    Subscription;
  - по каждому адресу: Delivery — `recipients`, Bounce — `bouncedRecipients` с `diagnosticCode`,
    DeliveryDelay — `delayedRecipients`, Complaint — `complainedRecipients`;
  - события могут прийти повторно («at least once»), повтор узнаётся по `eventId`.
- **Стоп-лист** [P5]. Адрес с постоянными отказами блокируется автоматически, до 14 дней,
  снять можно только через поддержку. Отправка на него принимается и получает ID, но письмо
  не уходит: приходит Bounce с подтипом `OnAccountSuppressionList` / `Suppressed`. Опечатка
  в почте дилера проявится как Bounce, а не как ошибка запроса **[вывод]**.
- **Одно письмо или отдельное каждому.**
  - По цене разницы нет [P3].
  - Отказы приходят по адресам в обоих случаях [P4].
  - Разница в том, что в одном письме сотрудники дилера видят адреса друг друга. Скрыть их можно
    через `BccAddresses` [P1]. Что «Скрытая копия» не видна остальным, — стандартное поведение
    почты, на странице Postbox это не сказано.
- Песочница для новых аккаунтов (отправка только на подтверждённые адреса) на прочитанных
  страницах не найдена.

## 5. Что нужно от сайта (шаблон лендинга)

| Что | Откуда | Зачем | Источник |
|---|---|---|---|
| ClientID Метрики | `ym(<счётчик>, 'getClientID', cb)` или cookie `_ym_uid` | конверсия в Метрику (`ClientId`) | [M13]; cookie сейчас — [R2] `u6-gallery.html:2658` |
| yclid | параметр `yclid` в адресе страницы (ставит Директ) | конверсия по объявлению (`Yclid`) | [M8] |
| UTM | параметры адреса | уже передаются, `u6-gallery.html:2659` | [R2] |
| sessionId CallTouch | `window.ct('calltracking_params','<mod_id>').sessionId` или cookie `_ct_session_id` | источник заявки в CallTouch | [C4], [C9] |
| Номер счётчика Метрики и `mod_id` CallTouch дилера | настройки дилера в платформе | вставить скрипты в шаблон | [вывод] |
| Адрес страницы | `location.href` | `requestUrl` в CallTouch | [C1] |

Особенности:
- Cookie `_ym_uid` Метрика ставит через 6–9 с после загрузки страницы. Если клиент отправил форму
  раньше, ClientID будет пустым [R6] `cabinet-web-entry-cookies-and-formid.md:34`. `getClientID`
  с колбэком дождётся значения **[допущение]**: на странице [M13] сроки не описаны.
- Поэтому пустые ClientID, yclid и sessionId надо хранить как «нет», а не как ошибку. Заявка
  доставляется дилеру в любом случае, а в Метрику и источник CallTouch не попадает **[рекомендация]**.
- Значения хранятся без «;» на конце: сейчас интеграция Tilda пишет cookie с «;» [R5].
- **Заявки из бота.** Если чат начат на сайте («В чате», «ЛК с сайта»), ClientID и сессию
  CallTouch надо передать из лендинга в бот при старте, как сейчас делает веб-вход ([R2] `:2823`).
  Если клиент пришёл в мессенджер не с сайта, идентификаторов нет, и в Метрику такая заявка не
  попадёт **[вывод]**. В CallTouch её можно отправить без `sessionId`, но источник CallTouch
  не определит [C1].

| Шаг подключения дилера | Кто | Как |
|---|---|---|

Ручных настроек под дилера у владельца не остаётся. У дилера два ручных шага: выдать доступ
в Метрике и скопировать данные CallTouch.

## 8. Варианты

### Метрика

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **А. Один логин платформы, дилер выдаёт ему «Редактирование»; офлайн-конверсии пачками** | Решение владельца; один токен; проверка `my_grant`; дилеру не нужно авторизовать приложение | Общая квота 5 000 запросов в сутки; конверсия в отчётах через ~3–24 ч; у логина платформы полный доступ к счётчикам дилеров — его надо беречь (2FA, токен в секретах) | **рекомендую** |
| Б. Дилер сам авторизует OAuth-приложение платформы своим аккаунтом | Квота на каждого дилера **[допущение: квота на user_login]**; не нужен общий логин | Токен на каждого дилера, хранение и продление; дилер должен быть владельцем или иметь «Редактирование»; сложнее | запасной |
| В. Measurement Protocol | События почти сразу | Окно 12 часов; токен MP на каждый счётчик; не заменяет офлайн-загрузку | не рекомендую как основной |
| Г. Оставить конверсии CallTouch → Метрика | Ничего не делать в платформе | Только у дилеров с CallTouch; нет заявок «без сессии»; противоречит решению владельца | нет |

### CallTouch

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **А. Сервер платформы шлёт `register` после проверок** | Статус и повторы на экране доставки; только проверенные заявки; не нужен токен | Нужно передать `sessionId` с сайта | **рекомендую** |
| Б. Отправка из браузера | Просто | Нет статуса и повторов; спам тоже уйдёт | нет |
| В. Автоотслеживание форм CallTouch | Ничего не делать | Не видит заявки из бота; задвоение с А | нет |

### Письмо

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **А. Одно письмо, все адреса дилера в «Кому»** | Как привыкли; один MessageId; статус по каждому адресу через события | Сотрудники видят адреса друг друга (внутри одного дилера — обычно не проблема **[допущение]**) | **рекомендую** |
| Б. Одно письмо, адреса в «Скрытой копии» | Адреса скрыты | Получатель не видит, кому ещё ушло | если дилер попросит |
| В. Отдельное письмо на каждый адрес | Свой MessageId на адрес | Та же цена, больше запросов при квоте 1 письмо/с | не нужно |

## 9. Рекомендация

Это моё предложение, не факт.

1. **Метрика — вариант А.**
   - Логин платформы, дилер выдаёт «Редактирование».
   - Платформа проверяет `my_grant` при подключении и раз в сутки.
   - Цель `action` со своим идентификатором создаётся автоматически.
   - Конверсии грузятся пачкой раз в 15–60 минут по ClientId, с yclid если он есть, и с ценой
     заявки, если владелец решит её передавать.
   - Каждая заявка отправляется в Метрику один раз, номер загрузки хранится у заявки.
   - Перед этапом 7 перепроверить, какой метод загрузки актуален (пометка Deprecated [M10]).
2. **CallTouch — вариант А.**
   - Сервер шлёт заявку сразу после списания (шаг 5).
   - Поля: `phoneNumber`, `fio`, `email`, `subject` (тип заявки), `requestUrl`, `sessionId`,
     `requestNumber` = номер заявки платформы.
   - Повтор только при ошибке, не больше 5 запросов в секунду.
   - Токен берётся только для проверки при подключении.
3. **Не задваивать Метрику.**
   - В кабинете показать дилеру: «Платформа передаёт заявки в цель <имя>. Если у вас включена
     передача заявок из CallTouch в Метрику, для Директа используйте одну из двух целей».
   - Звонки из CallTouch в Метрику платформа не трогает.
4. **Письмо — вариант А** (все адреса в «Кому»).
   - Квоты Postbox поднять до запуска.
   - События доставки подключить через Data Streams, чтобы «Состояние доставки» показывало статус
     по каждому адресу.
5. **Сайт.** Шаблон сохраняет ClientID, yclid, UTM и sessionId CallTouch в заявку и передаёт их
   боту при старте чата. Пустые значения не блокируют доставку письма.

## 10. Вопросы владельцу

1. Заявки «По телефону»: какой робот шлёт им письмо? В условии робота на скриншоте этого типа нет.
   Нужно ли платформе слать по ним CallTouch и Метрику? (`REQUIREMENTS.md:90`: доставляются
   «как обычно».)
2. «Тип лида 1» = «В мессенджере» — откуда это значение? В справочнике полей его нет. Это заявки
   бота, начатые в мессенджере без сайта?
3. Что такое «{{Идентификаторы посетителя}}» в роботе Метрики: поле «Ya_id» (`_ym_uid`) или поле
   приложения? И что в «{{Сумма}}»: цена заявки для дилера или сумма из сделки? Нужно ли
   платформе передавать в Метрику цену?
4. Передаёт ли сейчас CallTouch у дилеров заявки в Метрику (интеграция «Яндекс.Метрика» в кабинете
   CallTouch)? Если да, какой источник конверсий оставить дилерам для Директа?
5. Включено ли на сайтах дилеров автоматическое отслеживание форм CallTouch? Если да, при прямой
   отправке будут двойные заявки в CallTouch.
6. Логин Метрики для платформы: отдельный аккаунт Яндекса на организацию, хранится у владельца?
   (Нужен до этапа 5; к нему у агентов доступа нет.)
7. Письмо: все адреса в «Кому» (видно всем) или в «Скрытой копии»?
8. Заявки из мессенджера без сайта в Метрику не попадут — принимаем?
