## 2. Бот

**Скрипты с записью во внешние сервисы** (только с флагом `--apply`; адреса и ключи — из `.env`):

- `scripts/register_webhooks.py` — регистрирует и снимает вебхуки ботов MAX и Telegram;
- `scripts/bx_delete_test_deals.py` — удаляет сделки и контакты в Битриксе;
- `scripts/issue_cabinet_link.py` — пишет токен кабинета в базу бота (только localhost).

Жёстко прописан только адрес MAX API по умолчанию; без токена из `.env` запросы не проходят. Если рядом положить
`.env` старой системы — скрипты пишут в старый бой.

**Ранбуки** в `bot/CLAUDE.md` и `bot/docs/handoff/` содержат готовые команды к старому бою (Dockhost, n8n). К новой
платформе не относятся.

**Тесты:** 1490 проходят, 29 падают без `.env` старой системы (нет полей `UF_CRM_…` Битрикса) — так же и в нетронутом снимке.

**Урок инцидента 12–13.10 (≈22 ч без Dialogflow).** С v3.4.2 образ собирался из `git archive`, а `credentials.json` в
`.gitignore` — ключ не попал в образ. Не поймали, потому что: не сравнивали список файлов нового образа с боевым;
клиент Dialogflow создаётся при каждом вызове — старт сервиса был чистым; живая проверка после выкатки касалась
только веб-входа. Принятые правила:

- сразу после смены образа — живой старт по коду в MAX и Telegram, проверка лога на ошибки ключа; не сошлось — откат;
- сборка из `git archive` без ключей; ключи — только из окружения сервера;
- образы с секретами в реестр отправляет только владелец.

Вывод для новой платформы: самопроверка ключей при старте сервиса (с сигналом, если ключ не загрузился) и
обязательная живая проверка после каждой выкатки.

## 3. n8n

**Зависимости внутри снимка:**

- `nocodb/build_v3_workflow.py` берёт узлы из `flow/AI Agent v2.0 MAX.json` — файл нужен;
- `flow/lib/pipeline_sim.test.mjs` читает два файла из `flow/archive/2026-07-05-baseline/` — перенесены только они;
- генераторы пишут `pinData` пустым и на него не опираются; сверка `check_sources_vs_live.py` поле `pinData` пропускает.

**Отличия снимка от боевого n8n** (полный перечень — `n8n/SOURCE.md`): заглушка вместо ключа Auto.ru, пустой `pinData`,
вымышленные госномера в комментариях `jsCode`. Учитывать при первой сверке в новой системе.

**Ключ Auto.ru** перевыпустить нельзя. В новой системе — тот же ключ, из хранилища ключей n8n, не из репозитория.

**Скрипты с записью во внешние сервисы:** около 8 пишут в n8n (`flow/cabinet-web-entry/api/…`), около 20 — в NocoDB
(`nocodb/add_*`, `apply_*`, `fix_*`, `push_tables.py`, `cleanup_stale_notes.py`), два косвенно доходят до Битрикса
(`run_save_crm_test_once.py`, `nocodb/debrand_testruns.py`). Список — `n8n/SOURCE.md`. Без задачи владельца и без
адресов и ключей новой системы не запускать.

**Сверка «генератор = бой»** — `flow/cabinet-web-entry/api/check_sources_vs_live.py` (только чтение);
ожидаемые расхождения — `expected_divergences.json`.

## 4. Лендинг — что не видно из кода

**Блоки живут только внутри страницы Tilda:**

- опираются на jQuery Tilda, на штатные блоки **T809** (выбирает Hero по UTM-метке и удаляет остальные варианты),
  T270 и T390, на форму `.uc-tildaform` со скрытыми полями из редактора и на `data-tilda-req`;
- Tilda ставит `box-sizing: content-box` на все элементы, склеивает CSS и JS всех блоков в общий контекст
  (отсюда `var` и `window.*`) и подменяет `onerror` у тегов — поэтому в коде `addEventListener('error')`;
- порядок на странице важен: U1 после T809, форма выше U2.

**Настройки сайта вне кода:**

- форма содержит только `dealer_id`;
- цвет кнопки вписывается в первую строку U1 вручную при вставке;
- preconnect к боту прописан в HEAD сайта;
- остальные настройки приходят из NocoDB (`Dealers`) через бота.

**Выкладка ручная:** владелец вставляет блоки; лимит блока T123 — 100 000 байт; блоки вставляются парами (U2 с U6,
U1 с U2). Расхождение копии и сайта видно только через `check-live.py` — в новую платформу не перенесён.

**Зависимости от бота:** `/cabinet/api/dealer/`, `/catalog/`, `/bot-links`, `/cabinet/api/web/open`,
`/widget-custom/widget.js`, `/widget-custom/vendor/`. Telegram и MAX обязательны для каждой марки. Тестовая страница
показывает данные, только пока поднят дев-стенд бота через ngrok.

**Решения, которые нельзя «чинить»:** собственная проверка согласия; класс `swiper` снят с галереи; `loop: false`;
попытка входа в кабинет хранится только в памяти страницы (повторная сделка принята); эксперимент с калькулятором
в `archive/Ver_4_u6_calc_experiment/` отменён.

**U5 нет сознательно:** выбор мессенджера живёт в U6; контакты — U7, чтобы не путать с архивным U5.

**Сборка:** читает только `docs/tilda-blocks/Ver_4_dev/`; `terser` и `clean-css` приходят транзитивно (не прописаны в
`package.json`), версия Node не закреплена. Стендам нужны python3, playwright, Chromium и сеть.

**Ключ API Яндекс.Карт** — браузерный, в `u7-contacts.html` и сборках; виден на живых страницах.

**Открытые хвосты старого лендинга:** заголовки кэша `/catalog` и `/bot-links` на стороне бота (бриф не передан);
запрос характеристик и ставок после каталога; P3 из плана 2026-10-12-001.

## 5. Что придётся заменить своим в новой платформе (вывод)

| В старой системе | В новой платформе |
|---|---|
| T809 Tilda выбирает Hero по UTM | своя логика: правило «параметр = значение → пресет Hero» |
| Форма Tilda + вебхук в Битрикс | заявка сразу в модуль заявок платформы |
| `dealer_id` в форме, цвет кнопки в U1, preconnect в HEAD — руками | всё из настроек дилера и марки |
| jQuery, T270/T390, общий контекст JS Tilda | свой шаблон страницы без зависимости от Tilda |
| Ручная вставка блоков, лимит 100 000 байт | публикация шаблона платформой |
| `check-live.py` по живым сайтам | своя проверка опубликованных страниц |
| Битрикс: хранение заявок, письма, CallTouch, Метрика | модуль заявок и доставки |
| Ключи из `.env` / файлов старой системы | ключи только из окружения нового сервера; самопроверка при старте |
