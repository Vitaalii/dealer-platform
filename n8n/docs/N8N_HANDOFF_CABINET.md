# ТЗ для Alex_refactoring: данные оценки трейд-ина для личного кабинета

Дата: 2026-08-10. Адресат — CE проекта Alex_refactoring. Контекста кабинета у тебя
нет — этот документ самодостаточен, читать код кабинетного репозитория не нужно.

**Минимум контекста.** У бота появился клиентский личный кабинет (страница на
Tilda + API бота): клиент подтверждает телефон кодом и заполняет анкету, а с
недавнего времени — видит кредитный калькулятор, который считает в браузере на
тех же формулах `calc_engine.js`, что и твой Calc Engine в n8n. Входные данные
расчёта (позиция, цена, ставки, программа) бот **замораживает в снапшот** в
момент выдачи ссылки и на каждом ходе диалога — чтобы клиент видел те же цифры,
что называл Александр, даже если живые ставки сменятся. Для анкет трейд-ина и
комбо кабинету нужны данные оценки auto.ru — сейчас они до бота не доходят.
Отсюда две задачи ниже.

## 1. Задача 1 — доставить данные оценки auto.ru в бот

### Что сейчас

Результат оценки (`found_info` из ответа
`apiauto.ru/1.0/stats/partner/predict_by_vin_or_lp`) и посчитанная сумма зачёта
живут только внутри n8n: как observation тула `evaluate_auto` (контекст LLM) и
в tool-ответе Combo Calculator (`tradein_evaluation` в `combo_prepare.js`).
Наружу, в бот, ничего из этого не уходит — ни в колбэк Save-to-CRM, ни в
`json_cache`.

### Канал доставки — уже работает

Нода **Final Response** в `AI Agent v3.0.json` возвращает боту
`{ text, json_cache, session_context_update }`; `json_cache` бот сохраняет как
есть (`n8n_cache` в контексте пользователя) и возвращает тебе же в
`qualification_context.cached_json` на следующем ходе. Сейчас `json_cache`
наполняется только результатами Car Search (цепочка Cache Gate → Attach
Cache). Нужно класть в этот же объект данные оценки — приёмная сторона бота
уже готова и ждёт **два ключа верхнего уровня** `json_cache`:

| Ключ | Тип | Что это |
|---|---|---|
| `found_info` | object | Блок `found_info` из ответа auto.ru **целиком, как отдаёт сервис** (mark, model, year, steering_wheel, mileage, photos, owners_count, pts_original и всё прочее — не фильтруй) |
| `ti_valuation` | number | Сумма оценки трейд-ина (та, что сейчас `estimated_value` / `tradein_price_to` в combo-ветке) |

Точки чтения на стороне бота (для справки, лезть туда не нужно):
`cabinet_service.py:2733–2735` — `n8n_cache.get("found_info")` /
`n8n_cache.get("ti_valuation")` при заморозке снапшота; из `found_info` кабинет
рендерит блок «Ваш автомобиль» по ключам `mark`, `model`, `year`,
`steering_wheel` (код LEFT/RIGHT — бот сам переводит в «Левый/Правый»),
`mileage`, `plate`, `photos.main`; отсутствующие ключи просто не показываются.

### Госномер — отдельно, иначе потеряется

**В ответе auto.ru госномера нет** — он был только во входных параметрах твоего
запроса к сервису (клиент продиктовал его Александру). Если положить в
`json_cache` только сырой ответ, клиент увидит блок «Ваш автомобиль» без
госномера. Удобнее всего — **вложить его внутрь `found_info` под ключом
`plate`** (именно этот ключ ждёт фронт кабинета). Ожидаемая структура целиком:

```json
{
  "user_request": { "...": "как сейчас" },
  "complectations": [ "...как сейчас..." ],
  "found_info": {
    "mark": "KIA",
    "model": "Rio",
    "year": 2019,
    "steering_wheel": "LEFT",
    "mileage": 87000,
    "photos": { "main": "//avatars.mds.yandex.net/get-verba/..." },
    "owners_count": 2,
    "pts_original": true,
    "plate": "А123БВ777"
  },
  "ti_valuation": 890000
}
```

(`found_info` — сырой ответ сервиса плюс один добавленный ключ `plate`;
остальные поля auto.ru, не показанные в примере, оставляй как есть.)

### Чего делать НЕ надо

- **Не нормализуй URL фото.** `photos.main` приходит протокол-относительным
  (`//avatars.mds.yandex.net/...`) — бот дополняет до `https:` сам при
  заморозке. Нормализация на стороне n8n не нужна и не следует её делать.
- Не переименовывай и не «причёсывай» ключи `found_info` — контракт «как отдал
  сервис», любые преобразования на стороне бота.
- Не клади данные оценки в `ai_payload` колбэка Save-to-CRM — этот канал бот
  не разбирает на эти поля, работать не будет.

### Сценарии без трейд-ина — не сломать

Оценка выполняется не в каждом диалоге (чисто кредитные и стоковые сценарии её
не имеют). Контракт на этот случай: **ключей просто нет** в `json_cache`
(или `null` — бот трактует одинаково: `found_info` не-dict → null). Ничего
не подставляй, пустые объекты не клади — кабинет в этом случае показывает
редактируемые поля «Ваш автомобиль» (текущее поведение), это штатно.
Правка не должна затронуть наполнение `json_cache` Car Search'ем: `found_info`
/ `ti_valuation` — добавка к существующему объекту, не замена.

Обрати внимание на Cache Gate: `json_cache` пересобирается не на каждом ходе
(`fresh_cache || cached_json`). Данные оценки должны переживать этот механизм —
появившись после `evaluate_auto`, оставаться в `json_cache` на последующих
ходах (иначе бот заморозит снапшот без них на следующем же ходе).

## 2. Задача 2 — промпт: сначала комплектация, потом ссылка

Калькулятор кабинета считает по снапшоту, а снапшот замораживается по
**выбранной комплектации** (`user_request.selected_complectation_id` в
`json_cache`). Если Александр выдаёт ссылку на кабинет до того, как клиент
выбрал конкретную комплектацию, снапшота нет: клиент получает кабинет без
калькулятора, с ручным вводом трёх полей. Формально это штатная деградация,
фактически — потеря главной новой функции.

Нужна правка промпт-блока: **довести подбор до выбора конкретной комплектации,
и только после этого предлагать ссылку на кабинет.** Готовая формулировка — в
`docs/CABINET_PROMPT_NOTE.md` кабинетного репозитория (раздел «Дополнение
2026-08-10», прилагаю вместе с этим ТЗ); там же — базовая вставка про
`cabinet_url`/`cabinet_status`, если она ещё не внесена. Промпт-блоки живут в
NocoDB; у тебя есть `Prompts.csv` и папка `nocodb/` — где именно править,
решай по своим конвенциям.

## 3. Проверка результата

Проверяй на своём тест-контуре с `[TEST]`-копиями воркфлоу, не на боевых.

1. **Данные доехали до контекста бота.** После диалога с оценкой (сценарий
   трейд-ин/комбо, госномер продиктован) — запрос к дев-базе бота:

   ```sql
   -- SQLite (дев):
   SELECT json_extract(context_json, '$.n8n_cache.found_info'),
          json_extract(context_json, '$.n8n_cache.ti_valuation')
   FROM users WHERE platform_user_id = '<id клиента>';

   -- PostgreSQL:
   SELECT context_json::json #> '{n8n_cache,found_info}',
          context_json::json #> '{n8n_cache,ti_valuation}'
   FROM users WHERE platform_user_id = '<id клиента>';
   ```

   Правильный результат: первый столбец — JSON-объект с `mark/model/year/
   steering_wheel/mileage/plate/photos`, второй — число. Оба `NULL` — данные
   не доехали (смотри, кладёт ли их Final Response и переживают ли Cache Gate).

2. **Заморозка подхватила.** В логе бота на ближайшем ходе после появления
   данных: `cabinet: снапшот калькулятора user=<id> заморожен: item_id=...`
   (строка без исключений). Содержимое снапшота:

   ```sql
   SELECT json_extract(calc_snapshot, '$.found_info.plate'),
          json_extract(calc_snapshot, '$.ti_valuation')
   FROM cabinet_profile WHERE user_id = <PK users.id>;
   ```

   Непустые значения = контракт выполнен целиком. (Замечание: снапшот
   замораживается по выбранной комплектации — в тестовом диалоге доведи подбор
   до выбора, см. Задачу 2.)

3. **Сквозная проверка (по желанию):** клиент проходит верификацию в кабинете →
   `GET /cabinet/api/me` отдаёт `calc.found_info` и `calc.ti_valuation`; в
   анкете трейд-ина появляется read-only блок «Ваш автомобиль» с фото
   (протокол-относительный URL уже дополнен до `https:` ботом), в комбо —
   строка «Зачёт вашего автомобиля — 890 000 ₽».

Контакт — владелец кабинетного репозитория. Спорные места (структура
