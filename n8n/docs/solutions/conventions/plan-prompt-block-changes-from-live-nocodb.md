# Правки промпт-блоков планировать только от живой NocoDB, катить черновиками Active=false

## Context

План «нарезать T-01_TOOLS на T_FINALIZE/T_EVALUATE/T_COMBO», принятый в прошлой сессии, дважды разошёлся с реальностью при исполнении (2026-07-16):

1. T-01_TOOLS оказался целиком правилами `finalize_deal` (3028 зн.), а не описанием трёх инструментов, как предполагалось по памяти прошлой сессии.
2. Владелец контента уже сам сделал гранулярные tool-инструкции: живые ST_TRADEIN_TOOL_NEEDED / ST_COMBO_TOOL_NEEDED (активные) — это сжатые ШАГ 2–3 из legacy. Созданные по старому плану T_EVALUATE/T_COMBO дублировали его работу и были удалены в тот же заход.

Живая таблица к тому моменту ушла далеко от локального CSV-снапшота: 98 блоков против 53, WF_CREDIT_LEGACY и монолитные OBJ_* выключены, возражения переведены на primary-блоки BLK_* (например BLK_CREDIT_ADVOCATE). Два кейса офлайн-симуляции, написанные по старому снапшоту, упали именно из-за этого дрейфа — не из-за правок кода.

## Guidance

1. **Канонический источник — живые таблицы NocoDB** (с 2026-07-13 владелец правит контент и каркасы прямо в UI). Локальные `nocodb/*.csv` — стартовый снапшот, по нему нельзя ни резать тексты, ни оценивать, что где активно.
2. **Перед исполнением плана из прошлой сессии — перечитать живое состояние** затронутых блоков и карты (Active-флаги, наполнение стабов, новые Block_ID). План пересматривается по фактам, даже если был согласован: часть работы могла уже быть сделана владельцем в другом виде.
3. **Выкатка правок блоков — двухфазная, через черновики:**
   - новые строки добавляются с уникальным Block_ID, `Active=false`, `Version_Set` следующей версии и Notes с инструкцией активации (компилятор собирает blocks в словарь по Block_ID — дубликат ID молча затёр бы живую строку);
   - компилятор предпочитает новый блок при `Active=true`, иначе сохраняет старое поведение (пример v3.01: `const voiceId = active("G-02_VOICE_V2") ? "G-02_VOICE_V2" : "G-02_VOICE"` и фолбэк `T_FINALIZE` → `T-01_TOOLS` по `tools_open`);
   - переключение делает владелец одним заходом в NocoDB (включить новые, выключить старые), без реимпорта воркфлоу.
4. **Симуляцию гонять на свежем снапшоте живых таблиц** (`nocodb/add_needcheck_v303.py --snapshot-only --snapshot <path>`, ранее `add_v301_draft_blocks.py`), а **оба** состояния — и «до активации», и «после активации» — строить мутацией клона снапшота (`structuredClone` + перещёлкивание Active, flip/flipBack), не отдельными фикстурами и не чтением сырого снапшота. **Сырое содержимое снапшота не считать фиксированным ни «pre», ни «post»:** снапшот отражает живые таблицы на момент снятия, поэтому после `--activate-drafts` он становится пост-активационным, и кейс, ассертящий сырой снапшот как «до активации», молча ломается ровно в момент выкатки (инцидент 2026-07-22: два need-check-кейса `v3_pipeline_sim`/`resolver_prompt_sim` упали сразу после активации черновиков v3.03, хотя код тестов и пайплайна не менялся; починка — вывод обоих состояний обратной мутацией клона). Каждую мутацию сопровождать громкой проверкой существования строки (`assert(row, "…нет в снапшоте — пересоберите …")`), чтобы устаревший снапшот падал явно, а не тихо.
5. **Падение старого теста после снятия свежего снапшота — сначала проверить дрейф таблиц**, потом подозревать регрессию кода: ожидания кейсов фиксируют состояние контента на момент написания.

## Why This Matters

Контент правит не-разработчик параллельно с рефакторингом кода — это принятое ограничение проекта. Любой план, опирающийся на снапшот или память прошлой сессии, устаревает за дни: здесь это стоило бы дублей инструкций в промпте (то, с чем боремся — раздутый промпт ≥9k токенов) и затирания работы владельца. Двухфазная выкатка черновиками даёт владельцу контроль над моментом переключения и мгновенный откат чекбоксами, при этом код можно патчить заранее.

## When to Apply

- Перед любой правкой строк Prompt_Blocks / Intent_Block_Map или логики Prompt Compiler
- При исполнении согласованного ранее плана, если между планированием и исполнением прошло время
- При падении кейсов v3_pipeline_sim после обновления снапшота таблиц

## Examples

Было (план прошлой сессии): резать T-01 на три tool-блока по текстам из CSV.

Стало (после сверки с живой таблицей): только `T_FINALIZE` (finalize-правила 1:1, показ на closing/finalize_required) + `G-02_VOICE_V2` (сжатие 3365→2033 зн.); роль T_EVALUATE/T_COMBO уже выполняли живые ST-блоки владельца. Эффект тот же: −~757 токенов на tool_needed-ходах, −~333 токена на каждом ходе, без дублей.

Фолбэк в компиляторе (переходное состояние, пока владелец не активировал черновики):

```js
if (useTFinalize) parts.push(content("T_FINALIZE"));
// переходный фолбэк: пока T_FINALIZE не активирован владельцем — старый T-01 по tools_open
else if (turn.tools_open && active("T-01_TOOLS")) parts.push(content("T-01_TOOLS"));
```
