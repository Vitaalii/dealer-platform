# Изоляцию прогонов на `[TEST]` доказывать кодом обработчика callback, а не входными данными

## Context

Перед приёмкой де-брендинга (2026-09-16) нужно было гарантировать, что 45
прогонов на `[TEST]` не создадут сделок в боевом Bitrix и не пошлют алертов в
группы дилеров.

Первая попытка рассуждать «подберём такой вход, чтобы модель не дошла до
финализации» провалилась по построению графа:

```
finalize_deal --ai_tool--> Agent
finalize_deal --ai_tool--> Agent Retry
```

Тулы привязаны к нодам агента **связями графа, а не условием**. Флаг
`tools_open` из `Stage Classifier` управляет только составом промпт-блоков.
Значит, **никакой вход не может запретить модели вызвать `finalize_deal`** — а
её недетерминизм и есть то, что проверяется приёмкой (инцидент #4084: 2
расхождения из 6 на побайтово одинаковых входах).

Дополнительно: `[TEST] AI Agent v3.0` побайтово совпадает с продом по всем 14
code-нодам и читает **те же** таблицы NocoDB. «Тестовый» он только по
саб-воркфлоу и вебхуку.

## Guidance

**Изоляция доказывается чтением кода принимающей стороны, а не конструкцией
входа.** Порядок проверки:

1. **Куда ведёт цепочка CRM тестового контура.** `[TEST] finalize_deal` и
   `Save CRM Direct` → `TOOL: Save to CRM_test` (`12IRy1rcYOuZzV7m`) → ngrok-адрес.
   За ним — **дев Python-бот, у которого есть доступ к боевому Bitrix**
   (установлено владельцем 2026-09-16). То есть «другой хост» изоляции не даёт.
2. **Что делает обработчик `/n8n_callback` при данных прогона.** Читать код, а
   не предполагать. Для `main.py:814`:

   | Что | Строка | При пустом `deal_id` и неизвестном `user_id` |
   |---|---|---|
   | блок Bitrix целиком | `main.py:889` | `if bx_url and deal_id:` — **пропускается** |
   | создание сделки/контакта | `main.py:312`, `331` | `crm.deal.add` / `crm.contact.add` в обработчике **не вызываются вовсе** |
   | отключение бота | `main.py:856` | `UPDATE ... WHERE platform_user_id = <unknown>` — 0 строк, INSERT нет |
   | архив NocoDB | `main.py:656`, вызовы `1944`, `2349` | пишется только из путей отправки сообщения клиенту — при прямом вызове вебхука n8n не выполняется |
   | алерт в группу | `main.py:914` → `955` | **единственная возможная внешняя запись**, при `status in ["visit","call"]` |

3. **Практическое правило: не передавать `deal_id`.** Один этот ключ отсекает
   всю работу с Bitrix на стороне бота. В n8n `Edit Fields` выставит
   `deal_id = null`, и обработчик уйдёт мимо блока.

**Полный набор правил прогона:**

- `deal_id` не передавать;
- `user_id` с явным тестовым префиксом (`test-debrand-`, `test-`) — таких нет в
  БД бота, поэтому `UPDATE User` не заденет ни строки;
- дилер `99` (тестовый дилер дев-стенда) в `qualification_context.dealer_id` и в
  первых двух символах `start_code`;
- `qualification_context.cached_json` заполнить — тогда `Cache Gate` уведёт ход
  мимо `Call Car Search`, и обращений к складам и каталогам дилеров не будет;
- после прогонов **посчитать фактические вызовы** `finalize_deal` по
  `intermediateSteps` исполнений, а не полагаться на «не должно было».

## Ловушка с маршрутизацией алерта

Группа для алерта выбирается по `start_code` из БД бота (`main.py:947-952`), а
**не** по коду дилера из payload. Для неизвестного `user_id`
`load_context_from_db` вернёт `{}`, префикс станет `"00"`, `Max_Group_ID` не
найдётся и сработает фолбэк на `SUPPORT_GROUP_ID` (`main.py:69`). То есть алерт,
если случится, уйдёт **в группу поддержки дев-образа, а не в группу дилера 99**.
Код дилера во входе на это не влияет.

## Why This Matters

«Тестовый контур» здесь означает только другой вебхук и форкнутые
саб-воркфлоу. Код нод, таблицы NocoDB и модель — те же, а принимающий бот имеет
боевые доступы. Рассуждение «вход подобран так, что финализации не будет»
неверно по построению графа и не выдерживает недетерминизма модели. Единственное
надёжное основание — что принимающий код физически не может создать запись при
таких данных.

На приёмке 2026-09-16 правила сработали: 45 прогонов, вызовов `finalize_deal` —
**0** на 47 сопоставленных исполнениях, внешних записей — 0.

## When to Apply

- Перед любыми прогонами на `[TEST]`, доходящими до нод `Agent` / `Agent Retry`
- При оценке «безопасно ли гонять приёмку» в плане
- При появлении нового тула, привязанного к агенту
