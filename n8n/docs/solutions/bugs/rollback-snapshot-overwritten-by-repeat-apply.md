# Повторный `--apply` перезаписал снапшот отката уже применённым состоянием

## Context

Правка `apply_debrand_blocks.py` (де-брендинг четырёх блоков, 2026-09-16) шла по
протоколу репозитория: снапшот «до» → PATCH по одной записи → сверка чтением.
После первого `--apply` проверили откат на одном блоке (`--rollback --only
G-02_VOICE_V2`), убедились, что блок вернулся в исходный `sha df0fa3bcf287`, и
запустили `--apply` второй раз, чтобы вернуть его в правленое состояние.

Второй `--apply` **переписал снапшот текущим состоянием базы**. Для трёх
остальных блоков текущее состояние было уже ПРАВЛЕНЫМ, поэтому в файле отката
вместо состояния «до» оказалось состояние «после»:

```
BLK_CREDIT_REFERENCE     sha=b928a9281ba5 ожидали=a634147e9730  ЭТО СОСТОЯНИЕ ПОСЛЕ
BLK_TRADEIN_REFERENCE    sha=d73e6bbdba19 ожидали=2192621719ce  ЭТО СОСТОЯНИЕ ПОСЛЕ
BLK_COMBO_REFERENCE      sha=d73e6bbdba19 ожидали=2192621719ce  ЭТО СОСТОЯНИЕ ПОСЛЕ
G-02_VOICE_V2            sha=df0fa3bcf287 ожидали=df0fa3bcf287  OK
```

Откат для трёх блоков из четырёх перестал существовать. Ни одна проверка
протокола этого не заметила: `write_verified` сверяет запись, а не снапшот, и
все четыре PATCH прошли успешно. Коварство ровно в этом — **чем аккуратнее
работаешь (проверил откат перед тем, как на него полагаться), тем вернее
ломаешь путь отката**.

## Guidance

1. **Снапшот пишется РОВНО ОДИН РАЗ, при первом `--apply`.** Если файл уже
   существует — не трогать его ни при каких условиях.
2. **Отсутствие блока в существующем снапшоте — стоп, а не «допишу».** Если
   собираемся писать блок, которого в снапшоте нет, откатывать его будет нечем:
   останавливаемся и требуем осознанного решения.
3. **Удалять файл снапшота можно только вместе с откатом уже применённого** —
   иначе следующий `--apply` снимет «снапшот до» с наполовину правленой базы.
4. **Проверять сам снапшот, а не только запись.** После любого прогона, который
   мог его задеть, сверять sha записей в файле с задокументированными BASE_SHA.

Реализация (`nocodb/apply_debrand_blocks.py`):

```python
SNAPSHOT.parent.mkdir(parents=True, exist_ok=True)
if SNAPSHOT.exists():
    print(f"снапшот уже есть, НЕ перезаписываю: {SNAPSHOT.relative_to(ROOT)}")
    saved = set(json.loads(SNAPSHOT.read_text(encoding="utf-8")))
    gap = [bid for bid, *_ in todo if bid not in saved]
    if gap:
        sys.exit(f"ОСТАНОВ: в снапшоте нет блоков {gap}, а писать их "
                 f"собираемся — откатывать будет нечем.")
else:
    SNAPSHOT.write_text(...)
```

Проверка гарда — сравнение md5 файла до и после повторного прогона.

## Why This Matters

Снапшот — единственный путь отката правки живой боевой таблицы, которую
Prompt Compiler читает на каждом ходе. Его порча не диагностируется ничем в
штатном протоколе: скрипт рапортует «записано 4 блока», сверка чтением
зелёная, а откатиться уже нельзя. Обнаружить это можно только отдельной
проверкой содержимого снапшота — либо в тот момент, когда откат понадобился,
то есть в самый неподходящий.

## How It Was Found And Fixed

**Обнаружено** явной сверкой содержимого снапшота с задокументированными в
плане BASE_SHA сразу после проверки отката — не автоматикой, а потому что
операция «откат + повторный apply» выглядела подозрительной и её решили
перепроверить.

**Восстановлено** из полного дампа таблицы (все 134 блока), снятого в той же
сессии ДО первой записи. Корректность подтверждена двумя независимыми
способами:

1. sha всех четырёх блоков из дампа совпали с BASE_SHA, записанными в плане;
2. обратная замена текущего текста (`MODEL_NEW → MODEL_OLD`,
   `VOICE_NEW → VOICE_OLD`) дала побайтово тот же результат, что дамп.

Отсюда практика: **перед первой записью снимать полный дамп таблицы отдельно
от снапшота скрипта**. Он дешёвый, и он спасает, когда снапшот испорчен.

## When to Apply

- При написании любого нового `apply_*.py` по образцу репозитория
- Перед вторым и последующими запусками `--apply` любого существующего скрипта
- После любой операции «частичный откат → повторное применение»
