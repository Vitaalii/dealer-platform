# Форму observation тула в n8n нельзя предполагать — читать по форме данных, а не по пути

## Context

Юнит U3 плана 2026-08-10-001 доставляет данные оценки трейд-ина в `json_cache`,
извлекая их из `intermediateSteps` агента. Реализация была покрыта 25 проверками
и 16 кейсами симуляции — все зелёные. На стенде юнит не сработал **дважды подряд**,
каждый раз молча: ключи просто не появлялись, ошибок не было.

Три предположения о форме оказались неверны, и все три вскрылись только на живых
исполнениях:

1. **Исполнение #2999 (трейд-ин).** `observation` приходит не объектом, а **строкой
   с массивом item'ов**: `'[{"status":"SUCCESS",...}]'`. Код делал `JSON.parse` и
   читал `obs.status` — то есть поле массива, всегда `undefined`. Проверка
   `typeof obs !== "object"` такой вход не отсекала: `typeof [] === "object"`.
2. **Исполнение #3050/#3048 (комбо).** Нода `Merge Calc` **снимает обёртку**
   `response`, которую формирует `combo_prepare.js`. Код читал
   `item.response.tradein_evaluation` — `item.response` не существует.
3. **Исполнение #3048.** Тул называется `Combo_Calculator` (подчёркивание), а не
   `Combo Calculator`. Разводка по имени тула — третья точка хрупкости.

Общее у всех трёх: **оффлайн-тесты были зелёными на фикстурах, которые я сам и
придумал**. Тест проверял код против предположения, а не против реальности.

## Guidance

1. **Фикстуру для ноды, потребляющей ответ тула, снимать с живого исполнения**, а
   не сочинять. Минимальный путь: `GET /executions/<id>?includeData=true` →
   `data.resultData.runData.<Нода>[0].data.main[0][0].json`. В кейс класть форму
   дословно и подписывать номером исполнения — тогда видно, чем она подтверждена.
2. **Извлекать по форме данных, а не по фиксированному пути и не по имени тула.**
   Стабильна только форма записи. Рабочий приём — нормализовать вход и просканировать
   кандидатов:

   ```js
   // строка -> значение; объект -> [объект]; массив -> он сам
   const items = Array.isArray(obs) ? obs : [obs];
   // и сам item, и возможная обёртка response
   const records = evalRecordsFrom(item).concat(evalRecordsFrom(item.response));
   ```

   где `evalRecordsFrom` распознаёт известные формы (`node.tradein_evaluation`
   либо `node.status` + `node.tradein_price_to`) и возвращает нормализованные записи.
3. **`typeof x === "object"` не отличает массив от объекта.** Там, где ожидается
   именно объект, проверять `!Array.isArray(x)` явно — иначе массив проедет дальше
   и даст `undefined` на первом же обращении к полю.
4. **Молчаливое «ничего не нашли» — плохой контракт для отладки.** Юнит корректно
   реализовывал «нет оценки → ключей нет», и это же поведение маскировало баг: с
   живого стенда «оценки не было» и «форму не разобрали» выглядят одинаково. Если
   ход шёл через тул оценки, а запись не распозналась — это стоит логировать.

## Why This Matters

Оба прогона дошли до стенда и до ручной проверки SQL в базе бота, то есть цена
ошибки — полный цикл «правка → импорт → диалог → запрос к базе → разбор», дважды.
При этом сама починка каждый раз занимала минуты: диагностика по исполнению давала
точную точку разрыва сразу. Дешевле было снять фикстуру с первого живого прогона,
чем трижды угадывать форму.

## When to Apply

- Перед написанием кода, читающего `intermediateSteps`, ответ `executeWorkflow`-ноды
  или любой чужой сериализованный вывод внутри n8n
- При зелёных оффлайн-тестах и неработающей функции на стенде — первым делом
  сверять форму фикстуры с живым исполнением, а не искать логическую ошибку
- При ревью правок, где встречается `x.some.fixed.path` по данным из другой ноды
