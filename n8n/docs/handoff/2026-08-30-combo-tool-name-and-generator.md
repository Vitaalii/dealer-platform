### 1.4. Установленная причина

**Имя инструмента в промпте не совпадает с именем, объявленным модели.**

n8n выводит имя функции для модели из имени **узла**, заменяя пробелы
подчёркиваниями. Узел назывался `Combo Calculator` → модели объявлялась функция
`Combo_Calculator`. Промпт-блоки комбо-сценария предписывают вызвать
`combo_calculator` (строчными).

Расхождение в блоках NocoDB `Prompt_Blocks` (активные на момент инцидента):

```
CS_COMBO_V2              …до ответа инструмента combo_calculator
ST_COMBO_TOOL_NEEDED_V2  …немедленно и МОЛЧА вызови инструмент `combo_calculator`
```

Ни в одном блоке правильного написания `Combo_Calculator` не было. Всего имя в
нижнем регистре встречается в семи блоках: `CS_COMBO_V2`,
`ST_COMBO_TOOL_NEEDED_V2` (активные), `CS_COMBO`, `ST_COMBO_TOOL_NEEDED`,
`WF_COMBO_LEGACY`, `CS_COMBO_LEGACY`, `D_COMBO` (неактивные).

**Подтверждение фактом.** В контрольном прогоне 2026-08-28 (исполнение **3521**,
дословный повтор тела запроса из 3517, модель уже `gemini-3.1-flash-lite`)
модель вызвала инструмент под именем:

```
ВЫЗВАН: 'Combo_Calculator'  аргументы={"plate":"х318те750","mileage":"36000"}
```

То есть объявленное имя действительно было `Combo_Calculator` с подчёркиванием
и заглавными.

**Контраст с трейд-ином.** Узел `evaluate_auto` пробелов в имени не содержит,

## 3. Установленные ограничения инструментов

Проверено экспериментально. Не выясняйте заново.

### 3.1. Публичный API n8n не может писать этот воркфлоу

Схема API отвергает поле `binaryMode`, которое есть в живых настройках
`[TEST] AI Agent v3.0`. Перебор на одноразовых воркфлоу:

```
settings {executionOrder}                     -> 200 ok
settings {executionOrder, callerPolicy}       -> 200 ok
settings {executionOrder, availableInMCP}     -> 200 ok
settings {executionOrder, binaryMode}         -> 400 "settings must NOT have additional properties"
PUT без ключа settings вовсе                  -> 400 "must have required property 'settings'"
```

Живые настройки:
`{"executionOrder":"v1","binaryMode":"separate","availableInMCP":false,"callerPolicy":"workflowsFromSameOwner"}`.

**Следствие: любая правка узлов или связей выполняется владельцем в интерфейсе
n8n.** Через API запись прошла бы, но `binaryMode: "separate"` был бы утрачен
без возможности вернуть тем же каналом.

**Что через API можно:** чтение всего; создание и удаление воркфлоу;
включение/выключение через `POST /workflows/{id}/activate` и `/deactivate` —
эти эндпоинты `settings` не трогают (проверено на одноразовом воркфлоу).

### 3.2. Данные саб-ноды LM недостижимы из code-ноды

Проверено 2026-08-19 пробником с боевой топологией (agent 3.1 +
lmChatOpenRouter), перебором 14 способов доступа:

```
$('LM').all() / .all(0,0) / .first()   -> Error: No data found from `main` input
$items('LM') / $items('LM',0,0)        -> то же
$node['LM'] / $node['LM'].json         -> то же
$('LM').item                           -> Invalid expression
$('LM').isExecuted -> true (булево)    $('LM').params -> статика
$execution -> работает                 $('Agent').all() -> только {output}
```

Причина: саб-нода отдаёт данные по связи `ai_languageModel`, а интерфейс `$()`
ходит только в `main`. Ноды-обёртки не существует: у саб-ноды нет main-выхода
по определению.

Подробности и следствия — в докстроке
`nocodb/patch_guard_abort_detection.py`.

### 3.3. Ретенция истории исполнений n8n — около 2,5 суток

Исполнения старше пропадают: обращение к `/executions/3463` через двое суток
вернуло 404. **Следствие:** тела запросов для повторных прогонов нужно
сохранять сразу; отчёты по частоте (`nocodb/guard_report.py`) видят только это
окно.

### 3.4. Ключ OpenRouter недоступен

Лежит в credentials n8n (`openRouterApi`, id `hrFobDiOtSwC9E0F`), в `.env`
проекта не выдаётся. Запросить API OpenRouter по `generation_id` изнутри этого
репозитория нельзя — данные из панели OpenRouter предоставляет владелец.

Поле `native_finish_reason` в данных исполнения n8n отсутствует вовсе:
`generationInfo` хранит только `finish_reason`.

копия**, залитая для примера. Рабочий бот живёт в отдельном репозитории

`cabinet`, `cabinet_url`, `CABINET_LINK` даёт **ноль** совпадений, хотя
кабинетная механика в боте работает с 2026-08 (payload содержит `cabinet_url` и
`cabinet_status`, см. любое исполнение n8n).

**Не редактировать. Не считать источником истины.** Всё, что касается
поведения бота, уточняется у владельца или в репозитории `unifiedbot`.

### 5.2. `doc/ARCHITECTURE.md` и `doc/TECH_BREAKDOWN.md` — той же природы

Bitrix24. Даты правки — июнь 2026, то есть старше всех описанных здесь работ.

Такие же справочные копии. Править нельзя, устаревание не отслеживается.

Не путать с `doc/N8N_ARCHITECTURE.md` (май 2026) — он про n8n, но тоже давний.
Актуальные документы этого проекта лежат в `docs/` (без `doc/`): `CONCEPTS.md`,
`docs/resolver-rules.md`, `docs/test-contour-checklist.md`,

## 6. Незакрытое

### 6.1. Одиночный кредит фактически не проверен

Прогон 3568 (раздел 2.1) помечен как `credit`, но вызвал `combo_calculator` —
это артефакт способа сборки тела запроса, а не поведение кредитного сценария.

**Почему комбо-тело не годится.** Тело было получено из исполнения 3517 (комбо)
и в нём менялось только поле `session_context.request_type` на `credit`.
Остальное осталось комбо-запросом: в нём есть госномер, а кэш несёт
`type_name: "Расчет комбо (Трейд-ин + Кредит)"`. Модель увидела данные
трейд-ина и позвала комбо-инструмент. Настоящий кредитный диалог таких данных
не содержит.

**Косвенный довод, что переименование кредит не задевает:** среди активных
кредитных блоков инструмент упоминает только `finalize_deal` —
`ST_CREDIT_CLOSING`, `BLK_CREDIT_NO_PHONE`, `BLK_CREDIT_NO_PHONE_REPEAT`,
`BLK_CREDIT_PAUSE`. Имени `combo_calculator` в кредитных блоках нет. Это
рассуждение, а не замер.

**Чего не хватает:** захваченного тела реального кредитного диалога до вызова
инструмента. Из-за ретенции (3.3) старые исполнения недоступны — нужен свежий
диалог на стенде.

### 6.2. Прод v2 несёт то же расхождение имён

`flow/AI Agent v2.0 MAX.json` содержит узел `Combo Calculator`; `Prompts.csv`
(старая таблица промптов боевого бота) содержит `combo_calculator` — три
вхождения.

То есть в проде та же мина, латентная: видимо, модель прода расхождение
переживает, как и `gemini-3.1-flash-lite`.

**Решение владельца: не трогать.** Через несколько дней планируется переезд на
v3, боевую версию решено оставить как есть.

### 6.3. Печать адреса кабинета текстом вместо маркера

Контракт `[CABINET_LINK]` (раздел 5 документа `N8N_HANDOFF_CABINET.md` в
репозитории бота, коммит f815255 там же) требует, чтобы модель **никогда** не
печатала адрес кабинета: вместо адреса ставится маркер, бот подставляет
гиперссылку.

Маркерная инструкция живёт только в трёх блоках `BLK_*_CABINET_CHOSEN`, которые
попадают в промпт лишь на интенте `choose_cabinet`. На других ходах ничто не
запрещает напечатать адрес — и в исполнении **3521** модель это сделала:

> «…заполнить детали в личном кабинете на нашем сайте:
> `https://demo.autodc.org/cabinet#t=…`»

Формально нарушения нет (правило вне тех блоков не действует), но контракт
говорит «никогда». Наблюдение зафиксировано, в работу не бралось.

### 6.4. `T-01_TOOLS` неактивен, а ветка компилятора под него не срабатывает

В NocoDB блок `T-01_TOOLS` имеет `Active=false` (длина 3028 симв.). Ветка
`Prompt Compiler`, которая его подставляет
(`nocodb/build_v3_workflow.py:274`):

```js
if (useTFinalize) parts.push(content("T_FINALIZE"));
// переходный фолбэк: пока T_FINALIZE не активирован владельцем — старый T-01 по tools_open
else if (turn.tools_open && active("T-01_TOOLS")) parts.push(content("T-01_TOOLS"));
```

`T_FINALIZE` активен (`Active=true`, 3019 симв.), поэтому первая ветка
срабатывает всегда, а вторая — никогда. Переходный фолбэк отработал и больше не
нужен.

**Что не сделано:** ни блок не заархивирован, ни мёртвая ветка не убрана.
Отдельная задача, в работу не бралась.

## 7. Решения владельца, действующие как правила

### 7.1. Модель — `gemini-3.1-flash-lite`

Переведена владельцем 2026-08-28 в 11:22 UTC, после инцидента 3517 (который шёл

Узел `Agent LM` — тип `lmChatOpenRouter`, credentials `openRouterApi`
(`hrFobDiOtSwC9E0F`). Резервная модель `Agent LM Fallback` —
`openai/gpt-4.1-mini` через `openAiApi` (`PtI7CvwiH2WYU1pM`), подключена с

### 7.2. Теневой резолвер остаётся включённым

`[TEST] AI Resolver (shadow)` (id `F3eluZCNKGAcPwOT`) активен. Отключение
предлагалось и **отменено**.

Устройство: собственный вебхук `POST /webhook/ai-resolver-shadow-test`, который
дёргает бот (`user-agent: Python/3.11 aiohttp/3.13.3`). Цепочка:
`Webhook → Unwrap Body → Resolver Core → Prepare Log → Save Log (NocoDB)`.
Узла `Respond to Webhook` нет — вызов односторонний.

**Следствие, которое стоит знать:** `Tool: Resolver Core` за один ход диалога
запускается дважды — один раз из узла `Run Resolver` основного воркфлоу, один
раз из теневого. Это удвоенный расход модели на классификацию, и это задумано.

В `Resolver_Shadow_Log` на 2026-08-28 было 53 записи (первая 2026-07-10,
вердикты: 52 `ok`, 1 `unknown_intent`). Критерий приёмки контура
(`docs/test-contour-checklist.md:129`) требует **≥100 размеченных ходов** —
порог не достигнут. Потребитель лога — `nocodb/shadow_report.py`.

### 7.3. Имя инструмента: `combo_calculator` в v3, `Combo Calculator` в v2

Расхождение **намеренное**. В v3 узел переименован ради совпадения с промптом
(раздел 1.4); в v2 имя остаётся прежним, потому что v3 клонирует тул-узлы из v2
по имени, а прод решено не трогать (6.2).

Объяснение продублировано в трёх местах, чтобы его не «исправили обратно»: в
комментарии к `TOOL_NODES` в `nocodb/build_v3_workflow.py`, в сообщении коммита
`f527a68` и здесь.

### 7.4. Активация кабинета выполнена

2026-08-19 включены все три сценария (`credit → tradein → combo`, по одному
запуску с проверкой между ними). Итог: `G-07_CABINET.Scenario =

## 8. Что делать дальше

По убыванию приоритета. Для каждого пункта указано, чего не хватает.

### 8.1. Проверить одиночный кредит на живом диалоге

**Зачем:** единственная непроверенная фактически часть переименования (6.1).
**Чего не хватает:** свежего диалога по кредиту на стенде, доведённого до
вызова инструмента. Из-за ретенции 2,5 суток захватывать тело нужно сразу после

`[TEST] AI Agent v3.0` и сохранить в файл.
**Как проверить:** повторить запрос на вебхук `/webhook/ai-handoff-v3-test` и
убедиться, что вызван ожидаемый инструмент, `finish_reason: tool_calls,stop`,

**Зачем:** эвристика обрыва в `Tool Guard` калибровалась на 15 исполнениях с
одним обрывом — это отсутствие противоречий, а не измеренная точность.

расхождение эвристики с настоящим `finish_reason`.
**Чего не хватает:** накопленных исполнений. Ограничение — ретенция 2,5 суток
(3.3), поэтому отчёт надо снимать регулярно, либо заводить долгий стор
