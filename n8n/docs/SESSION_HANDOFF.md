### Правила работы, действующие с 2026-09-16

- **Прогоны на `[TEST]` — без `deal_id`.** Контур побайтово совпадает с продом
  по всем code-нодам и читает **те же** таблицы NocoDB; «тестовый» он только по
  вебхуку и саб-воркфлоу. За его ngrok-адресом — **дев Python-бот с доступом к
  боевому Bitrix**. Тулы привязаны к агенту связями графа, поэтому вход не может
  запретить модели вызвать `finalize_deal`. Пустой `deal_id` отсекает всю работу
  с Bitrix на стороне бота (`main.py:889`), а создающих вызовов `crm.deal.add` /
  `crm.contact.add` в обработчике нет вовсе. Разбор —
  `docs/solutions/conventions/test-contour-runs-isolation-from-live-crm.md`.
- **Дилер `99`** (тестовый дилер дев-стенда) и **`user_id` с префиксом
  `test-debrand-` / `test-`** во всех прогонах. Таких пользователей нет в БД
  бота, поэтому `UPDATE User` не заденет ни строки.
- **Алерт по неизвестному `user_id` уходит в `SUPPORT_GROUP_ID` дев-образа**, а
  не в группу дилера 99: группа выбирается по `start_code` из БД бота
  (`main.py:947-952`), а не по коду дилера из payload.
- **Протокол правки блоков** (`apply_*.py`): срез «до» → dry-run → снапшот →
  проверка отката на одном блоке → `--apply` → независимая сверка sha. Снапшот
  пишется **один раз**; повторный `--apply` его не трогает — иначе путь отката
  исчезает молча, см.
  `docs/solutions/bugs/rollback-snapshot-overwritten-by-repeat-apply.md`.
- **Канонический запуск sim-тестов** — `node --test flow/lib/*.test.mjs`.
- **Классы плейсхолдеров A/B/C** — прежде чем трогать любой шаблон в квадратных
  скобках, определить класс:
  `docs/solutions/design-patterns/prompt-placeholder-classes.md`.

### Связь с Python-стороной

Бот — отдельный проект **UnifiedBot**, репозиторий `unifiedbot_dev_cabinet`.
Там идёт работа по многоботности: один бот на бренд или группу брендов, 5–8
ботов на канал (MAX и Telegram), ветка `feat/multibot-brand-routing`.

**Для n8n проверено:** `user_id` нового формата `"<bot_key>:<id мессенджера>"`
(например `tg-geely:123456789`) проходит прод-контур без изменений. Приведения к
числу нет ни в одной ноде, разбора по `:`, `_`, `-` над `user_id` нет, памяти
агента с `sessionKey` не существует, единственная запись `user_id` в NocoDB —
колонка `SingleLineText`. `session_id` вида `sess_tg-geely:123456789_99AB12CD`
тоже переживает: единственный его потребитель — `LIKE` в
`Get Session Logs (API)`, а `:` и `-` там литералы. **Правок воркфлоу не
требуется.** Брендовая маршрутизация уже приезжает в payload
(`data_routing.*`, `qualification_context.dealer_id`, `session_context.dealer_*`),
названия каналов и ботов в логике n8n не участвуют.

**Точная граница доказанного по возврату в `/n8n_callback`.** Сохранность
значения подтверждена **конфигурацией нод и живым типом на входе**
`TOOL: Save to CRM`: схема поля `user_id` объявлена `string`,
`attemptToConvertTypes` выключен, а исполнение 4377 показало на входе
`"user_id": "1789319758536"` — строкой. **Снимком тела исходящего запроса это НЕ
подтверждено**: n8n тело HTTP-запроса в данных исполнения не хранит. Живая
проверка запланирована на Python-стороне — пилот U8 плана
`docs/plans/2026-09-15-001-feat-multibot-brand-routing-plan.md` в репозитории
`unifiedbot_dev_cabinet`. До неё формулировка «байт-в-байт» держится на выводе
из конфигурации, а не на замере провода.

Две отложенные задачи касаются обеих сторон: **З-6** (`/n8n_callback` без
аутентификации) и **З-2** (заглушка «Клиент» в `user_data.name`).

### З-5. `Get Session Logs (API)`: публичный GET без авторизации и склейка SQL

Воркфлоу `Get Session Logs (API)`, id `I7r3lWLiKmW1HojQ`, активен и используется:
Python зовёт его из `fetch_n8n_logs_for_archive` (`main.py:1514`) при архивации
диалога. Живое исполнение 4448 от 2026-09-16 04:11.

Две проблемы в одной ноде `Postgres (n8n DB)`:

```sql
WHERE d.data::text LIKE '%sess_{{ $json.query.session_id }}%'
```

1. **Параметр вебхука склеивается в SQL** без кавычек и экранирования. Сегодня
   не стреляет: `session_id` собирается из `bot_key` (`[a-z0-9-]`) и кода
   `start_code` формата `\d{2}[A-Z0-9]{6}` — две цифры (код дилера) плюс шесть
   заглавных латинских букв или цифр. Ни в одном из наборов апострофа нет, взяться
   ему неоткуда. Но это инъекционная поверхность: вывод держится на charset
   входа, а не на экранировании, и падает при любом его расширении.
2. **Вебхук `GET /webhook/get-session-logs` без аутентификации** (`options: {}`),
   отдаёт сырые `execution_data` до трёх исполнений — то есть полные диалоги
   любого клиента тому, кто знает или подберёт `session_id`.

Состояние: **не начато**.

### З-3. Замеры приёмки де-брендинга

Правка применена 2026-09-16. Три замера закрывают окно ретенции исполнений
(~2.5 суток), поэтому промежутков без покрытия не остаётся:

```bash
# 7-е сутки — вторник 2026-09-23
python3 debrand_observe.py --label after-7d --limit 60 --budget 300
python3 debrand_observe.py --compare before after-7d
```

Критерии приёмки, все должны выполниться на каждом замере:

| Показатель в выводе `--compare` | Порог |
|---|---|
| `ответов с нарушением по марке` | **0** |
| `из них с утечкой в ответ` | **0** |
| `медиана длины ответа` | в коридоре **242–362** симв. (база «до» — 302, порог ±20 %) |
| `медиана [SPLIT] на ход` | в коридоре **0.8–1.2** (база «до» — 1.0) |

**Что считается нарушением по марке.** Упоминание марки само по себе — НЕ
нарушение: дилеры торгуют разными брендами, и назвать клиенту его собственную
марку штатно. Нарушение — ровно два случая:

- **(а)** в ответе есть **«Dargo»** — модель из снятого примера, её появление
  означает, что модель процитировала образец вместо данных клиента;
- **(б)** в ответе названа марка, которой нет в `ai_clean_context` этого хода
  (ни в `model`, ни в названиях комплектаций) и рядом с которой не стоит машина
  клиента.

Оговорка к (б): в боевых данных `model` часто приходит без марки
(`"model": "CITYRAY"`), и ассистент дописывает её сам — «Geely CITYRAY». Это
законно, поэтому марка засчитывается своей, если стоит в пределах ±40 символов
от названия машины клиента. Реализация и границы метода — в докстроке
`brand_violations()` (`nocodb/debrand_observe.py`); проверка уровня модели, кроме
Dargo, не делается сознательно.

Прежний критерий «`ответов с маркой` = 0» был неверен: он считал нарушением
любое `haval|dargo` и давал ложные срабатывания на законном трафике Haval.
Замерено: на 30 прогонах приёмки старая проверка пометила бы **9 из 30**.

**Перед каждым замером прогонять контрольные кейсы детектора:**

```bash
cd nocodb
python3 debrand_observe.py --selftest
```

Девять кейсов: пять на законных ответах (включая реальные исполнения 4395, 4441,
4406) и три искусственных нарушения. Ожидается `сбоев: 0`. Если детектор
сбоит — замер бессмыслен, чинить сначала его.

**Что делать, если критерий не выполнен: НЕ откатывать самостоятельно.**
Собрать отчёт владельцу и остановиться. В отчёт: какой именно критерий и на
сколько не выполнен, номера исполнений с нарушением, текст ответа клиенту и
содержимое `ai_clean_context` на этих ходах (есть ли в нём `model` и
комплектация — от этого зависит, дефект это правки или отсутствие данных на
входе). Команда отката существует и проверена, но применяет её владелец:

```bash
cd nocodb
python3 apply_debrand_blocks.py --rollback
```

Причина запрета на самостоятельный откат: правка сидит в живой боевой таблице,
которую `Prompt Compiler` читает на каждом ходе, и откат мгновенно вернёт в
промпт «Haval Dargo» всем брендам. Решение о размене должно быть осознанным.

## 3. Что сделано по существу

### 3.1. Цепочка доставки данных оценки

Задача из `docs/N8N_HANDOFF_CABINET.md`: кабинет морозит снапшот калькулятора
из `n8n_cache` и ждёт там два ключа верхнего уровня — `found_info` (сырой блок
auto.ru плюс госномер) и `ti_valuation` (число).

Маршрут данных после правок:

```
auto.ru → [TEST] TOOL: AUTO.RU EVALUATION
             └ нода Code in JavaScript: found_info целиком + вложенный plate   (U1)
                  ├─ чистый трейд-ин: observation тула evaluate_auto
                  └─ комбо: combo_prepare.js → tradein_evaluation.found_info   (U4)
                       → Merge Calc (СНИМАЕТ обёртку response!)
                            ↓
                   Agent / Agent Retry → intermediateSteps
                            ↓
                   Final Response: evalFromSteps() + evalFromCarryover()        (U3)
                            ↓  тот же хелпер в Bypass Respond и Reminder Respond
                        json_cache → бот → n8n_cache → снапшот кабинета
```

### 3.2. Ключевые проектные решения

- **Чиним в источнике.** `found_info` пробрасывается терминальной нодой воркфлоу
  оценки — одна правка кормит обе ветки.
- **Канал в главный конвейер — `intermediateSteps`** обоих агентов. У `Post Guard`
  шагов нет, поэтому читаются и `Agent`, и `Agent Retry`, иначе оценка на
  retry-ходе теряется.
- **Извлечение по ФОРМЕ данных**, а не по пути и не по имени тула. Три раза
  подряд предположение о форме оказалось неверным (см. 4.1), поэтому сейчас
  сканируются оба контейнера (`item` и `item.response`) и обе формы записи
  (`tradein_evaluation` либо `status`+`tradein_price_to`).
- **Перенос между ходами — через `evaluation_carryover`**, не через `json_cache`.
  Бот перезаписывает контекст целиком и на rebuild-ходе (TTL 600 с либо переход
  к стадии расчёта) шлёт `cached_json = null`; прежнего кэша в этот момент нет
  ни под каким ключом.
- **Хелпер вливания подмешан во все три выхода**, возвращающих `json_cache`
  (`Final Response`, `Bypass Respond`, `Reminder Respond`), потому что кабинет
  морозит снапшот на каждом ходе.
- **Строго ПОСЛЕ Cache Gate.** Гейт различает ходы по непустоте `cached_json`;
  carryover, влитый до него, увёл бы rebuild-ход в обход Car Search и каталог
  перестал бы обновляться. `Attach Cache` сознательно не трогаем.

### 3.3. Что защищено и почему

Файлы канона Calc Engine правит кабинетный агент; его автотесты сверяют статику
с каноном побайтово. **Не менять без согласования:** `flow/lib/calc_engine.js`,
`calc_engine.golden.test.mjs`, `golden_cases.json`, `build_calc_engine_workflow.py`,

## 5. Что открыто и ждёт решения

### 5.1. Фолбэк-ответы Александра — диагностировано, решение не принято

Симптом: на ходе с сообщением клиента про пробег («35 тыс») Александр отвечает
«Извините, произошла небольшая техническая заминка…».

Причина установлена по 13 ходам в окне ретенции. Это дефолт из `Final Response`,
срабатывающий когда пусты и черновик агента, и результат повтора. Модель
`google/gemini-2.5-flash-lite` возвращает `finish_reason: "error"` с нулём
токенов — успешный HTTP-ответ без содержимого. Перед срывом агент шлёт один и
тот же запрос по 3–4 раза (одинаковый `promptTokens`): модель отдаёт
`finish_reason: tool_calls` без пригодного к разбору вызова.

Две дыры в страховке:

1. `Agent LM Fallback` (`openai/gpt-4.1-mini`) подключён к обоим агентам,
   `needsFallback: True`, но **не вызывался ни разу за 13 ходов** — механизм
   n8n срабатывает на выброшенное исключение, а здесь ответ формально успешный.
2. `Agent Retry` питается **той же** `Agent LM`, то есть повтор идёт в ту же
   нестабильную модель.

Комбо страдает чаще трейд-ина: трейд-ин укладывается в один раунд вызова
инструмента, комбо стабильно требует три-четыре (у тула шесть параметров).
Частота: 2 фолбэка из 13 ходов; по комбо-ходам с инструментом — 2 из 5.

Мои правки ни при чём: холостые раунды идут при неизменном `promptTokens`, то
есть до попадания данных в контекст. `found_info` — 523 символа, 4% комбо-ответа.

**Три предложенных варианта, решение за владельцем:**

| # | Правка | Цена |
|---|---|---|
| A | отвязать `Agent LM` от `Agent Retry`, оставить там только `Agent LM Fallback` — повтор пойдёт в другую модель | одна строка в `build_v3_workflow.py` + переимпорт |
| B | разрешить второй повтор в `Tool Guard` (сейчас ровно один) — осмысленно только вместе с A | небольшая правка |
| C | перевести `Agent LM` с `gemini-2.5-flash-lite` на `gemini-2.5-flash` — убрать холостые раунды и латентность | прямое удорожание каждого хода |

Рекомендация была: A обязательно, B вместе с A, C — по решению владельца.

### 5.2. Внешняя зависимость: `evaluation_carryover`

Реализация в n8n уже сделана против этого контракта и терпит отсутствие ключа.
До выкатки данные доедут в `json_cache` на ходе оценки, но **не переживут первую
пересборку кэша** — примерно на десятой минуте диалога. Это известное ограничение,
а не баг: шаг 5 раздела H чек-листа до выкатки непроверяем.

### 5.3. Экономия платных вызовов оценки — замер сделан, работа не начата

Вызов auto.ru платный, а сабфлоу оценки исполняется **безусловно при каждом**
вызове Combo Calculator (`Execute Workflow` до `Prepare Combo`, кэша по паре
«госномер + пробег» нет). Ни один активный промпт-блок повторный вызов не
запрещает.

Замер по логам дал мало: ретенция исполнений n8n ~2.5 суток, в окне был **один**
комбо-диалог с **одним** вызовом. Сценарий «десяток вызовов» не опровергнут — он
не наблюдался.

Порядок согласован с владельцем: **сначала промпт и контекст, потом замер с
заранее включённым сбором, кэш — по числам. Кэш не начинать.**

Промптовая часть уже готова черновиком `BLK_EVAL_REUSE` (Active=false) плюс
вывод `ti_valuation`/`ti_evaluated_car` в `ai_clean_context` (уже в коде).

Оценка кэша на стороне n8n, если дойдёт: отдельный план на 3–4 юнита, риск
средне-высокий (вмешательство в граф Combo Calculator задевает монолитный
билд-скрипт, чью идемпотентность придётся доказывать заново), покрывает только
комбо-маршрут — чистый `evaluate_auto` агент зовёт напрямую.

## 7. Разведка для будущей переработки промпта

`docs/prompt-branches-map.md` — полная карта диалоговых веток, снята с живых
данных 2026-08-13. Ничего не правилось, это чистая разведка по заказу владельца.

Самое существенное из найденного:

- **Колонки `Level` и `Stage` у блока компилятор не читает вообще.** Подключение
  определяется только `Block_ID`, `Active`, `Intent_Triggers` и `Scenario`.
  Способов попасть в промпт ровно четыре, один из них — жёсткий список имён
  внутри JS-кода ноды. Поэтому `G-07_CABINET` потребовал правки кода.
- **Девять активных блоков мертвы** (~2100 токенов): вытеснены механизмом `_V2`
  либо не имеют ссылок. Правка такого блока не даёт эффекта и никак не сигналится.
- **Стадию считает бот, не n8n.** `Stage Classifier` берёт готовое
  `session_context.current_stage` и только переопределяет по интенту.
- **Стадия `tool_needed` в `stock` и `consult` пустая**: профильные блоки —
  заглушки «[TODO владелец контента]» с июля, фолбэк `WF_*_LEGACY` тоже выключен.
- **Шесть живых конфликтов** с цитатами, в том числе `G-03_GOAL` («каждое
  сообщение ведёт к визиту», v3.00) против трёх `CS_*_V2` (обязательный
  проверочный вопрос, v3.03) — оба текста в каждом промпте трёх сценариев.
- Выключенного legacy-контента 13 157 токенов — вчетверо больше самого тяжёлого
  живого промпта (2891).

Владелец собирается перерабатывать промпт комплексно и просил **не предлагать
улучшений**, пока не изучит карту.
