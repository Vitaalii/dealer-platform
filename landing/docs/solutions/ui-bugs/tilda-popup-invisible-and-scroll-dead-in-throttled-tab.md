# Нативный поп-ап Tilda невидим, а скролл мёртв в приторможенной вкладке

## Problem

`tilda-popup-1.0.min.js` вешает блокировку скролла синхронно, а видимость поп-апа отдаёт CSS-переходу. Когда вкладка скрыта или приторможена, переход не выполняется: класс стоит, `opacity` остаётся `0`, скролл заблокирован. Для посетителя страница выглядит мёртвой — ничего не открылось и ничего не прокручивается.

## Symptoms

- Клик по `a[href="#popup:infoblock"]` ничего не показывает, страница перестаёт скроллиться.
- Проявляется не при загрузке, а на уже работавшей странице: поп-ап до этого открывался и закрывался нормально, а сломался после ~5 минут бездействия.
- `document.body.className` содержит `t-body_popupshowed t390__body_popupshowed`.
- `document.body.style.overflow` при этом **пуст** — блокировку держит класс Tilda, а не инлайновый стиль.
- У `.t-popup`: `display: block`, класс `t-popup_show` присутствует, `opacity: 0`.

## What Didn't Work

- **Подозрение на гонку при инициализации.** Опровергнуто: T390 вешает делегированный слушатель на `document` внутри `t_onReady`, он привязывается один раз и навсегда. К моменту отказа обработчик уже дважды успешно отработал.
- **Подозрение на переинициализацию разметки сторонним скриптом.** Опровергнуто замером: `MutationObserver` на блоке с ссылкой и на секции поп-апа за 6 минут зафиксировал **ноль мутаций**. Узел ссылки остался тем же, `isConnected: true`.
- **Подозрение на наш код блокировки скролла.** Опровергнуто: `body.style.overflow` в сломанном состоянии пуст.
- **`document.querySelector('[data-popup-id="..."]') → null` как признак пропавшего поп-апа.** Ложный след: таких узлов на странице нет вообще и никогда не было — поп-апы T390 адресуются через `data-tooltip-hook`. `data-popup-id` относится к другому механизму поп-апов Tilda.
- **Только `opacity: 1 !important`.** Не помогает: незавершённый переход продолжает управлять значением, пока не доиграет, и в приторможенной вкладке `opacity` так и остаётся `0`.

## Solution

Выключить сам переход, а не только задать конечное значение:

```css
/* В своём T123-блоке, глобально для нативных поп-апов Tilda */
.t-popup { transition: none !important; }
.t-popup.t-popup_show { opacity: 1 !important; }
```

Плюс сторож на случай, если обработчик Tilda прервётся между установкой класса и показом поп-апа и блокировка останется висеть:

```js
/* Инвариант: t-body_popupshowed имеет смысл только когда в DOM
   есть хотя бы один показанный .t-popup. Нарушение — чиним. */
function healStuckTildaLock() {
    if (!document.body.classList.contains('t-body_popupshowed')) return;
    if (document.querySelector('.t-popup.t-popup_show')) return;
    document.body.classList.remove('t-body_popupshowed', 't390__body_popupshowed');
    console.warn('⚠️ снят зависший t-body_popupshowed — показанных поп-апов Tilda в DOM нет');
}
```

Вызывать на смене экрана и на `visibilitychange` при возврате во вкладку.

## Why This Works

Цепочка отказа:

1. По клику Tilda **синхронно** ставит `display: block`, класс `t-popup_show` и `t-body_popupshowed` на `<body>` — скролл блокируется немедленно.
2. Видимость зависит от `transition: opacity 0.3s ease-in-out` из `opacity: 0`.
3. В скрытой вкладке браузер переход не продвигает. Класс стоит, значение остаётся нулевым.
4. Результат: модальное окно «открыто» и невидимо, страница не скроллится.

Пятиминутный порог — это Chrome intensive throttling. Замер на живой странице: секундный интервал за 376 с сработал 34 раза, дрейф после ~5 минут в фоне — ровно ~59 с на тик, то есть таймеры зажаты до одного срабатывания в минуту. Зависший поп-ап продержался в состоянии `display:block / t-popup_show / opacity:0` больше шести минут.

Ключевой момент, ради которого этот урок и записан: **идущий CSS-переход перебивает `!important` на целевом свойстве.** Пока переход не доиграл, используемое значение диктует он, а не каскад. Поэтому лечится именно `transition: none`, а не более «сильное» объявление `opacity`.

## Prevention

- Если видимость модального окна зависит от CSS-перехода, а блокировка скролла ставится синхронно — это состояние рассинхронизируется в любой приторможенной вкладке. Либо оба шага синхронные, либо блокировка снимается по тому же событию, что и показ.
- Переопределяя чужую анимацию, отключайте `transition`, а не только конечное значение. `!important` на свойстве не останавливает уже идущий переход.
- Держите инвариант «глобальный флаг блокировки истинен только при наличии видимого владельца» и умейте его проверить. Флаг на `<body>` без владельца в DOM — всегда баг.
- Проверять модальные окна нужно в том числе в скрытой вкладке: переключиться на другое окно на 5+ минут, вернуться и кликнуть. Обычный прогон в активной вкладке этот класс отказов не ловит.
- Замеряйте троттлинг напрямую: `setInterval` с записью дрейфа показывает зажатие таймеров однозначно, без догадок.
