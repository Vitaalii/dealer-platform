# Два блока инициализируют один ресурс — порядок `$(document).ready` решает, кто первый

## Problem

Блок U7 (контакты) потребляет `window._dealerReady` — промис со строкой дилера, который штатно создаёт U2. На странице, где U2 нет, U7 должен создать промис сам.

Наивная реализация запасного пути выглядит безобидно:

```js
$(document).ready(function () {
    ensureDealerReady();          // создаёт промис, если его ещё нет
});
```

На странице без U2 это работает. На странице квиза, где U2 есть, U7 всё равно делал свой запрос — то есть таблица дилеров запрашивалась **дважды за загрузку**, а `window._dealerReady` дважды перезаписывался.

## Symptoms

- В сетевой панели два запроса к `/catalog/{table}` вместо одного.
- Поведение зависит от страницы при полностью одинаковом коде блока.
- Проверка `if (window._dealerReady) return;` внутри функции стоит и выглядит рабочей, но не срабатывает.

## Root cause

jQuery выполняет ready-обработчики **в порядке регистрации**, а регистрация идёт в порядке выполнения скриптов — то есть в порядке блоков на странице.

На странице квиза расстановка такая:

```
rec2472574461  форма Tilda
rec3792600201  U7   ← регистрирует свой ready первым
rec2472574541  U2   ← регистрирует свой ready вторым
rec3783092401  U1
```

Вся очередь ready отрабатывает синхронно в одном тике:

```
тик ready:
  U7.ready()  → _dealerReady ещё undefined → создаёт свой  ← дубль
  U2.ready()  → init() → _dealerReady = свой промис        ← перезапись
```

Проверка «промис уже есть» ничего не ловила, потому что на момент её выполнения U2 ещё не отработал. Порядок блоков в редакторе Tilda — не гарантия и меняется мышью, поэтому «поставить U7 ниже U2» решением не является.

## What didn't work

- **Проверка `if (window._dealerReady) return;` внутри ready-обработчика.** Проверяет слишком рано — вопрос не в наличии проверки, а в моменте.
- **Рассчитывать на порядок блоков.** В Tilda он меняется перетаскиванием и нигде не зафиксирован.
- **Вывод по коду вместо замера.** Порядок ready-обработчиков из исходника одного блока не виден: он определяется расстановкой на странице.

## Solution

Отложить инициализацию в **макрозадачу** — тогда она выполнится после того, как вся очередь ready опустеет:

```js
$(document).ready(function () {
    // ... остальная инициализация блока ...

    setTimeout(ensureDealerReady, 0);
});
```

Нулевой таймаут ставит вызов в очередь макрозадач, а все ready-обработчики выполняются синхронно в текущем тике. К моменту вызова блок-владелец уже успел выставить глобал.

Условие корректности: **владелец должен присваивать глобал синхронно**, до первого `await`. В нашем случае U2 присваивает `window._dealerReady` в начале `init()`, до `await loadCarData(...)` — проверено по коду. Если бы владелец присваивал глобал после await, `setTimeout(…, 0)` не помог бы и понадобился бы явный сигнал готовности (событие или промис-регистр).

## Why this works

- Обработчики `$(document).ready` выполняются синхронно, один за другим, в пределах одного тика.
- `setTimeout(fn, 0)` — макрозадача, она не может выполниться, пока текущий тик не завершён.
- Значит отложенный вызов гарантированно видит результат всех ready-обработчиков, независимо от того, какой блок стоит выше.

## Verification

Стенд: `docs/testing/dealer-ready-order.html`

Он воспроизводит именно расстановку «потребитель выше владельца» с настоящей jQuery 1.10.2 и печатает фактическую последовательность:

```
U7 ready-обработчик: _dealerReady = undefined
U7 ready-обработчик: отложил ensureDealerReady на макрозадачу
U2 ready-обработчик: присваиваю _dealerReady синхронно
U7 ensureDealerReady: промис уже есть → СВОЙ ЗАПРОС НЕ ДЕЛАЕМ
ИТОГ: _dealerReady = ОТ U2 ; U7 делал свой запрос: false
```

Стенд написан под общий случай, а не под этот баг: чтобы проверить похожую ситуацию, достаточно заменить имена в двух заглушках — «владелец» и «потребитель». Пригодится всякий раз, когда два независимых блока на одной странице могут инициализировать один и тот же ресурс.

Обе ветки надо проверять: с владельцем на странице (дубля быть не должно) и без него (запасной путь обязан сработать).

## Prevention

- **Если блок создаёт ресурс, который может создать и кто-то другой, — откладывай создание в макрозадачу.** Синхронная проверка в ready ловит только тех владельцев, что стоят выше по странице.
- **Не закладывайся на порядок блоков Tilda.** Он не зафиксирован и меняется в редакторе.
- **Считай запросы, а не полагайся на глаз.** Признак этого класса ошибок — лишний сетевой запрос, а не видимая поломка: страница выглядит рабочей.
- **Проверяй на обеих страницах.** Дублирование проявляется только там, где присутствуют оба блока.
