# «Галерея стала медленнее» — как отличить регресс блока от разброса бутстрапа и бэкенда

## Context

2026-09-19 поступила жалоба: после трёх правок (проверка согласия в U6, вынос цвета кнопки в CSS-переменную, блок «Опции» в U3) галерея на шаге 2 стала заметно дольше грузиться. Замечено на глаз, цифр не было.

Измерения показали, что замедления нет, а ощущение создаёт разброс, который на порядок больше вклада любого кода блоков.

## Где на самом деле время

Разложение задержки до первой фотографии на холодном кеше:

| Этап | Время | Чьё |
|------|-------|-----|
| Бутстрап Tilda до старта запросов к данным | ~1 790 мс | jQuery + нативный CSS Tilda, вне контроля проекта |
| Ответ `/catalog/{TABLE_MAIN}` | 620–830 мс (TTFB ~850 мс без сжатия) | бэкенд бота |
| Первый запрос фотографии | стартует на ~2 400 мс | следствие двух строк выше |
| **Вся синхронная работа всех блоков на переходе 1→2** | **8–10 мс** | наш код |

Соотношение и есть вывод: код блоков отвечает за доли процента наблюдаемого времени. Галерея не может показать фотографию раньше, чем придёт каталог, а каталог не запрашивается, пока не отработает бутстрап.

Фотографии при этом не были проблемой: webp, 46–138 КБ, в среднем 91 КБ, шесть штук на комплектацию.

## Разброс важнее среднего

Шесть прогонов, версии чередовались. Решающее наблюдение — не разница между версиями, а разница **внутри одной версии**:

```
версия «до», прогон 2:  бутстрап 1788 мс → первое фото 2411 мс
версия «до», прогон 3:  бутстрап  651 мс → первое фото 1421 мс   ← та же версия!
```

Почти 1.2 секунды разницы между двумя прогонами одного и того же кода — статика Tilda в одном случае пришла из кеша, в другом нет. Любая разница между версиями (60 мс в пользу новой) тонет в этом разбросе.

**Отсюда правило: один замер до и один после ничего не доказывают.** Нужно несколько прогонов каждой версии вперемешку, и сначала надо посмотреть на разброс внутри версии. Если он больше межверсионной разницы — вывода о регрессе сделать нельзя, каким бы убедительным ни казалось среднее.

## Как построить честный A/B на Tilda

Git в проекте нет, откатить блок для сравнения не из чего — но у Tilda обычно живёт предыдущая публикация под другим URL. Прежде чем сравнивать тайминги, **докажите, что пара версий отличается только тем, что вы исследуете.**

Проверка занимает одну команду: посчитать, сколько строк каждого блока рабочей копии присутствует на каждой из двух страниц.

```python
h = re.sub(r'\s+',' ', open('старая.html').read())
c = re.sub(r'\s+',' ', open('текущая.html').read())
for f in os.listdir('docs/tilda-blocks/Ver_3_ong/'):
    lines = [l.strip() for l in open(base+f) if len(l.strip()) >= 30]
    print(f, sum(l in h for l in lines), sum(l in c for l in lines), len(lines))
```

В этом случае вышло так:

| блок | старая страница | текущая |
|------|-----------------|---------|
| u1, u4, u7 | 256/256, 310/310, 255/319 | идентично |
| u2 | 188/210 | 208/210 |
| u3 | 599/623 | 623/623 |
| u6 | 653/755 | 755/755 |

Плюс проверка маркеров **более ранних** задач — они должны совпадать, иначе пара смешивает эффекты: валидация телефона 2/2, сторож отправки 2/2, свайп ряда названий 4/4, minus-features 6/6, запасной путь дилера отсутствует в обеих. Совпало — значит различие ровно в исследуемых правках, и сравнение изолирует именно их.

Если бы маркеры ранних задач разошлись, сравнение пришлось бы отбросить: оно измеряло бы сумму всех промежуточных изменений, а не три последние.

## Что мерить

Метрики, не зависящие от кеша картинок (он почти всегда прогрет и делает «время до отрисовки» нулевым):

```js
var res = performance.getEntriesByType('resource');
var cat = res.filter(e => /TABLE_MAIN_ID/.test(e.name))[0];
cat.startTime;   // когда фронт дошёл до запроса данных = стоимость бутстрапа
cat.duration;    // ответ бэкенда

var t = performance.now(); window.ucQuiz.goTo(2); performance.now() - t;
// goTo диспатчит uc:step синхронно → это вся работа всех слушателей разом

// дубликаты запросов — одной строкой
var m = {}; res.forEach(e => m[e.name] = (m[e.name]||0)+1);
Object.values(m).filter(v => v > 1).length;
```

Время ответа бэкенда честнее мерить вне браузера, серией:

```bash
for i in 1 2 3 4 5; do
  curl -sS -o /dev/null -w "%{time_total}s TTFB=%{time_starttransfer}s %{size_download}б\n" \
    "$API/catalog/$TABLE?cb=$RANDOM"
done
```

Осторожно: `curl` по умолчанию **не** запрашивает сжатие, а браузер запрашивает. Без `-H "Accept-Encoding: gzip"` цифры завышены — здесь 243 КБ и 1.67 с против 22 КБ и 1.03 с.

## Ловушка: инструментирование, которое само создаёт находку

Первый замер показал **15 495 вызовов `updateGallery` за один переход** — выглядело как найденная лавина. На чистой перезагрузке оказался **ровно один вызов**.

Причина: две обёртки, поставленные последовательными вызовами в консоли, замкнулись друг на друга. Первая сохранила оригинал, вторая сохранила первую, а повторное выполнение фрагмента переприсвоило захваченную ссылку — счётчик считал сам себя.

Правило: **после любой обёртки, давшей неожиданно большое число, перезагрузите страницу и поставьте ровно один слой инструментирования.** Аномалия, которая не переживает чистую перезагрузку, принадлежит замеру, а не коду. Здесь на это указывала и сама асимметрия — счётчик показывал 15 495, а собранных стеков был один; расхождение между двумя счётчиками одного события всегда означает, что считаются разные вещи.

## Что нашлось попутно

Ни у `/catalog`, ни у выдачи фотографий нет заголовков кеширования — ни `Cache-Control`, ни `ETag`, ни `Expires`. Браузер работает по эвристике, повторные визиты перезапрашивают неизменившееся. Это расширение уже отложенного пункта **R4** из `CLAUDE.md` (там он был только про `widget.js`), и чинится не в Tilda-блоках, а в `main.py` проекта бота.

Сжатие у `/catalog` при этом есть и работает: 22 КБ вместо 243 КБ.

## Prevention

- **Не притягивать причину к недавним правкам только потому, что они недавние.** Сначала измерить разложение по этапам; если код блоков стоит единицы миллисекунд против секунд ожидания, дальше искать в правках бессмысленно.
- **Смотреть разброс внутри версии до сравнения версий.** Если он больше межверсионной разницы, вывод о регрессе невозможен.
- **Валидировать пару A/B по содержимому, а не по названию URL.** «Предыдущая публикация» может оказаться на десятки задач старше.
- **Аномалию в замере проверять чистой перезагрузкой с одним слоем инструментирования**, прежде чем записывать её в находки.
